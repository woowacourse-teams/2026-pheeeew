# Galaxy S10 5G 실제 기기 POST 후 대기 비교

2026-10-18, USB 연결 SM-G977N / Android 12(API31), Wi-Fi, USB 충전, 배터리 100%, 측정 시작 온도 29.1°C. Debug 측정 전용 com.pheeeew.pressprobe, 실제 api-dev 서버. 기존 com.pheeeew 데이터는 건드리지 않았다.

500ms / 감정별30 / 전체100 설정을 동일하게 유지했다. before는 조회 종료 대기 보존만 적용된 코드, after는 POST 후에도 첫 입력의 남은 대기를 적용한 코드다. 최초 an/dev 무수정 버전과의 비교가 아니다. 기존 재현 앱(547f0877 기반)에 현재 #799 전송 변경을 적용했다. 최신 제품 전체 APK 설치로 해석하지 않는다. 계측 외 두 소스의 차이는 POST 후 대기 계산뿐이다. 조회 분리·합치기 실험 패치는 포함하지 않았다.

실제 PressScreen과 PressViewModel을 사용하며 ViewModel에 자동 입력했다. 물리 터치 지연·첫 화면 그리기·애니메이션 프레임을 측정한 것은 아니다. 입력 간격은 단발1회, 짧은 연타5회(100ms 간격), 같은 감정100회/교차100회(100ms 간격). 각 조건 3회. 순서 before1 → after1 → after2 → before2 → before3 → after3. 실제 전송 완료를 기다리고 별도 GET으로 서버 증가량을 검증했다. 전후 앱 설치 시 앱 데이터는 유지했다.

| 연속 입력 600회씩 | before | after |
|---|---:|---:|
| POST 시도 | 89 | 104 |
| 전체 집계 GET | 36 | 88 |
| 개인 집계 GET | 6 | 6 |
| HTTP 합계 | 131 | 198 |
| 회차별 확인 p95 범위 | 743~2157ms | 571~585ms |

POST +16.9%, 전체 측정 요청 +51.1%. 각 run_end 이전 검증용 개인 GET1/전체 GET1도 포함한 수치다. 이 고정 검증 요청 12개를 빼면 운영 요청은 119→186회다. run_start 이전 초기화 조회는 제외했다. 단일 사용자 결과이므로 다중 사용자 서버 처리량이나 최대 수용 인원으로 환산하지 않는다.

단발 p95는 before581~619 / after582~607ms, 짧은 연타 before575~578 / after578~582ms. 두 조건 모두 각각 한 POST로 처리됐다. 전체 24개 측정 조건, 입력1236회, 서버 증가1236회이며 종료 후 pending0을 확인했다. 앱 종료·장애 주입·재시작 복구를 실행한 실험은 아니다.

확인 지연은 입력 로그→Accepted 결과 처리 로그 간격이다. 수정 전 3차 같은 감정의 p95 2157ms도 제외하지 않았다. 네트워크/서버 응답을 고정하지 못한 실제 환경의 반복 결과이며 인과 효과의 정밀 추정치는 아니다. 로컬 상태 반영 시간은 별도 CSV에 있고 화면 그리기 시간과 다르다.

결론: 이번 변경만으로 요청 최소화 목표를 만족하지 못한다. POST 후 불필요한 대기는 줄지만 버퍼가 자주 비면서 전체 GET이 더 자주 발생하는 경로를 확인했다. 전체 집계 조회의 합치기·갱신 주기와 함께 다음 후보를 검증해야 한다.

원본 Logcat은 logs/*.console.txt, 파서 입력은 logs/*.log다. 원본 PID·시각은 console.txt에 그대로 있다. `python3 analyze.py`로 completion 6개와 입력·서버 증가량·잔여 큐를 검사하고 comparison.csv를 재생성한다. 실제 기기 화면은 actual-device-screen.png다. 이 이미지는 adb screencap의 원본 캡처다.
