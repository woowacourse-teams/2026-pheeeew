# 개인 프레스 실험

2026년 10월 14일 기준 코드 a8233674db8785522502ffe1a36e35ff5be2a313에서 개인 프레스 Repository의 기본 전송 설정을 가상 시간으로 측정했다. 서버와 HTTP 계층은 가짜이므로 아래 요청 수는 Sender 호출 수이며 실제 HTTP POST 수가 아니다. 실제 앱 정상 입력 9회 측정과 앱 재실행 후 서버 집계 확인도 완료했다. 아래 가상 시간 표와 실제 앱 표는 구분한다.

당시 재현 코드는 별도 원격 브랜치 [feat/644-personal-press-reproduction](https://github.com/woowacourse-teams/2026-pheeeew/tree/feat/644-personal-press-reproduction)에 보존했다. 고정된 실험 코드 커밋은 [3898c00290ef97b2b74c819695049c36b7416d91](https://github.com/woowacourse-teams/2026-pheeeew/commit/3898c00290ef97b2b74c819695049c36b7416d91)이다. 재현 브랜치는 실험 보관용이며 제품 브랜치에 병합하기 위한 변경이 아니다.

저장된 로그의 재분석은 실험 코드를 체크아웃하거나 기기를 연결하지 않아도 가능하다. 이 자료 브랜치의 AN/Pheeeew에서 실행한다. 두 스크립트는 Python 표준 라이브러리만 사용한다.

정상 분석기는 전체 로그의 시작·종료를 먼저 연결하고 모든 회차의 완료·중단 상태를 stderr로 보고한다. 기본값은 첫 회차부터 분석하며 이후 회차가 정확히 9개여야 한다. 보관 로그에는 중단된 예비 실행 1회가 있어 `--start-run 2`로 명시적으로 제외한다. 로그 앞의 시작 없는 종료 기록도 별도로 보고한다.

선택된 9회는 단일·같은 감정·교차 감정 각각 1~3회로 구성되어야 하며, 시작과 종료의 조건·회차 번호가 일치해야 한다. 선택된 회차가 중단됐거나 뒤에 추가 회차가 남으면 실패한다. 과거의 완료 회차로 빈자리를 채우지 않는다. 새 로그도 보고된 회차 목록을 확인한 뒤 예비 실행을 제외할 시작 번호를 지정한다. CSV는 stdout에만 출력하므로 회차 보고와 섞이지 않는다.

## 실험 조건과 지표 정의

기본값은 대기 500ms, 감정별 최대 30회, 전체 최대 100회, 후속 요청 최소 간격 100ms다. 최초 개인·전체 조회는 즉시 성공한 뒤 입력을 시작한다. 입력은 t=0부터 100ms 간격이며 100회 조건의 입력 창은 t=10000ms에 끝난다. 같은 시각의 예약 작업은 새 입력보다 먼저 처리한다. 입력 종료 후 최대 60000ms 관찰한다.

같은 감정 조건은 EmotionState의 첫 감정에 100회, 교차 조건은 다섯 감정에 각각 20회 입력한다. 입력 시각은 감정별 FIFO로 보관하고 각 전송 묶음에 연결한다. 성공 확인 지연은 성공 Sender가 반환하는 시각에서 입력 시각을 뺀 값이다. p50/p95는 nearest rank 방식이다. 대기 입력 수에는 진행 중인 묶음도 포함된다. 정리 시간은 마지막 입력 시각이 아니라 입력 창 종료 시각부터 계산한다.

가짜 서버는 요청 지연 후 감정별 값을 더하고 즉시 최신 개인 집계를 응답한다. 집계 GET 지연·HTTP 인증·재전송·UI 프레임 시간은 이 실험에 포함되지 않는다. 단일 입력은 한 표본이므로 p50/p95를 분포로 해석하지 않는다.

## 정상 상황 결과

시간 단위는 ms다. 모든 조건에서 입력이 전부 수용·반영되었고 대기 입력은 0으로 정리되었다. 최대 동시 전송은 1이었다.

| 입력 | 응답 지연 | Sender 호출 | 최대 대기 | 확인 p50 | 확인 p95 | 입력 창 종료 후 정리 |
|---|---:|---:|---:|---:|---:|---:|
| 단일 1회 | 100 | 1 | 1 | 600 | 600 | 500 |
| 같은 감정 100회 | 100 | 15 | 8 | 500 | 800 | 400 |
| 교차 100회 | 100 | 15 | 8 | 500 | 800 | 400 |
| 같은 감정 100회 | 1000 | 7 | 26 | 1800 | 2600 | 1100 |
| 교차 100회 | 1000 | 7 | 26 | 1800 | 2600 | 1100 |
| 같은 감정 100회 | 3000 | 5 | 62 | 4700 | 6300 | 6400 |
| 교차 100회 | 3000 | 4 | 66 | 5000 | 6500 | 4300 |

3초 응답 조건에서 같은 감정 입력은 감정별 30회 제한으로 더 많은 묶음으로 나뉘었다. 응답 지연이 커질수록 요청 수가 감소해도 입력 확인 지연과 대기는 증가하므로, 요청 수만으로 개선을 판단하지 않는다.

## 임계값과 실패 확인

새 측정 테스트는 같은 감정 29회까지 전송하지 않고 30회에서 즉시 전송하는 경우와, 감정별 상한 미만으로 전체 99회까지 전송하지 않고 100회에서 즉시 전송하는 경우를 확인한다. 두 경우 가상 시간을 진행하지 않아도 전송한다.

기존 LongQueue 테스트는 오프라인 10000회 입력 후 복구, 거절 중 새 입력 유지, 처리 불명 집계 대조·미확인 묶음 정리·후속 입력, 조회 실패, 취소, 숫자 범위 방어를 검증한다. 대부분 전송 대기 0ms·최소 간격 10ms를 사용하므로 기본 설정의 성능 결과와 합치지 않는다. 테스트용 멱등 Sender 결과도 실제 API의 멱등 보장으로 해석하지 않는다.

## 실제 앱 측정 절차

1. 개발 서버에 연결된 테스트 기기에서 앱 커밋·빌드 종류·서버 버전·기기·OS·네트워크를 기록한다.
2. 같은 개인 집계에 다른 기기가 입력하지 않도록 하고 날짜 경계를 피한다.
3. 최초 집계 조회 완료와 이전 대기 입력 정리를 확인한다. 실험 전 개인 감정별 서버 집계를 저장한다.
4. 단일 입력, 같은 감정 10회/초·10초, 다섯 감정 교차 10회/초·10초를 각각 3회 반복한다. 목표 입력과 실제 수용 입력을 구분한다.
5. 실제 POST 시도와 인증 후 재전송, GET을 구분한다. 입력별 확인 지연은 입력과 묶음 연결 관측이 준비된 경우에만 계산한다.
6. 입력 종료 후 최대 60초 관찰하고 서버 집계 증가, 최대 대기, 정리 시간, 거절·처리 불명을 기록한다. 화면 숫자는 낙관적 값이므로 서버 반영 증거로 사용하지 않는다.

실제 입력·묶음 연결 관측과 정상 조건의 기기 반복 측정은 완료했다. 앱 HTTP 경계의 오류·응답 유실, 실제 네트워크 단절·복구와 UI 첫 그리기 지연 측정도 완료했다. 패널 표시 시각과 실제 서버 자체의 장애 실험은 이 측정 범위에 포함되지 않는다. 처리 불명 묶음이 정리되어도 성공·유실로 확정하지 않는다. 429·500·응답 유실의 실제 앱 HTTP 분류와 복구 결과는 아래에 기록했다.


## 실제 앱 정상 입력 결과

2026년 10월 14일 15시 29분부터 15시 33분까지 KST에 Galaxy S10 5G SM-G977N, Android 12, Wi-Fi에서 측정했다. 앱은 a8233674 기반 브랜치의 관측 로그 추가본, debug 2.2.1+10이며 api-dev.pheeeew.com을 사용했다. 서버 배포 버전은 확인하지 않았다. 가짜 지연은 주입하지 않았다.

UiAutomation의 touchscreen DOWN/UP 이벤트를 100ms 간격으로 주입했다. 100회 입력 창은 10000~10002ms였으며 회차마다 입력 종료 후 15초를 관찰했다. 최초 두 예비 실행은 클릭 도구의 긴 터치와 입력 소스 누락으로 중단했으며 아래 결과에서 제외했다. 본 실험 시작 개인 집계는 43이었다.

총 603회가 수용되고 개인 집계는 43에서 646으로 증가했다. 감정별로 답답 363회, 나머지 네 감정 각 60회가 증가했다. 모든 프레스 POST는 200이고 재전송·거절·처리 불명은 관찰되지 않았다. 회차 종료의 대기 입력은 모두 0이었다. 앱을 종료하고 다시 실행한 새 세션의 개인 집계 GET 200 응답에서도 646과 감정별 값을 재확인했다.

입력 확인 시각은 Sender 성공 결과를 Repository가 처리하기 직전 로그이며, UI 프레임 반영 지연은 포함하지 않는다. 개인 집계 증가를 통한 성공 확인 외에 기기 테스트에서도 화면 감정별 숫자의 증가가 제시한 입력 수와 일치하는지 확인했다. 화면 값에는 낙관적 입력이 포함되므로 서버 증거는 성공 응답과 새 세션 GET으로 구분한다.

가상 100ms 응답 실험의 POST 15회와 달리 실제 앱은 20~23회였고 1개 입력 묶음도 있었다. 실제 응답 시간과 앱 실행 조건이 다르므로 같은 조건의 성능 비교로 해석하지 않는다. 작은 묶음을 만드는 추가 전송 계기의 원인은 후속 분석 대상으로 남긴다. 세 회차의 지연을 합쳐 하나의 p95로 계산하지 않는다.

## 실제 앱 재실행과 로그 분석

아래 설치·기기 테스트는 별도 보존한 재현 코드에서 실행한다.

전용 테스트 기기에서 개발 서버용 debug 앱을 설치하고 온보딩을 완료한다. 아래 테스트는 실제 서버에 603개 입력을 보내며 명시적인 옵션이 없으면 건너뛴다.

```sh
./gradlew :androidApp:installDebug
./gradlew :shared:connectedAndroidDeviceTest \
  -Pandroid.testInstrumentationRunnerArguments.class=com.pheeeew.measurement.PersonalPressDeviceProbeTest \
  -Pandroid.testInstrumentationRunnerArguments.personalPressProbe=true
adb logcat -d -v epoch -s PressMeasurement:I '*:S' > measurements/personal-press/device.log
python3 measurements/personal-press/summarize_device.py measurements/personal-press/device.log > measurements/personal-press/device.csv
```

PressMeasurement는 debug Android에서만 활성화되며 입력 감정·대기 수·묶음 sequence·감정별 횟수·개인 집계·HTTP endpoint/method/status/duration을 기록한다. 토큰·헤더·원문 응답·기기 식별자는 기록하지 않는다. 관측 콜백 예외는 전송을 중단하지 않으며 가상 실험에서 예외 콜백을 주입해 검증했다.

분석 스크립트는 마지막 9개 회차의 입력과 감정별 FIFO 묶음을 연결한다. 미완료 회차, 거절·처리 불명, 실제 수용과 요청 수의 불일치는 분석을 실패시킨다. 장애 실험을 정상 결과로 덮어쓰지 않는다. 저장된 2026-10-14-device.log와 CSV에는 본 측정과 마지막 서버 집계 재확인이 남아 있다.


## 장애 주입과 복구 결과

같은 기기와 개발 서버용 앱에서 2026년 10월 14일 16시 23분부터 16시 26분 KST에 실행했다. 본 실험 시작 집계는 653이다. 장애 제어가 적용되지 않은 예비 실행의 7개 입력은 결과에서 제외하고 시작 집계에 포함했다.

400·429·500은 dev debug 앱의 OkHttp interceptor에서 첫 프레스 POST에만 합성한 HTTP 응답이다. 이 세 조건에서는 해당 요청을 서버에 보내지 않았다. 타임아웃은 서버에 보내기 전 3초 후 SocketTimeoutException을 주입했으며, 기본 20초 요청 제한의 실제 만료 실험은 아니다. 응답 유실은 실제 서버에 POST를 보내 200을 받은 뒤 응답을 닫고 예외를 주입했다. 서버 자체를 오류 상태로 만들지는 않았다.

각 조건에서 첫 5개 입력 후 후속 2개를 추가했다. 첫 묶음의 크기 5를 로그로 확인했다. 요청 크기·전송 주기·실패 정책은 바꾸지 않았다.

| 조건 | 실제 앱이 본 HTTP 결과 | Repository 결과 | 개인 집계 증가 | 최대 대기 | 종료 시 대기 |
|---|---|---|---:|---:|---:|
| 400 | 400 → 200 | Rejected → Accepted | 2 | 5 | 0 |
| 429 | 429 → 200 | OutcomeUnknown → Accepted | 2 | 7 | 0 |
| 500 | 500 → 200 | OutcomeUnknown → Accepted | 2 | 7 | 0 |
| 타임아웃 | TIMEOUT → 200 | OutcomeUnknown → Accepted | 2 | 7 | 0 |
| 응답 유실 | TIMEOUT → 200 | OutcomeUnknown → Accepted | 7 | 5 | 0 |
| 오프라인 입력 10회 | 복구 후 200 한 번 | Accepted | 10 | 10 | 0 |

429·500·타임아웃은 개인 집계 GET 3회로 첫 5개 미확인 묶음을 정리한 뒤 후속 2개를 전송했다. 첫 묶음을 재전송하지 않았다. 실험 장치는 첫 요청을 서버에 보내지 않았다는 사실을 알지만 앱의 관측 결과는 처리 불명이다. 따라서 집계에서 확인되지 않아 정리한 입력을 확정 거절이나 유실로 분류하지 않는다.

429 응답에 Retry-After: 2를 넣었지만 현재 Sender는 429를 OutcomeUnknown으로 분류한다. 이 실험에서 관찰한 것은 집계 대조이며 Retry-After 기반 재시도가 아니다. 이 동작을 변경할지는 후속 정책 검토 대상으로 남긴다.

응답 유실은 개인 집계 GET 1회로 첫 5개 반영을 확인했고 후속 2개만 추가로 보냈다. 전체 7개가 반영되어 첫 묶음의 중복 반영은 관찰되지 않았다.

오프라인 조건은 기기의 Wi-Fi와 모바일 데이터를 실제로 끈 뒤 입력했다. 연결 복구 전에는 프레스 POST가 없고 낙관적 숫자만 10 증가했다. 원래 Wi-Fi=1·모바일 데이터=1로 복원한 명령 완료 시각부터 서버 성공까지 6831ms였다. 이 시간에는 무선 연결을 다시 얻는 시간이 포함된다. 복구 후 POST 1회로 10개가 반영됐다. 실험 종료 후 두 설정의 복원을 재확인하고 장애 제어 파일이 제거된 것을 확인했다.

정상적으로 끝난 각 장애 조건은 1회 실험이며 반복 표본의 통계로 해석하지 않는다. 장애와 UI 입력을 모두 마친 뒤 앱을 종료하고 재실행한 개인 집계 GET 200에서도 총 908, 답답 588·나머지 네 감정 각각 80을 재확인했다. 본 실험의 275개 수용 입력 중 서버 증가 255개와 미확인 정리 20개가 구분된다.

## 애니메이션과 숫자 첫 그리기 지연

화면 주사율은 약 60Hz다. 실제 Compose의 drawWithContent에서 첫 변형 버튼, 변경된 숫자, 새 반응 효과를 그린 직후 관측한다. 버튼은 앱 포인터 핸들러의 DOWN 수신부터, 숫자와 반응 효과는 Repository 입력 수용부터 시간을 잰다. 입력 주입부터 앱 핸들러에 도달하기 전 시간, RenderThread/GPU 처리와 패널 표시 지연은 포함하지 않는다. 디버그 로그·추가 그리기 관측의 오버헤드도 포함하므로 release 사용자 체감 지연으로 일반화하지 않는다.

900ms 간격 단일 감정 30회, 같은 감정 10회/초 100회, 다섯 감정 교차 10회/초 100회를 실행했다. 각 지표는 조건별 30·100·100개의 관측이 남아 입력과 표본 수가 일치했다.

| 조건 | 버튼 변형 p50 / p95 ms | 숫자 반영 p50 / p95 ms | 반응 효과 p50 / p95 ms |
|---|---|---|---|
| 900ms 간격 30회 | 20.49 / 23.70 | 36 / 42 | 38 / 44 |
| 같은 감정 100회 | 16.00 / 24.89 | 27 / 32 | 28 / 34 |
| 교차 감정 100회 | 17.76 / 23.97 | 27 / 32 | 28 / 33 |

같은 감정 연타 중 버튼의 최대 첫 그리기 지연은 60.05ms였다. p95가 약 25ms라는 이유로 모든 입력이 그 안에 반응했다고 해석하지 않는다. UI는 서버 성공을 기다리지 않고 반응하며, 오프라인 및 처리 불명 중에도 첫 그리기 이벤트가 관찰됐다. 관측한 범위는 애니메이션 시작 지연이고 전체 애니메이션의 프레임 누락률은 아니다.

## 장애와 UI 실험 재실행

아래 설치·기기 테스트는 별도 보존한 재현 코드에서 실행한다.

개발 서버용 debug 앱을 설치하고 온보딩을 완료한 전용 기기에서 실행한다. 테스트는 첫 실패 묶음·후속 입력·네트워크 복구·UI 입력을 포함해 총 275개를 수용하도록 한다. 네트워크 설정은 finally에서 복원하며 사용자 조작 없이 실행한다.

```sh
./gradlew :androidApp:installDebug
./gradlew :shared:connectedAndroidDeviceTest \
  -Pandroid.testInstrumentationRunnerArguments.class=com.pheeeew.measurement.PersonalPressFailureAndUiProbeTest \
  -Pandroid.testInstrumentationRunnerArguments.personalPressFailureProbe=true
adb logcat -d -v epoch -s PressMeasurement:I '*:S' > measurements/personal-press/failure-ui.log
python3 measurements/personal-press/summarize_failure_ui.py measurements/personal-press/failure-ui.log
```

DebugPressFaultInjection은 dev debug에서만 엔진에 설치되며 api-dev의 정확한 개인 프레스 POST 경로에만 적용된다. 테스트가 run-as로 files/press-probe-fault-MODE 파일을 만들면 첫 해당 POST가 파일을 소비한다. 테스트 finally에서도 파일을 제거한다. UI 그리기 훅은 관측 콜백이 없는 앱에서 추가 draw 의존성을 만들지 않는다.

저장 결과는 2026-10-14-failure.csv, 2026-10-14-ui.csv와 2026-10-14-failure-ui.log다. 실험 코드 커밋에서 프레스·Tap 회귀 테스트 51개와 기기 측정 테스트 1개가 통과했고 관련 Kotlin 형식 검사도 통과했다. 이 자료 전용 변경에서는 저장된 로그를 재분석해 CSV와 일치하는지 확인한다.
