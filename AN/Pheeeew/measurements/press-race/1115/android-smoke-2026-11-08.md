# #1115 Android 실기기 확인 — 2026-11-08

**상태: 미완료.** 기본 폴링과 캐시 폴링은 응답과 단일 입력 반영을 확인했습니다. SSE는 화면을 나갔다 돌아온 뒤 `429`가 반복됐고, 앱을 완전히 재시작한 뒤에도 첫 응답이 오지 않았습니다. 세 방식의 성능 비교나 이슈 완료 판정은 할 수 없습니다.

| 확인 항목 | 기본 폴링 | 캐시 폴링 | SSE |
|---|---|---|---|
| 첫 상태 응답 | 63~84ms (2회) | 76~143ms (2회) | PRESS 93초, ALL 86초 동안 HTTP 응답·첫 상태 없음. 재시작 후 69초에도 없음 |
| 반복 조회 | 1.043~1.473초 (157간격) | 1.049~1.207초 (268간격) | 해당 없음 |
| 단일 입력 후 내 점수 | 1회 입력 후 79→80, 화면 감정 횟수 +1 | 2회 입력에서 80→81, 81→82. 화면 감정 횟수 각 +1 | 미실행. 첫 상태 미수신 |
| 활동 인원 | 입력 전 0명, 입력 후 1명 관측 | 입력 직후 표본 1명, 약 6초 뒤 0명 | 미측정 |
| 화면 전환·복귀 | PRESS↔ALL, 지도 이탈 후 PRESS 재진입 응답 확인 | PRESS→ALL 응답 확인 | 재진입 요청은 시작됐으나 429 또는 무응답 |
| 판정 | API·화면 기본 동작 확인 | API·입력 반영 확인 | 정상 동작 미확인 |

첫 응답 시간은 수신기 시작부터 서버 응답을 받은 시점까지입니다. 화면 픽셀 표시 완료나 입력→랭킹 반영 지연을 뜻하지 않습니다. 실행 시점과 세션이 달라 폴링 수치 간 우열도 판단하지 않습니다.

## 실행 조건

- 기기: Android 실기기 `SM-G977N`, Android 12 (SDK 31), USB ADB 연결 1대
- 앱: Debug/dev, `com.pheeeew.updatetest`, 2.5.0 (103201)
- API 환경: `https://api-dev.pheeeew.com`; 서버 배포 커밋과 운영 설정은 확인하지 못함
- 입력: 세션별로 같은 감정 `답답` 버튼을 한 번씩 눌렀습니다. 입력 API는 `POST /api/v2/emotions/presses`입니다.
- 수신 API: 캐시 폴링 `GET /api/v2/press-race/snapshot`, 기본 폴링 `GET /api/v1/press-race/snapshot`, SSE `GET /api/v1/press-race/stream`
- 입력 횟수가 바뀐 구간 중 일부는 출처를 기록하지 못했습니다. 통제한 단일 입력만 입력 결과로 계산했습니다.

## SSE 재접속 결과

- 17:55:15 PRESS 요청: 토큰 확인 성공, 전송 시작. 93초 동안 HTTP 응답 상태와 첫 상태가 기록되지 않았고 화면은 순위 로딩 중이었습니다.
- 17:56:48 ALL로 전환: 새 요청은 시작됐지만 86초 동안 HTTP 응답 상태와 첫 상태가 없었습니다.
- PRESS 재진입: HTTP `429` 7회 관측. 각 응답은 51~218ms에 도착했고, 재시도 대기는 0.775~4.981초였습니다.
- 앱 강제 종료 후 재실행: 토큰 확인과 전송 시작은 성공했지만 69초 동안 HTTP 응답과 첫 상태가 없었고 화면은 로딩 중이었습니다.
- BE 계약은 같은 기기의 동시 구독 수가 2개를 넘으면 `429`를 반환하며, 서버가 닫힌 연결을 알아차리기 전까지 이전 연결이 제한 수에 남을 수 있다고 설명합니다([PR #1106](https://github.com/woowacourse-teams/2026-pheeeew/pull/1106)). 관측한 `429`가 어떤 연결 때문에 발생했는지는 서버 로그가 없어 확인하지 못했습니다.
- 클라이언트 측 원인 후보(미확정): Android는 Ktor 3.5.2의 OkHttp 엔진을 사용하고, 화면 전환 시 `collectLatest`가 이전 요청을 취소합니다. Ktor의 [PR #5981](https://github.com/ktorio/ktor/pull/5981)은 응답을 받기 전에 취소된 OkHttp 요청의 응답을 닫지 않는 문제를 수정합니다. 화면 전환 뒤 이전 SSE 연결이 남아 `429`가 난 현상과 맞지만, 이 실험에서 원인을 확정하거나 수정 후 재현 검증하지는 않았습니다. 첫 요청에서 응답 헤더를 받지 못한 이유도 별도로 미확인입니다.

## 확인 범위와 남은 항목

- 한 대만 연결되어 다른 기기의 입력, 주변 순위 변화, 동점, 미참여 사용자, 빈 순위 목록은 확인하지 못했습니다.
- 입력 배치·재시도 부하, 인증 만료, 실제 네트워크 단절·복구, 날짜 변경은 확인하지 못했습니다.
- 캐시 TTL, SSE 서버 발행 주기, 서버 배포 버전·설정은 확인하지 못했습니다.
- 서버 계약상 `activeCount`는 최근 5초 안에 입력한 서로 다른 기기 수입니다([PR #1099](https://github.com/woowacourse-teams/2026-pheeeew/pull/1099)). 이번 캐시 폴링 입력에서 1명 후 약 6초 표본에 0명이 보여 계약의 시간 창과 일치했습니다. 샘플 간격 때문에 정확한 만료 시각은 측정하지 않았습니다.
- 기기 간 종단 지연과 실제 패널 표시 완료 시각은 측정하지 않았습니다.
