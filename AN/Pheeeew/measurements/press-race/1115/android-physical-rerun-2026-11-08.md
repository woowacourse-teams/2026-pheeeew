# #1115 Android 실기기 검증 — 2026-11-08

**결과: 부분 확인.** Car 에뮬레이터 앱은 삭제했다. 이후 확인은 연결된 Android 실기기에서 캐시 폴링 → SSE → 기본 폴링 순서로 진행했다. 세 방식 모두 같은 HTTP 입력 1회가 `Applied` 응답을 받았다. 점수·감정 횟수·활동 인원의 화면 변화는 성능 측정과 분리한 재확인에서 확인했다. 기능 연결은 확인했지만 방식별 성능 우열은 판단하지 않았다.

## 실기기 결과

| 측정 항목 | 캐시 폴링 | SSE | 기본 폴링 |
|---|---:|---:|---:|
| PRESS 첫 상태 응답 | 80ms (1회) | 81ms (1회) | 108ms (1회) |
| 입력 → HTTP 전송 / POST 응답 | 505ms / 77ms (1회) | 509ms / 80ms (1회) | 514ms / 65ms (1회) |
| POST 결과 | `Applied` (1회) | `Applied` (1회) | `Applied` (1회) |
| PRESS→ALL→PRESS 첫 상태 응답 | ALL 62ms, PRESS 52ms | ALL 106ms, PRESS 87ms | ALL 164ms, PRESS 56ms |
| 안정 연결 중 수신 간격 | 90개 구간, 1.064~1.243초 | 변경 이벤트만 수신; 입력 후 이벤트 2건 | 133개 구간, 1.059~1.219초 |

- 세 입력 모두 HTTP 전송 시도 1회가 `Applied`로 끝났다. 재시도나 중복 입력은 관측되지 않았다.
- 각 방식은 같은 감정 버튼을 한 번씩 사용했다. 앱을 바꿔 설치할 때 `adb install -r`를 사용해 앱 데이터와 로그인 상태를 보존했다.
- 폴링 간격은 이전 응답 완료부터 다음 응답 완료까지 앱 로그로 계산했다. 이는 실제 사용자에게 보이는 랭킹 반영 시간과 다르다.
- 화면 수치는 ADB가 읽은 접근성 텍스트에서 확인했다. 실제 패널에 그려진 완료 시각은 측정하지 않았다. 별도 화면 재확인 값과 시각은 [화면 관찰 로그](android-physical-ui-repeat-2026-11-08.log)에 보존했다.

## 화면 관찰 재확인 — 성능 측정과 별도 실행

성능 표본과 분리해 각 모드에서 같은 감정 버튼을 1회 더 눌렀다. 접근성 화면에서 점수·감정 횟수·활동 인원 변화가 보이는지 확인했다.

| 방식 | 입력 전 | 입력 후 약 2초 | 후속 화면 표본 |
|---|---|---|---|
| 캐시 폴링 | 87회, `답답` 25번, 활동 0명 | 88회, `답답` 26번, 활동 1명 | 입력 후 9.760초에 캡처 완료: 88회, 26번, 0명 |
| SSE | 88회, `답답` 26번, 활동 0명 | 89회, `답답` 27번, 활동 1명 | 입력 후 9.685초에 캡처 완료: 89회, 27번, 0명 |
| 기본 폴링 | 89회, `답답` 27번, 활동 0명 | 90회, `답답` 28번, 활동 1명 | 입력 후 9.744초에 캡처 완료: 90회, 28번, 0명 |

- 후속 표본은 7초 대기 후 접근성 화면을 읽었고, 화면 덤프가 끝난 시각은 입력 후 약 9.7초였다. 따라서 이를 활동 인원이 7초에 감소했다고 해석하지 않는다.
- 로그에는 다른 참여자의 이름이 포함될 수 있는 전체 화면 덤프를 저장하지 않고, 내 순위·감정 횟수·활동 인원만 남겼다.

## 입력 후 상태 변화

- 별도 화면 재확인에서는 세 방식 모두 점수와 `답답` 횟수가 입력 한 번만큼 증가했고, 활동 인원이 0명→1명→0명으로 표시됐다. 마지막 화면 표본은 입력 후 약 9.7초에 캡처됐다.
- SSE에서 입력 뒤 상태 이벤트가 두 번 왔다. 두 번째 이벤트는 새 입력으로 세지 않았다. 화면의 활동 인원은 최근 입력 시각에 따라 바뀔 수 있으므로 이벤트 개수와 입력 횟수를 동일하게 취급하지 않는다.
- SSE 네트워크 복구 뒤 추가한 입력 1회도 `Applied`였다. POST 응답 로그 뒤 756ms에 SSE 상태 변경 로그가 찍혔다. 이 값은 같은 기기 로그 시각의 POST 응답→수신 이벤트 구간이며, 서버 저장 시각이나 다른 기기까지의 지연은 포함하지 않는다.

## 네트워크 복구

각 모드에서 Wi‑Fi와 모바일 데이터를 약 8초 끄고 다시 켰다. 아래 첫 값은 Android가 연결 불가를 알린 때부터 다시 사용 가능하다고 알릴 때까지다. 두 번째 값은 복구 알림 이후 앱이 정상 응답을 받은 시점까지다.

| 방식 | 단말 네트워크 불가→복구 | 복구 알림→정상 응답 |
|---|---:|---:|
| 캐시 폴링 | 12.946초 | 0.903초 뒤 정상 snapshot 응답 |
| SSE | 13.112초 | 0.631초 뒤 HTTP 200 스트림 연결; 이후 입력 변경 이벤트 수신 확인 |
| 기본 폴링 | 31.748초 | 1.670초 뒤 정상 snapshot 응답 |

- 기본 폴링의 첫 단절 확인 명령은 오프라인 상태 조회 결과가 없을 때 복구 명령까지 진행하지 못했다. 이를 발견한 즉시 Wi‑Fi와 모바일 데이터를 다시 켰고, 연결 복구를 확인했다. 따라서 기본 폴링의 31.748초에는 그 실행에서 복구 명령을 다시 호출하기까지의 시간이 포함되어 다른 두 회차와 직접 비교할 수 없다. 캐시 폴링과 SSE 회차에서는 복구 명령이 항상 실행되도록 절차를 바꿨다.
- 세 회차 모두 앱은 다시 정상 응답을 받았다. 기기에서 실제 단절과 재연결을 관측했다.

## 이탈·재진입과 연결 수명

- 세 방식 모두 PRESS에서 ALL로 이동했고 돌아온 화면에서 다시 상태 응답을 받았다.
- 폴링 로그는 화면 이탈 후 `view=NONE`으로 바뀐 것을 기록했다. 앱 코드에서는 화면 교체 시 `collectLatest`가 이전 요청을 취소하고, 화면 종료 시 receiver 작업을 취소한다. SSE 로그에는 취소 완료나 서버 쪽 스트림 종료 기록이 없으므로 실제 소켓 종료까지는 확인하지 않았다.
- 이번 SSE의 5초 대기 후 재진입은 HTTP 200, 첫 상태 108ms였다. 앞서 기록한 빠른 재진입 실험에서는 `429`가 반복된 회차가 있어 SSE 재접속 문제가 모두 해결됐다고 판정하지 않는다. 원인은 서버 구독 로그가 없어 미확인이다. [이전 SSE 재접속 기록](android-sse-stream-fix-2026-11-08.md)

## 서버 계약과 검증 범위

- 앱 빌드는 `https://api-dev.pheeeew.com`, HTTP 입력으로 확인했다. 실제 개발 서버 배포 커밋과 런타임 설정은 확인하지 못했다.
- 서버 PR 문서에는 기본 snapshot의 `activeCount`가 최근 5초 입력 기기 수로 설명되어 있고([PR #1099](https://github.com/woowacourse-teams/2026-pheeeew/pull/1099)), 캐시 TTL 기본값 1초([PR #1101](https://github.com/woowacourse-teams/2026-pheeeew/pull/1101)), SSE의 변경 이벤트 발행 기본 간격 1초와 heartbeat 15초([PR #1106](https://github.com/woowacourse-teams/2026-pheeeew/pull/1106))가 기술되어 있다. 이 값은 문서의 기본값이며 현재 개발 서버에서 실제 적용된 값은 미확인이다.
- 이번 기기 확인은 실제 사용자 한 명만 참여했다. 다른 기기 입력에 따른 순위 반영, 동점 순위, 미참여 사용자, 서버의 빈 순위 응답은 실제 서버에서 확인하지 못했다.
- 인증 만료, 날짜 경계, 서버 CPU·DB 부하, 요청·응답 바이트, 실제 패널 표시 완료 시각은 미측정이다.
- 기존 자동 테스트는 동점·빈 목록·미참여 사용자 매핑, 오래된 응답 폐기, 화면 교체 시 이전 요청 취소를 다룬다. 이번 실행에서 Android host 테스트 30개가 통과했다. [테스트 결과와 XML 경로](android-host-test-2026-11-08.log)
- 첫 응답은 각 방식 1회뿐이다. 첫 응답 시간만으로 성능 우열을 판단하지 않는다.

## 실행 환경과 근거

- 기기: `SM-G977N`, Android 12, USB 연결 1대. Car 에뮬레이터는 실험에 사용하지 않았다.
- 앱: Debug/dev `com.pheeeew.updatetest`, 2.5.0 (103201). 앱 코드 커밋 `ec0b2a18d` 위에서 빌드했다.
- 입력: `POST /api/v2/emotions/presses`; 같은 `답답` 버튼, 방식별 통제 입력 1회.
- 수신 API: 캐시 폴링 `/api/v2/press-race/snapshot`, SSE `/api/v1/press-race/stream`, 기본 폴링 `/api/v1/press-race/snapshot`.
- 원본 계측: [android-physical-rerun-2026-11-08.log](android-physical-rerun-2026-11-08.log)
- 화면 관찰 근거: [android-physical-ui-repeat-2026-11-08.log](android-physical-ui-repeat-2026-11-08.log)
- 자동 테스트 근거: [실행 요약](android-host-test-2026-11-08.log), 원본 결과 [ApiRequestExecutorTest](android-host-test-api-request-executor.xml) · [PressRaceComparisonReceiverTest](android-host-test-press-race-comparison-receiver.xml)

## 판정
