## 요청은 도달했지만 연속 입력 결과가 다른 이유

기존 구현은 시스템 `CONFIRM` 효과를 요청하고, 이 기기는 삼성의 `SemHaptic` 효과로 처리했다. Jindong은 강도 0.6의 20ms 주 진동 뒤에 라이브러리의 보조 구간을 붙인 파형을 요청했다. 따라서 두 구현은 **서로 다른 패턴**을 비교한 것이다. 실제 강도나 촉감이 같다는 전제는 두지 않았다. 파형은 [OS 원본 기록](device/device-03/matched-service-records.json)에서 확인할 수 있다.

빠른 입력의 앱 콜백 간격 중앙값은 기존 구현 **68.28ms**, Jindong **69.93ms**였다. 실제 감정 패드의 빠른 입력에서는 각각 **75.72ms**, **81.72ms**였다. 이는 앱에서 수신한 콜백 간격이며 물리적 터치 간격이 아니다. 드라이버의 DOWN/UP 간 16ms와 입력 후 25ms 대기 설정을 실제 입력 주기로 해석하지 않았다. 일반 입력 콜백 간격은 각각 **268.02ms**, **267.93ms**였다. [간격 원본과 집계](device/device-03/summary.json).

기존 구현에서 취소된 연속 입력 기록 76건은 모두 다음 요청 시작 시각과 이전 요청 종료 시각이 **0~2ms 이내로 겹쳤다**. 다음 입력이 진행 중인 효과를 교체한 것으로 해석한다. Jindong의 짧은 파형은 해당 빠른 입력 80회에서 모두 OS상 완료됐다. 모든 요청이 기록에 남았다는 사실과, 모터가 실제로 어떻게 느껴졌는지는 구분해야 한다. 근거: [취소 시각 대조](device/device-03/cancellation-audit.json), [서비스 기록](device/device-03/matched-service-records.json).

일반 입력에서 OS가 기록한 요청 수명의 중앙값은 기존 **112ms**, Jindong **36ms**였다. 이것은 OS의 시작·종료 기록 차이이며 실제 모터 지속 시간을 측정한 값이 아니다. 패턴 길이가 다른 만큼, 취소 건수가 적다는 사실을 라이브러리 자체의 품질 우위로 일반화하지 않는다.

## 복귀·차단·기존 앱 격리

- 화면 복귀와 앱 복귀는 각 구현에서 각각 10회 모두 OS 요청이 기록됐다. 이탈·백그라운드 상태의 20개 스냅샷에서는 현재 요청과 대기 요청이 모두 비어 있었다. 이는 해당 시점의 관찰이며 전체 백그라운드 시간의 연속 계측은 아니다. [스냅샷 판정](device/device-03/summary.json), [기존 구현 입력 원본](device/device-03/native-core-01/result.json), [Jindong 입력 원본](device/device-03/jindong-core-01/result.json).
- **입력 거절, 시각 효과 전용, View 햅틱 OFF, 시스템 햅틱 OFF**를 각 10회씩 확인했다. 두 구현 모두 해당 구간의 OS 진동 요청은 0건이었다. 거절·시각 전용은 햅틱 콜백 자체가 호출되지 않았고, View·시스템 OFF는 호출이 들어와도 OS 요청으로 이어지지 않았다. 시스템 OFF 원본: [기존](device/device-03/native-settings-off-01/result.json), [Jindong](device/device-03/jindong-settings-off-01/result.json).
- 최종 실행 전후 기존 `com.pheeeew` 및 기존 테스트 앱들의 UID·설치 경로·버전·설치/업데이트 시각이 같았다. 두 비교 패키지만 설치·업데이트했다. 시스템 햅틱 설정은 원래 값 **1 → 1**로 복원했다. 이 검증은 설치 정보에 관한 것이며 기존 앱의 모든 내부 데이터를 대조한 것은 아니다. [전후 설치 정보·설정](device/device-03/metadata.json).
- 비교 화면과 계측 코드는 일반 제품 컴파일에서 제외되는 것을 확인했다. 기존·신규 햅틱 단위 테스트 14개도 통과했다. [제품 소스 격리 확인](product-isolation.json), [검증 로그](logs/27-product-source-isolation.log).

## 도입 판단과 남은 확인

**공통 Kotlin 패턴을 실제 Android 감정 패드에 연결하고, 이번 복귀·차단 시나리오가 동작하는 것을 확인했다.** 반면 동기 호출 처리 시간은 기존 구현보다 길게 측정돼 성능 개선을 확인한 결과는 아니다. 한 기기의 Debug 빌드와 한 번의 본 시나리오 비교이므로 다른 기기·Release 빌드의 대표 성능으로 볼 수 없다. 본 시나리오의 실행 순서도 고정되어 있었다.

정식 도입 판단에는 사용자가 두 앱의 실제 감정 패드를 눌러 **길이·강도·연속 입력 촉감이 적절한지** 확인하는 단계가 남는다. 현재 두 비교 앱은 기기에 설치되어 있고, 런처에서 직접 열어 같은 감정 버튼을 비교할 수 있다. 실제 모터 시작 지연과 사용자 선호는 계속 미측정이며, iOS 엔진 복구·촉감 동등성도 이번 결과로 판정하지 않는다.

## 제외한 예비 실행과 원본 보존

최종 표는 **`device-03`만** 사용한다. [예비 실행 1](device/device-01/metadata.json)은 입력 미수신 회차가 있어 중단했고 원인은 미확인이다. [예비 실행 2](device/device-02/metadata.json)는 다른 자동 테스트가 앱을 실행한 시각과 입력 중단이 겹쳤다. [포커스 충돌 근거](device/device-02/focus-interference.txt)를 보존했으며 두 예비 실행은 최종 실패율·처리 시간에 합치지 않았다.

다른 테스트가 실기기 24회 수집을 마치고 집계 검토 단계에 들어갔으며 잔류 주입기가 없는 것을 확인한 뒤 최종 실행을 시작했다. 창 포커스를 잃으면 입력 전에 중단하는 보호 장치를 사용했다. 최종 26회 실행에는 입력 수 부족이나 포커스 중단이 없었다.

각 실행 폴더에는 입력 JSON, OS 진동 서비스 스냅샷과 화면 캡처를 두었고, JUnit 계측 출력도 보존했다. 같은 내용을 묶은 중복 tar 원본은 로컬에 보존하며 커밋 대상에서 제외한다. 재집계 코드는 [집계 스크립트](../../../hapticComparison/scripts/aggregate-device-comparison.py), 재실행 코드는 [실행 스크립트](../../../hapticComparison/scripts/run-device-comparison.py)에 있다.

[최종 데이터 검증 결과](device/device-03/verification.json): 실행 수·입력 수·OS 기록 수·차단 조건·대기 상태·설치 정보·설정 복원·소스 해시·문서 링크 확인을 통과했다.
