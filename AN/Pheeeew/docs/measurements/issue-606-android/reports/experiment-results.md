# #606 Android 핀 이미지 경로 비교 결과

측정일: 2026-10-03 (KST)

## 실험 조건

- 기기: Galaxy S23 FE (SM-S711N), Android 15, USB 연결
- 빌드: 동일한 R8 최적화 benchmark 빌드, 앱 프로세스를 매 실행 새로 시작
- 비교: A 현재 Compose 래스터화, B 같은 래스터화를 Dispatchers.Default로 이동, C A가 만든 PNG fixture를 로컬에서 디코드
- 표본: 완료된 측정 각 20회, 회당 139–140개 핀과 고유 이미지 14개. 이미지 크기 113×113px. PNG fixture 14개 합계는 93,757 bytes.
- 순서: A/B/C 순서를 회차마다 섞었다. 모드 사이 앱 프로세스는 다시 시작했으나 MapLibre 타일 캐시는 비우지 않았다.

## 시계와 결과

A와 B의 T0는 핀 데이터가 메모리에 준비된 page-result 시각이다. C의 T0는 로컬 PNG 14개를 읽어 바이트가 모두 준비된 마지막 server-image-input-ready 시각이다. 따라서 이 수치에는 API 요청과 C의 이미지 다운로드가 들어가지 않는다. C는 서버에서 바이트를 내려받는 실제 통신 실험이 아니라, 서버 이미지 입력을 로컬 fixture로 재현한 클라이언트 처리 실험이다.

첫 핀은 현재 load ID에 속하는 첫 비-snapshot first-pin-frame, 전체 핀은 같은 load ID의 fully=true all-pages-frame 콜백으로 측정했다. 이 콜백은 광학 센서로 화면 픽셀을 확인한 값은 아니다.

| 경로 | 표본 | 첫 핀 중앙값 / P90 (범위) | 전체 핀 중앙값 / P90 (범위) | 이미지 처리 합계 중앙값 / P90 | 실행 스레드 |
| --- | ---: | ---: | ---: | ---: | --- |
| A: 현재 방식 | 20 | 119 / 127 ms (96–400) | 412 / 434 ms (118–436) | 래스터 38 / 45 ms | 14개 래스터 모두 main |
| B: 백그라운드 래스터 | 20 | 72 / 95 ms (61–113) | 448 / 464 ms (132–473) | 래스터 93 / 111 ms | 14개 래스터 모두 DefaultDispatcher |
| C: PNG fixture | 20 | 38 / 55 ms (21–341) | 333 / 346 ms (35–364) | 디코드 30 / 54 ms | 14개 디코드 모두 DefaultDispatcher |

P90은 표본 20개의 최근접 순위(18번째 값)다. 각 표본의 프레임 시간·핀 수·스레드별 작업 수는 [trial-results.csv](../raw-measurements/trial-results.csv)에 있다.

### A를 기준으로 본 변화

| 비교 | 첫 핀 중앙값 | 전체 핀 중앙값 | 해석 |
| --- | ---: | ---: | --- |
| B 대 A | 39.5% 단축 | 8.7% 증가 | 첫 핀 표시는 빨라졌다. 전체 핀 완료 시간은 개선되지 않았다. |
| C 대 A | 68.1% 단축 | 19.2% 단축 | 로컬 압축 이미지 입력에서는 두 프레임 지표가 모두 단축됐다. |

B는 메인 스레드 래스터 작업을 없앴지만 작업 스레드의 14개 래스터 시간 합은 A보다 길었다. 따라서 이번 결과는 첫 핀 반응성 개선을 보여 주지만 전체 지연 개선을 입증하지 않는다. C는 중간 RGBA ByteArray → IntArray → Bitmap 생성 경로를 건너뛰며 두 지표가 개선됐지만, 실제 전송 시간·서버 이미지 캐시·응답 크기 계약은 측정하지 않았다.

## 시각·스레드 확인

A/B/C 화면 캡처에서 핀 그림과 형태에 눈에 띄는 차이는 없었다. 지도 타일과 API 핀 데이터가 실행마다 바뀌므로 픽셀 단위 이미지 diff는 하지 않았다.

Perfetto 10초 trace를 A와 B에서 각각 캡처했다. 파일은 [A trace](/private/tmp/issue606-current.trace), [B trace](/private/tmp/issue606-background.trace)이다. 현재 실행 환경에 trace processor가 없어 trace 기반 긴 프레임/deadline 통계를 산출하지 못했다. 대신 계측 로그에서 A의 raster-image 14개는 main, B의 14개는 DefaultDispatcher 작업 스레드에서 실행된 것을 확인했다. C의 server-image-decode 14개도 DefaultDispatcher에서 실행됐다.

## 한계와 다음 검증

- 매 회 API가 반환한 핀 수가 139 또는 140으로 바뀌어, 완전히 고정된 응답 fixture 비교는 아니다.
- 타일 캐시는 유지된 채 측정됐다. 전체 프레임 시간에는 타일 준비 상태가 섞여 있고, 실제 지도 프레임 콜백도 광학 표시 시각과 같지 않다.
- 이번 입력에는 고유 이미지 14개만 있었고 동적 문구 스탬프가 많은 고부하 시나리오는 실행하지 않았다.
- C는 앱 캐시에 둔 PNG를 사용했다. 서버 이미지의 다운로드, 압축 포맷, HTTP 요청 수, 디스크/메모리 캐시 적중률은 별도 측정이 필요하다.
- 기기 온도와 프레임 deadline 지표를 모든 회차에서 수집하지 못했다.

다음 실험은 고정된 API 응답 fixture와 고유 문구 스탬프가 많은 화면을 추가하고, 타일 준비를 통제한 뒤 A/B와 A/C를 각각 다시 비교해야 한다. 서버 이미지 방식은 실제 응답 바이트가 준비된 시각을 따로 계측해 다운로드 제외 지표와 사용자 체감 전체 시간을 함께 제시한다.
