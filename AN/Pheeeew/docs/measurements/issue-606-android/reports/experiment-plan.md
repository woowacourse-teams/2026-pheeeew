# #606 Android 핀 이미지 경로 비교 실험 계획

## 목적과 비교 대상

API 호출·서버 처리·이미지 다운로드 시간을 제외하고, **필요한 입력이 메모리에 준비된 시점부터 실제 핀이 그려진 지도 프레임까지** 비교한다. 같은 Android 기기, 핀 데이터, 이미지 모양과 빌드를 사용한다.

## 실행 상태

2026-10-03 실기기에서 일반 핀 시나리오의 A/B/C를 각각 20회 완료했다. 요약과 표본별 로그는 [실험 결과](experiment-results.md)와 [원시 측정값](../raw-measurements/trial-results.csv)에 기록했다. 동적 문구 스탬프가 많은 시나리오와 고정 API fixture, 실제 서버 이미지 응답을 사용한 검증은 아직 남아 있다.

| 변형 | 입력 | 클라이언트 작업 |
| --- | --- | --- |
| A: 현재 방식 | 핀 메타데이터 | Compose에서 이미지 생성·RGBA 추출 → Android Bitmap 변환 → MapLibre 등록 |
| B: 생성 작업 분리 | A와 동일 | UI 리소스·렌더 입력 준비 → 안전한 CPU 생성·픽셀 변환을 `Dispatchers.Default`에서 실행 → Bitmap·MapLibre 등록 |
| C: 서버 이미지 | 핀 메타데이터와 완성된 압축 이미지 바이트 | 이미지 디코드 → Android Bitmap → MapLibre 등록 |

두 실험을 독립적으로 진행한다. **실험 1은 A↔B**로 이미지 생성의 스레드 이동 효과를 확인한다. **실험 2는 A↔C**로 현재 구현을 서버 이미지 방식으로 바꿨을 때의 차이를 확인한다. 실험 2의 A에는 실험 1의 개선을 적용하지 않는다. B↔C 비교는 이번 실험의 판정 대상이 아니다.

## 입력 준비와 공정성

1. 동일한 bbox의 응답을 고정 fixture로 저장한다. 핀 ID·좌표·회전·순서·이미지 키·모양·크기(40dp에 해당하는 실제 픽셀)를 세 변형에서 일치시킨다. 정적 감정 핀과 동적 문구·색상 스탬프를 모두 포함한다. 샘플별 핀 수와 **고유 이미지 키 수**를 기록한다.
2. C의 이미지 파일은 A가 실제로 그린 결과와 시각적으로 같은 PNG 또는 WebP 무손실 파일로 준비한다. 이는 **서버 방식의 클라이언트 처리 모의 실험**이다. 실제 서버 제공 이미지의 인코딩·크기·캐시 계약이 정해지면 그 바이트로 재검증한다. 압축 파일과 A/B 입력을 모두 메모리에 미리 올린다. C가 별도 URL을 사용하더라도 다운로드 대기는 이번 구간에 넣지 않는다.
3. 세 변형 모두 첫 화면에서 이미지 캐시와 MapLibre style 이미지가 없는 상태로 시작한다. 별도 실험으로 동일 화면 재방문 시 캐시 적중을 측정한다. 타일 캐시는 각 변형에서 같은 웜 상태로 맞춘다. 이전 핀이 남아 첫 프레임으로 오인되지 않도록 시작 전 source를 비우고 새 load ID를 부여한다.
4. 주 실험은 동일 R8 최적화 빌드(`debuggable=false`)의 런타임 변형 선택기로 수행한다. 같은 기기·지도 스타일·카메라·줌·화면 크기·전원 상태에서 변형 순서를 섞는다. 계측용 debug 빌드 수치와 섞지 않는다.

## 실험 1: 메인 스레드 밖으로 이미지 생성 옮기기

현재 `EmotionPinSymbolImage.kt`의 `LaunchedEffect`에서 `ImageBitmap` 생성, Compose `CanvasDrawScope` 그리기, `toPixelMap()`과 RGBA 복사를 실행한다. 기존 trace에서는 이 `raster-image`가 메인 스레드에 있었고, 첫 진입 17개 이미지에 누적 153ms가 들었다. 최적화 빌드의 다른 첫 진입은 14개 이미지에 39ms였다. 두 수치는 조건이 달라 직접 비교하지 않는다.

1. 먼저 현재 단계별 시간을 `리소스·텍스트 준비`, `그리기`, `픽셀 읽기·RGBA`, `RGBA→Bitmap`, `style.addImage`로 나눈다. 각 구간의 실행 스레드와 고유 이미지 키를 기록한다.
2. B에서는 UI/Compose 값과 리소스를 먼저 준비하고, 변경되지 않는 렌더 입력만 백그라운드 작업에 전달한다. `painterResource`, `TextMeasurer`, `DrawScope` 객체를 스레드 안전성 검증 없이 그대로 `withContext(Default)`로 감싸지 않는다. 우선 독립적인 픽셀 복사·Bitmap 변환을 분리하고, 큰 구간인 그리기는 Android 전용 스레드 안전 렌더러로 옮겨 검증한다. 완료 결과만 UI 상태에 게시한다.
3. 이미지 키별 작업은 한 번만 실행하고 병렬 수를 제한한다. viewport가 바뀌면 오래된 load의 결과를 지도에 게시하지 않는다. 이미지 등록과 source 갱신의 순서는 유지한다. 스레드 이동 후 비어 있는 이미지·투명도·문구·색·회전·선택 동작을 확인한다.
4. Perfetto에서 B의 래스터화가 메인 스레드 밖에서 실행됐는지, 메인 스레드가 결과를 기다리며 막히지 않는지 확인한다. 작업 전환·동시 CPU 사용 때문에 경과 시간이 늘어나는지도 본다.

## 실험 2: 서버 이미지 디코드와 현재 생성 경로 비교

1. C는 압축 이미지 바이트를 디코드해 MapLibre가 받을 Android `Bitmap`을 만든다. 디코드는 백그라운드에서 수행하고, 중간 `RGBA ByteArray → IntArray → Bitmap` 왕복은 만들지 않는다. 이미지 키별 중복 제거·캐시 적중 조건은 A와 동일하게 맞춘다.
2. 이미지 형식, 알파, 밀도, 색 공간을 고정한다. 디코드된 이미지가 A와 같은 시각적 결과인지 샘플 핀을 픽셀 또는 스크린샷으로 검사한다. 차이가 있으면 동일 표현으로 맞춘 뒤 성능을 비교한다.
3. 서버에서 이미지 URL만 주는 설계라면 이미지 다운로드 완료 시각을 별도로 남긴다. 이번 **요청 제외 지표**에서는 해당 다운로드도 제외한다. 실제 제품 판단에는 총 이미지 바이트, 추가 요청 수, 캐시 적중률과 다운로드를 포함한 사용자 체감 시간도 별도로 제시한다.

## 시계와 지표

각 변형에서 **T0는 해당 페이지의 핀 메타데이터와 필요한 이미지 바이트(C)가 메모리에 모두 준비되어, 이미지 처리 작업을 시작할 수 있는 시각**이다. fixture를 미리 읽되, 처리 결과 이미지와 Bitmap은 미리 만들지 않는다. 페이지가 여럿이면 페이지별 T0와 마지막 페이지 T0를 함께 기록한다. 동일한 `elapsedRealtimeNanos` 계열 시계와 load ID를 사용한다.

| 지표 | 계산·의미 |
| --- | --- |
| 첫 핀 표시 | T0 → 현재 load ID의 핀이 포함된 첫 MapLibre 렌더 프레임 |
| 전체 핀 표시 | 마지막 페이지 T0 → 현재 load ID의 모든 **화면 내** 핀을 확인한 `fullyRendered` 프레임. 첫 페이지 T0→전체 핀도 함께 기록 |
| 이미지 준비 | T0 → 마지막 필요 이미지의 Bitmap 생성 완료. 고유 키별 생성·디코드 시간도 기록 |
| 지도 등록 | Bitmap 준비 → 마지막 style 이미지 등록 → `source.setGeoJson()` 호출 |
| 프레임 지연 | Perfetto의 메인 스레드 점유, 긴 프레임·deadline miss 수, 프레임 시간 분포 |
| 비용 | CPU 사용 시간, 작업 스레드, 할당량·최대 메모리, C의 압축·디코드 후 이미지 바이트 |

현재 `first-pin-frame`/`all-pages-frame`은 MapLibre 콜백에서 보이는 feature를 질의한 값이다. 실제 디스플레이 픽셀의 광학 측정값은 아니다. 기존 `all-pages-frame` 판정은 보이지 않는 핀이 있으면 발생하지 않을 수 있으므로, fixture의 모든 핀이 화면 안에 있는 시나리오를 쓰거나 **화면 내 기대 ID 집합**으로 판정하도록 계측을 보완한다. `map-idle-rendered`는 보조 지표로 둔다.

## 실행 순서와 판정

1. **실험 1 파일럿·본 실험:** A와 B를 각 5회 시험해 계측·화면 일치·스레드 위치를 확인한다. 이어 일반적인 고유 이미지 수(약 14~17개)와 고유 스탬프가 많은 시나리오에서 A/B를 순서를 섞어 각 20회 반복한다.
2. **실험 2 파일럿·본 실험:** 변경 전 A와 C를 각 5회 시험해 계측·화면 일치를 확인한다. 같은 시나리오에서 A/C를 순서를 섞어 각 20회 반복한다. 이때 A는 실험 1의 B가 아닌 현재 구현이다. 매회 카메라와 style을 초기화하고 기기 온도·캐시 상태를 기록한다. 다중 페이지 fixture는 첫 페이지와 전체 페이지 지연을 별도 검증한다.
3. 각 실험에서 A와 변경 방식의 중앙값·90백분위·범위 및 차이를 따로 보고한다. 가장 먼저 **첫 핀/전체 핀 프레임 시간**, 다음으로 **메인 스레드 점유와 긴 프레임**을 본다. C가 이미지 생성 CPU를 줄여도 디코드·지도 등록 또는 이미지 바이트가 늘어 총 시간이 길어지면 개선이라고 판단하지 않는다.

기존 실기기 기준점은 [`baseline-measurement.md`](baseline-measurement.md)에 있다. 이전 측정은 bbox·핀 수가 일치하지 않으므로 새 A/B/C의 개선율 분모로 사용하지 않는다.
