# 이벤트 버튼 Firebase Remote Config 운영

## 환경과 키

현재 Android와 iOS는 Firebase 프로젝트 `pheeeew-8bf12`를 공유한다. 앱의 `DEVICE_ENVIRONMENT`를 기준으로 아래 키 하나만 읽는다. Debug/Release의 fetch 간격과 환경별 키 선택은 서로 별개의 정책이다.

| 환경 | 파라미터 | 타입 | 앱 기본값 | 현재 빌드 |
| --- | --- | --- | --- | --- |
| dev | `press_event_enabled_dev` | Boolean | `false` | Android Debug / iOS Debug |
| prod | `press_event_enabled_prod` | Boolean | `false` | Android Release / iOS Release |

개발 키를 ON으로 게시해도 운영 앱은 운영 키만 읽는다. 파라미터 분리는 권한·Firebase 프로젝트 분리가 아니다. 콘솔 게시와 템플릿 복구는 두 키가 포함된 템플릿 전체에 적용된다.

## 최초 콘솔 등록

1. Firebase 콘솔에서 `pheeeew-8bf12` 프로젝트의 Remote Config를 연다.
2. 위 두 파라미터를 Boolean 타입, 기본값 `false`로 등록한다. 사용자 조건은 필요하지 않다.
3. 게시 전 변경 내역에 두 파라미터 이외의 수정이 없는지 확인한 뒤 게시한다.
4. 개발 키부터 `true`로 변경·게시하여 Android/iOS Debug에서 노출을 확인한다. 운영 키는 별도로 변경한다.

이 문서는 콘솔 등록 절차를 제공하며, 저장소 수정만으로 Firebase 콘솔에 파라미터가 등록되지는 않는다. 콘솔의 실제 현재 값과 등록·게시 여부는 별도 확인해야 한다.

2026-11-12 두 Boolean 파라미터를 기본값 false로 등록하고 버전 23으로 게시했다. 이후 운영값은 콘솔에서 확인한다.

## 변경·적용 시점

- 대상 환경의 키를 `true`로 설정·게시하면 프레스 화면에 이벤트 버튼이 표시된다. `false`이면 숨겨진다. 저장만 하고 게시하지 않은 값은 앱에 적용되지 않는다.
- Android는 `ProcessLifecycleOwner`의 `onStart`, iOS는 최초 활성 scene 표시와 background 이후 active 전환에서 비동기 조회·활성화를 요청한다. iOS의 중복 활성 알림과 SDK 요청 진행 중의 중복 갱신은 합친다.
- SDK 초기화 후 마지막 활성화 값을 먼저 복원하고, 이어서 `fetchAndActivate`를 실행한다. splash·인증·지도 준비는 이를 기다리지 않는다.
- 최소 fetch 간격은 Debug 0초, Release 3,600초다. 0초는 개발 검증용이며 운영 앱에는 적용하지 않는다. 양 플랫폼 네트워크 fetch timeout은 10초다.
- 최소 간격 안의 호출은 SDK 캐시를 사용한다. 1시간마다 자동 조회하는 타이머는 없고, 간격이 지난 뒤 다음 시작·전경 복귀에서 새 값을 조회한다. 앱을 계속 사용하는 동안의 실시간 구독·주기적 조회는 하지 않는다.
- 새 값의 조회와 활성화가 성공하면 현재 프레스 화면에도 즉시 반영한다. SDK가 성공했으나 새 활성화 내용은 없다고 반환해도 현재 활성화 값을 읽는다.
- 버튼 클릭은 즉시 이벤트 화면으로 이동한다. navigation entry마다 최초 1회 SDK 캐시 간격을 0초로 지정한 fetch 후 activate로 최신 설정을 확인한다. 전경 갱신이 진행 중이면 완료를 기다린 뒤 강제 조회하며 일반 전경 갱신의 최소 간격 설정 자체는 변경하지 않는다.
- 확인 중에는 로딩과 뒤로가기를 제공하고, 통과하기 전에는 이벤트 순위 조회·게임 ViewModel을 생성하지 않는다. false이면 컬렉션 날짜 상세 오류와 같은 UI로 `현재 진행중인 이벤트가 없어요.` / `다음 이벤트를 기다려주세요` / `확인`을 표시한다. 확인은 이전 화면으로 돌아간다.
- 진입 조회 실패 시 이전 true 캐시로 이벤트를 허용하지 않는다. `진행 중인 이벤트를 불러오지 못했어요`와 함께 OS에서 연결 안 됨이 확인되면 `네트워크 연결을 확인해주세요`, 그 외에는 `다음에 다시 시도해주세요`를 표시한다. 확인은 이전 화면으로 돌아간다. 연결 상태 확인은 최대 1초만 기다리며 상태를 알 수 없으면 일반 오류 안내를 사용한다.
- 진입 확인을 통과한 navigation entry는 설정을 계속 구독하지 않는다. 이후 OFF가 되어도 기존 게임·결과 제출·재시도·이벤트 ID·서버 접수 정책을 유지한다. 프레스 화면으로 돌아오면 갱신된 버튼 노출 상태를 따른다.

## 오프라인·실패·복구

- 처음 설치하여 활성화한 값이 없으면 `false`로 시작한다. 첫 실행이 오프라인이어도 앱 시작을 막지 않는다. 버튼 표시는 기본값·캐시 정책을 따르지만 이벤트 화면 최초 진입 확인에는 성공적인 최신 조회가 필요하다.
- Firebase SDK가 저장한 마지막 활성화 값은 프로세스 종료·재실행 후에도 복원한다. 조회 실패·오프라인·throttling에서는 마지막 값을 유지한다. 오래되었다는 이유로 자동으로 `false`로 바꾸지 않는다.
- SDK 초기화 실패 시 기본값을 유지하고 다음 전경 진입에서 초기화를 다시 시도한다. 정상 초기화 뒤 조회 실패는 다음 전경 진입에서 다시 조회한다. 네트워크 복구 자체만으로 즉시 재조회하지는 않는다.
- 값을 되돌릴 때는 대상 키만 이전 값으로 수정·게시하는 방법을 우선 사용한다. 템플릿 이력에서 복구할 경우 다른 키와 기존 Remote Config 파라미터까지 함께 되돌아갈 수 있으므로 전체 변경 내역을 확인한다.
- 복구한 값도 같은 fetch·활성화 정책을 따른다. 오프라인 단말의 기존 활성화 값을 원격으로 즉시 지우는 기능은 아니다.

## 검증 시나리오

1. Android·iOS 각각 같은 설치 상태에서 개발 키 ON → OFF → ON을 게시하고 background → foreground로 전환한다. 버튼 표시 → 숨김 → 표시를 확인한다. 운영 키가 바뀌지 않았는지도 확인한다.
2. 운영 빌드는 개발 키를 변경해도 바뀌지 않고 운영 키를 따르는지 확인한다. 운영 기기 검증은 게시 영향 범위를 확인한 별도 절차로 수행한다.
3. 전용 테스트 설치에서 활성화 이력 없이 오프라인으로 첫 실행하여 버튼이 숨겨지고 앱 진입이 진행되는지 확인한다. 기존 사용자 설치의 데이터를 지우지 않는다.
4. ON을 활성화한 뒤 앱을 종료하고 오프라인으로 재실행하여 캐시가 복원되는지 확인한다. OFF 캐시도 같은 방법으로 확인한다.
5. ON으로 버튼을 표시한 상태에서 OFF를 게시하고 버튼을 누른다. 이동한 이벤트 화면에서 종료 안내와 확인 버튼을 표시하고 순위·게임 요청을 시작하지 않는지 확인한다. 확인으로 돌아가면 버튼이 숨겨져야 한다.
6. 이벤트 화면의 최초 설정 조회를 실패시켜 연결 유무에 따라 두 실패 문구가 구분되고 확인으로 돌아가는지 확인한다. 확인 중 뒤로 이동한 경우 늦은 응답이 화면을 다시 열지 않아야 한다.
7. 진입 확인을 통과한 이벤트 화면에서 게임 중 OFF를 게시하고 전경 복귀로 설정을 수신한다. 기존 lifecycle에 따른 게임 일시 중단·취소 규칙은 그대로 유지되며, 설정 OFF 자체가 게임·완료 결과·제출·재시도를 막지 않는지 확인한다. 프레스 화면 복귀 시에는 버튼이 숨겨져야 한다.
8. Release는 마지막 성공 fetch 이후 1시간 안의 전경 복귀에 새 게시값이 즉시 반영되지 않을 수 있음을 확인한다. 화면 최초 진입 조회는 이 간격을 우회한다. SDK throttling·연결 실패가 있으면 진입 오류 안내를 표시한다.
