# 기기 활동 DB 비용 측정

활동 원본을 자동 삭제하지 않는 정책에서 저장 용량과 최근 30일 집계 비용을 확인해요. 운영 DB에 연결하지 않고 가짜 데이터만 사용해요.

## 다시 실행하기

BE 디렉터리에서 Python 3와 Docker로 실행해요.

```bash
python3 docker/benchmarks/device-activity.py
```

스크립트가 이름이 겹치지 않는 PostgreSQL/PostGIS 컨테이너를 생성하고 끝나면 해당 컨테이너와 임시 볼륨을 제거해요. 호스트 포트·외부 네트워크를 열지 않고 운영 연결 정보도 받지 않아요. 기존 개발 DB는 사용하지 않아요.

실제 `V20260909__create_devices.sql`, `V20260917_1__create_device_daily_activities.sql`을 적용하고 `DeviceDailyActivityRepository.findCounts`의 현재 SQL을 읽어 실행해요. 전체 Flyway 실행이나 JPA 통합 테스트를 대체하지 않아요.

## 측정 조건

- 측정일: 2026-09-17. ARM64 macOS의 Docker에서 AMD64 `postgis/postgis:17-3.5`를 실행했어요. 당시 이미지 ID는 `5bf22af1b0e8`, PostgreSQL 17.5 / PostGIS 3.5.2였어요. 운영 EC2와 다른 환경이에요.
- 컨테이너 제한: CPU 2개, 메모리 1GiB, 공유 메모리 256MiB. DB `shared_buffers=128MB`, `work_mem=4MB`였어요.
- Android/iOS는 절반씩이고 10개 기기 그룹이 번갈아 매일 활동해요. 하루 1,000개 시나리오의 전체 기기 수는 10,000개, 하루 10,000개 시나리오는 100,000개예요. 같은 날짜·기기는 한 행만 저장해요.
- 기준일은 KST 2026-09-17이고 집계 범위는 2026-08-19~09-17이에요. 오래된 활동도 삭제하지 않아요. 데이터 적재 후 `ANALYZE`를 실행하며 별도 `VACUUM`이나 인덱스 추가는 하지 않아요.
- 행 수와 실제 DAU·MAU 결과를 검증한 뒤 `EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)`을 5회 실행해요. SQL에는 서비스와 같은 3초 제한을 적용해요. 동시 앱 요청 없이 이미 읽은 데이터로 측정하며 콜드 캐시 성능은 측정하지 않아요.

## 결과

용량은 활동 테이블만의 `pg_table_size`와 `pg_indexes_size`이며, 합계는 `pg_total_relation_size`예요. MiB는 1,048,576바이트예요.

| 일별 활동 기기 / 보관 날짜 | 원본 행 수 | 테이블 MiB | 인덱스 MiB | 합계 MiB | 집계 중앙값 ms | 5회 범위 ms |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 1,000 / 30일 | 30,000 | 1.98 | 1.57 | 3.55 | 46.587 | 46.301~47.971 |
| 1,000 / 365일 | 365,000 | 23.79 | 18.85 | 42.64 | 46.400 | 45.933~52.600 |
| 10,000 / 365일 | 3,650,000 | 237.71 | 188.01 | 425.72 | 522.545 | 484.039~575.230 |

참조하는 `devices` 테이블과 인덱스는 10,000개 기기에서 1.96MiB, 100,000개 기기에서 19.30MiB였어요. 위 활동 원본 합계에는 이 용량, 날짜별 요약·상태 테이블, WAL, 임시 파일, 백업은 포함하지 않아요.

| 마지막 실행의 접근 | 30,000행 | 365,000행 | 3,650,000행 |
| --- | ---: | ---: | ---: |
| 최근 30일 활동 행 | 30,000 | 30,000 | 300,000 |
| 활동 테이블 접근 | 순차 스캔 | 날짜·기기 인덱스의 Bitmap Scan | 날짜·기기 인덱스의 Bitmap Scan |
| 기기 테이블 순차 스캔 행 | 10,000 | 10,000 | 100,000 |
| shared hit / read 블록 | 370 / 0 | 489 / 0 | 4,796 / 0 |
| temp read / written 블록 | 0 / 0 | 0 / 0 | 1,102 / 1,106 |

첫 두 시나리오는 플랫폼별 DAU 500개·MAU 5,000개, 마지막은 DAU 5,000개·MAU 50,000개로 기대값과 일치했어요. 세 시나리오 모두 SQL 3초 제한 안에 완료됐어요.

## 해석과 운영에서 남은 확인

원본이 30일에서 365일로 늘어도 이번 분포에서는 기존 `(activity_date, device_id)` 인덱스가 최근 30일 조회 범위를 제한했어요. 원본 전체 크기만큼 집계 시간이 늘지는 않았어요. 하루 활동량을 10배로 늘리면 최근 30일 입력도 10배가 되어 집계 중앙값이 약 523ms로 증가했어요.

큰 시나리오는 임시 블록을 약 8.61MiB 읽고 8.64MiB 썼어요. 실제 활동량 증가 시 정렬·중복 제거의 임시 I/O도 함께 관찰해야 해요. 이 결과만으로 `work_mem`이나 인덱스를 변경하지 않아요.

이는 에뮬레이션 환경의 5회 SQL 측정이며 운영 지연 상한이나 p95가 아니에요. JDBC·커넥션 대기·트랜잭션 종료·요약 저장 시간도 제외해요. 매일 새 기기가 생기는 분포, 플랫폼 편중, 다른 요청과의 경쟁, 인덱스 팽창은 재현하지 않았어요. SQL 측정 결과만으로 앱의 3초 트랜잭션 제한 준수를 보장하지 않아요.

**원본 자동 삭제는 추가하지 않아요.** 운영에서 실제 일별 행 증가량, 인덱스 포함 용량, 최근 30일 활동량, 전체 기기 수, 집계 시간과 DB 부하를 확인한 뒤 보관 정책을 판단해요. 배포 후 운영 기준값 측정은 남아 있어요.
