# regions·개인 Press 모니터링 재현

## 5-A: 격리 환경과 데이터 준비

Java 21과 Docker를 실행하고, [SGIS 준비 절차](../../scripts/regions/README.md)로 만든
2025년 2분기 전국 경계 import SQL을 지정한다. 실제 사용자 데이터·운영 키는 사용하지 않는다.

```bash
MONITORING_REPRO_IMPORT_SQL=/absolute/path/sgis-2025-2Q-import.sql \
./gradlew test --tests com.pheeeew.monitoring.MonitoringReproductionIntegrationTest --rerun
```

이 Mac의 Docker 연결 검증에서는 `JAVA_TOOL_OPTIONS=-Djava.net.preferIPv6Addresses=true`를 함께 지정했다.
사용한 SQL은 639,871,612바이트이며 SHA-256은
`8ff11e6b9c62b40cc2d6aec98ec236bff5b452910a818462ad47d816f3647a60`이다.

환경변수가 없으면 Spring과 컨테이너를 시작하기 전에 건너뛴다.
선택된 테스트는 공유 PostgreSQL 17·PostGIS 3.5 컨테이너 안에 매 실행 새 논리 DB를 만든다.
전체 Flyway와 JPA 검증 후 앱을 임의 포트에서 실행하고, 임시 RSA 키를 사용한다.
DB URL은 입력받지 않는다. 기존 개발 DB와 공유 테스트 DB에는 데이터를 넣지 않는다.
앱·풀은 테스트 종료 때 닫히고, 임시 DB와 import 파일은 Testcontainers 종료 때 함께 제거된다.

| 준비 조건 | 고정 값 |
| --- | --- |
| 실제 SGIS 경계 | SIDO 17 / SIGUNGU 252 / EMD 3,559 |
| 합성 기기 | 100개, Android·iOS 각 50개 |
| 감정 | 10,000개, 서울 EMD 표시점에 순환 배치, MEMO·익명·미삭제, 상태별 2,000개 |
| 개인 Press | KST 실행 당일, 기기별 5상태 × 1회, 총 500행·500회 |
| 앱 버전 | Android·iOS 활성 버전 1.0.0 |
| Hikari 최대 연결 | 10개 |

기존 `verify.sql`과 `backfill-verify.sql`을 실제 실행한다. 경계 개수, 감정 분류·내용,
Press 날짜·개수, 버전 행, 집계 준비 상태와 `/actuator/health`의 HTTP 200·UP을 확인한다.
빈 서울 EMD나 부분 seed는 통과할 수 없다. seed SQL은 이 테스트의 빈 임시 DB 전용이다.

이 단계는 실행 환경 준비 검증이다. 운영의 수십·수백 초 지연 재현이나 성능 개선을 증명하지 않는다.
호스트·Docker 자원을 사용하며 EC2/RDS 사양과 동일하지 않다. `test`에서 활성화되는 스케줄러는 유지한다.
운영 전용 DAU/MAU 집계 스케줄러는 실행하지 않는다.
`test` 프로필은 동기 콘솔 로그를 쓰므로 운영의 비동기 로그와 조건이 다르다.
5-B에서 단독 기준값, 5-C에서 regions 부하 중 동반 지연, 5-D에서 Press 단독·혼합 부하를 측정한다.

## 5-B: 경로별 단독 기준값

위 명령으로 준비 검증 후 9조건을 순서대로 실행한다. regions는 `126..128° / 37..38°` 화면,
그룹 필터 없이 SIDO·SIGUNGU·EMD를 각각 조회한다. 다른 조건은 Android·iOS 버전 확인,
health, 오늘 개인 Press 조회·전체 조회·저장이다. 합성 기기 1개의 실제 서명 토큰을 사용한다.
앱은 loopback 임의 포트에만 열며 Prometheus registry를 활성화한다. 외부 전송은 하지 않는다.

각 조건은 워밍업 3회·측정 20회, 동시 요청 1개와 요청 시작 간격 목표 1초다.
응답이 1초를 넘으면 다음 요청을 직렬로 시작해 실제 빈도는 낮아진다. 중첩·보충 요청은 없다.
HTTP 200뿐 아니라 regions 합계 10,000, 버전·health·Press의 실제 값도 확인한다.
쓰기는 마지막에 `{"counts":{"ANGRY":1}}`를 전송한다. 워밍업 포함 23회 적용되어 최종 합은 523이다.
응답 파싱·검증은 클라이언트 지연 측정에서 제외하고, 응답 본문 수신까지 측정한다.

성공한 실행은 `build/reports/monitoring/baseline.json`을 갱신한다. 실패하면 과거 파일이 남을 수 있으므로
`generatedAt`과 테스트 성공 여부를 함께 확인한다. 토큰·기기 식별자·응답 원문은 저장하지 않는다.
파일에는 워밍업/측정 원시 시간(ms), 최근접 순위 p50·p95·최대값, 측정 구간 길이와 DB Timer 차이가 있다.
DB Timer는 측정 20회 전후의 프로세스 전체 호출 수·누적 시간·평균 차이다. 요청별 시간이 아니며
같은 구간의 정리 스케줄러 호출도 포함될 수 있다. JDBC 통신·매핑·일부 대기를 포함하며
순수 SQL 시간이나 커넥션 점유 시간과 같지 않고, 중첩된 단계 시간을 더해서는 안 된다.
20개 표본의 p95는 탐색용 기준값이다. 운영 SLO·p99 판정이나 병목 재현 성공으로 해석하지 않는다.

## 5-C: regions 부하 중 동반 지연

위 실행 명령에 `MONITORING_REPRO_SCENARIO=regions`를 추가하면 새 데이터로 5-C만 실행한다.
EMD 조회 작업자 0→4→16개를 순서대로 두고, 각 단계에서 버전 Android/iOS·health·Press 내/전체 조회를
동시에 호출한다. 작업자와 동반 조회 모두 시작 간격 목표 1초이며, 느려지면 실제 빈도는 낮아진다.
공통 시작 신호와 요청별 상대 시작 시각을 기록한다. 동반 조회는 첫 3회 워밍업 후 20회가 측정이다.
`build/reports/monitoring/regions-companions.json`에 원시 시간·응답 검증 결과·단계 전체 DB Timer 차이,
100ms 간격 Hikari 사용/대기/전체 연결·힙·프로세스 CPU를 남긴다. CPU는 앱과 부하 생성기를 함께 포함하고
음수는 관측 불가다. 풀/Timer 관측은 워밍업과 진행 중 작업 회수 구간도 포함하며 요청별 값이 아니다.
timeout·비200·잘못된 본문에서 신규 발행을 멈추고 진행 중 결과를 회수해 부분 보고서를 저장한다.
해당 단계는 정상 응답/완료 조건 실패로 처리하고 후속 단계는 실행하지 않는다. 클라이언트 timeout이
서버 JDBC 취소를 보장하지 않는다. 성공한 단계만 비교하며, 짧은 탐색 실험으로 운영 원인을 확정하지 않는다.


## 5-D: Press 단독·혼합 스트레스 비교

`MONITORING_REPRO_SCENARIO=press`로 새 DB에서 추가 부하 없음 → 동일 기기 Press 32개 → 서로 다른 기기 Press 32개
→ regions EMD 32개 → regions 32개 + 서로 다른 기기 Press 32개를 순서대로 실행한다.
부하 작업자의 시작 간격 목표는 100ms(작업자당 최대 초당 10건), 동반 조회 5개는 기존 1초·3회 워밍업·20회 측정이다.
닫힌 루프이므로 느려지면 실제 요청량이 감소한다. 운영 트래픽을 복제한 실험이 아니라 경합을 찾는 스트레스 조건이다.
같은 기기의 같은 ANGRY 행에 대한 경합과 기기가 다른 요청의 공유 풀 사용을 비교한다.
POST 한 건당 `{"counts":{"ANGRY":1}}`를 보내며 재시도하지 않는다. 이 API는 counts를 받으므로 여러 누름을
한 요청으로 묶을 수도 있다. 실제 앱이 얼마나 묶어 보내는지는 클라이언트 코드를 별도로 확인해야 한다.
각 단계의 Press 증가량은 다음 단계에 유지한다. 데이터 행 수는 500개로 고정된다.
응답은 요청 시작 전 성공 누계와 현재 발행 시도 누계 범위·5상태·합계를 검증한다.
전부 성공하고 진행 중 요청을 회수한 실행만 기기별 ANGRY 증가와 전체 DB 증가가 성공 POST 수와 같은지 확인한다.
실패 POST는 커밋 여부를 알 수 없는 결과로 기록하고 후속 단계를 중단한다. 성공 수와 DB 차이를 유실로 단정하지 않는다.

`build/reports/monitoring/press-companions.json`에 단계별 실제 요청 시각·지연·상태·검증 결과·합성 기기 인덱스,
DB Timer 차이·풀/힙/CPU를 기록한다. UUID·토큰·응답 원문은 저장하지 않는다.
신규 요청 발행 예산은 단계당 45초다. 종료 때 진행 중 요청을 회수하며 관측은 유지한다.
운영의 3분 지연도 관측할 수 있도록 이 시나리오의 HTTP timeout은 5분이다. 23회 미완료나 오류는
부분 보고서를 남기고 실패한다. 5-C의 60초 timeout·1초 부하 간격은 유지한다.

5-C 최종 실행에서는 regions 최대 1.68초, 동반 요청 p95 222~249ms와 풀 대기 최대 10개가 관측됐다.
이는 운영의 3분 지연을 재현한 결과가 아니다. 로컬 감정 1만 건·Press 500행, 로컬 앱/DB·공유 부하 생성기,
`test` 로그/스케줄러 조건이며 운영 당시 요청량·데이터량·EC2/RDS 자원·락 상태는 아직 맞추지 못했다.
운영 Compose 설정은 앱 메모리 1024MiB와 MaxRAMPercentage=60이지만 이 테스트에 같은 자원 제한을 적용하지 않았다.
서버 sleep·강제 DB 락으로 지연을 만들지 않는다. 짧은 실험에서 지연이 작아도 운영 병목이 없다는 뜻은 아니다.


### 5-D 최종 실행 기록: 2026-10-10 KST

보고서 생성 시각 `2026-10-10T05:21:39.754840Z`, 선택 테스트 1개 통과(실패·오류·건너뛰기 0), 준비 포함 3분 32초.
