# 클라이언트 300m 균등 원 근사 좌표 가이드

클라이언트는 실제 위치 주변 반경 300m 원 내부에서 면적 균등하게 고른 좌표만 전송해요. 서버는 받은 좌표 주변 반경 300m에서 독립적으로 한 번 더 이동해 최종 위치를 저장해요. [ADR-0006](../adr/0006-use-independent-uniform-disks-for-sigh-location.md)의 계약이며, 구형 앱 전환과 실제 앱 검증이 끝나기 전에는 배포하지 않아요.

## 클라이언트 선택에 따른 차이

| 클라이언트가 보내는 값 | 공통 서버 처리 | 최종 모양·계약 |
| --- | --- | --- |
| 실제 위치 | 받은 좌표 주변 반경 300m 균등 원 | 서버만 이동하는 단일 원이에요. 비교용이며 제품 계약에서는 실제 위치 전송을 허용하지 않아요 |
| 실제 위치 주변 반경 300m 균등 원에서 고른 근사 좌표 | 동일해요 | 선택한 클라이언트·서버 이중 원 분포예요. 같은 장소에서도 외곽 밀도가 완만해져요 |
| 기존 300m 격자 중심 | 동일해요 | 격자 중심 주변 원이 돼요. 선택한 이중 원 분포와 달라서 클라이언트 변경이 필요해요 |

[최종 비교 그림·수치](../decisions/map-star-location-evidence.md)는 합성 좌표 비교예요. 오른쪽은 선택한 이중 원, 가운데는 서버만 원, 왼쪽은 이전 서비스의 사각형 방식이에요. 서버가 입력만 보고 경로를 감지하거나 서로 다른 모드를 선택하는 것은 아니에요. 클라이언트의 반경·분포를 바꾸면 비교한 모양과 달라져요.

## 한 번의 새 등록

1. 새 `requestId`를 만들고 기기의 WGS84 위치를 `[longitude, latitude]` 순서로 EPSG:5179에 변환해요.
2. 플랫폼 보안 난수원으로 서로 독립인 균등 난수 `U,V ∈ [0,1)`를 뽑아 아래 원 오프셋을 더해요.
3. 결과를 WGS84로 역변환하고 전송 객체에는 `requestId`, 근사 `longitude`, 근사 `latitude`만 넣어요. v2의 선택 `memo`는 기존대로 사용할 수 있어요.
4. 실제 위치·중간 좌표에 대한 불필요한 참조를 폐기해요. 재시도용으로는 이미 만든 요청만 유지해요.
5. 성공 응답의 `geometry.coordinates`를 지도에 표시해요. 요청 좌표를 최종 핀으로 사용하지 않아요.

```text
r = 300 × sqrt(U)
theta = 2 × pi × V
approximateEasting  = easting  + r × cos(theta)
approximateNorthing = northing + r × sin(theta)
```

원의 둘레가 아니라 면적 전체에 균등하게 뽑아요. `r=300×U`는 중심 쪽에 더 몰리므로 사용하지 않아요. 격자 스냅, 소수점 자르기, 최소 이동 거리, 재추첨 후 경계에 밀어붙이는 clamp도 넣지 않아요. 난수 0은 유효하므로 극히 드물게 이동이 0일 수 있어요. 무작위화는 최소 이격 거리를 보장하지 않아요.

`300m`는 EPSG:5179 투영 평면 거리예요. 위도·경도에 미터를 직접 더하지 않아요. 두 번 이동한 최종 좌표는 실제 위치에서 평면 기준 최대 600m까지 갈 수 있어요. 지표면 거리에는 투영·수치 오차가 있고 GPS 정확도까지 보장하는 값은 아니에요. 대한민국 밖 적용은 별도 검토가 필요해요.

## 좌표계와 공통 계산 확인

변환 라이브러리의 축 순서를 `x=longitude/easting`, `y=latitude/northing`으로 고정해요. EPSG:5179가 내장돼 있으면 그 정의를 사용해요. 직접 정의해야 한다면 기존 서버와 같은 아래 정의를 사용해요.

```text
+proj=tmerc +lat_0=38 +lon_0=127.5 +k=0.9996
+x_0=1000000 +y_0=2000000 +ellps=GRS80
+towgs84=0,0,0,0,0,0,0 +units=m +no_defs
```

공개 기준점 WGS84 `(126.9780, 37.5664)`는 기존 PostGIS 3.5 기준 EPSG:5179 `(953901.103685, 1952020.986470)`이에요. 아래 값은 **테스트용 고정 난수**이며 실제 앱에서 고정해서 사용하지 않아요.

| U | V | easting 이동(m) | northing 이동(m) |
| ---: | ---: | ---: | ---: |
| 0 | 0 | 0 | 0 |
| 0.25 | 0 | 150 | 0 |
| 0.25 | 0.25 | 0 | 150 |
| 0.81 | 0 | 270 | 0 |

예를 들어 `U=0.25,V=0`이면 `(954051.103685,1952020.986470)`을 WGS84로 역변환해요. 다시 EPSG:5179로 변환해 축 순서와 150m 동쪽 이동을 확인해요. 서버 통합 테스트의 투영 왕복 허용 오차는 `0.0001m`예요. 클라이언트 라이브러리에서도 공통 좌표와 허용 오차를 검증하고, 맞지 않으면 원인을 확인해요.

## 요청·재시도와 기존 별

`POST /api/v1/sighs`와 `POST /api/v2/sighs`의 필드 이름과 응답 형식은 같아요. 좌표 값의 의미만 격자 중심에서 무작위 근사 위치로 바뀌므로 클라이언트 변경이 필수예요.

- 한 번의 등록 요청을 재시도할 때 새 난수·새 위치·새 `requestId`를 만들지 않아요. 이미 만든 요청을 그대로 다시 보내요.
- 서버는 같은 `requestId`가 다른 좌표·메모로 와도 최초 저장 결과를 반환해요. 입력 좌표 원문을 저장하거나 비교하지 않아요.
- 동시 요청에서 여러 위치 후보가 계산될 수 있지만 저장되는 한숨과 최종 위치는 하나예요. 경합에서 진 요청도 저장된 위치를 반환해요.
- 이전 사각형 방식으로 저장된 별도 그대로 조회해요. 기존 별의 이동·재추첨·일괄 갱신은 하지 않아요.

## 위치 정보와 난수 처리

플랫폼의 보안 난수 API를 사용해 `[0,1)` 균등 값을 만들어야 해요. `Math.random` 같은 비보안 난수, 고정 seed, 현재 시각·좌표·사용자 식별자에서 만든 seed는 사용하지 않아요. 서버는 별도의 `SecureRandom`을 사용하므로 클라이언트와 난수 값을 주고받지 않아요.

실제 위치를 서버 DTO·모바일 로그·분석 이벤트·오류 수집 도구에 넣지 않아요. 전송한 근사 좌표도 로그·APM·프록시 요청 본문 기록 대상에서 제외해야 해요. 서버가 실제 위치를 별도 저장하지 않는다는 이유로 실제 위치 전송이 허용되는 것은 아니에요. 서버는 받은 숫자만으로 클라이언트가 올바르게 흐렸는지 판별할 수 없어요.

근사 좌표도 개인정보가 될 수 있어요. 같은 장소의 여러 공개 좌표를 연결해 평균내면 중심을 추정할 수 있으므로 이중 원 이동이나 보안 난수만으로 익명성을 보장하지 않아요. 새 등록마다 독립적으로 뽑는 것과 동일 등록 재시도에 요청을 재사용하는 것을 구분해요.

## 전환과 배포 전 체크리스트

- [ ] 클라이언트의 기존 격자 계산을 원 이동으로 교체하고 보안 난수·축 순서·공통 좌표·재시도를 확인해요.
- [ ] 구형 앱 차단·강제 업데이트 또는 별도 API 버전 유지 등 실제 전환 방식을 팀이 결정해요. JSON 호환만으로 혼재를 허용하지 않아요.
- [ ] 클라이언트 변경과 새 서버를 함께 연결해 실제 앱의 여러 위치·밀도·줌에서 확인해요. 서버만 바꿔서는 선택한 이중 원 분포가 되지 않아요.
- [ ] 위치 원문의 로그·APM·분석 수집 여부를 점검해요.
- [ ] 서버 PR 준비 후 클라이언트 팀원이 새 계약을 적용하고, 배포 전에 실제 앱 확인 결과와 배포 승인을 남겨요. 이번 서버 구현에는 자동 버전 판별·배포 차단 장치가 없어요.

시간에 따른 흐림·색상·노출 만료·줌별 크기는 이번 변경에 포함하지 않아요.
