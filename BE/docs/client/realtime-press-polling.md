# 실시간 프레스 폴링 연동

관련 이슈: [#1098](https://github.com/woowacourse-teams/2026-pheeeew/issues/1098) (기본 폴링),
[#1100](https://github.com/woowacourse-teams/2026-pheeeew/issues/1100) (캐시 적용 폴링).
앱이 일정 주기로 일반 HTTP 조회를 보내 실시간 프레스 화면의 순위와 최근 활동 인원을 받는 방식입니다.
이 문서는 BE의 계약과 앱 연동 방법을 설명합니다. 실제 앱 연동 검증 기록은 아닙니다.

## 사용할 수 있는 실시간 프레스 연동

아래 방식은 서로 독립된 API이며 앱이 하나를 골라 연동합니다. 입력, 집계, 순위 기준은 같습니다.

| 방식 | 경로 | 문서 |
| --- | --- | --- |
| WebSocket | `GET /api/v1/press-race` (Upgrade) | [실시간 프레스 연결, 입력 복구 연동](realtime-press.md) |
| 기본 폴링 | `GET /api/v1/press-race/snapshot` | 이 문서 |
| 캐시 적용 폴링 | `GET /api/v2/press-race/snapshot` | 이 문서의 [캐시 적용 폴링](#캐시-적용-폴링) |
| SSE 구독 | `GET /api/v1/press-race/stream` | [실시간 프레스 SSE 구독 연동](realtime-press-sse.md) |

두 폴링은 인증, 요청, 응답 필드와 의미, 순위 기준이 같고 응답의 최신성만 다릅니다.
기본 폴링은 요청마다 DB를 읽고, 캐시 적용 폴링은 서버가 만든 공통 순위를 유효시간 동안 재사용합니다.
폴링은 WebSocket 연결, 세션 초기화, 입력 ID, 재연결 정산이 필요하지 않습니다.
입력은 기존 `POST /api/v2/emotions/presses`를 그대로 사용합니다.

## 인증과 요청

`Authorization: Bearer <access token>`으로 기존 기기 access token을 전달합니다.
토큰이 없거나 유효하지 않으면 `401 AUTH-001`입니다. 쿼리로 조회 기기를 선택할 수 없습니다.

| 쿼리 | 규칙 |
| --- | --- |
| `view` | 선택. `PRESS` 또는 `ALL`. 생략하면 `PRESS`. 그 밖의 값은 `400 COMMON-001` |

```http
GET /api/v1/press-race/snapshot
GET /api/v1/press-race/snapshot?view=ALL
GET /api/v2/press-race/snapshot
GET /api/v2/press-race/snapshot?view=ALL
Authorization: Bearer <access token>
```

조회는 저장하지 않습니다. 같은 요청을 여러 번 보내도 점수, 활동 인원, 입력 제한에 영향이 없습니다.

## 응답

```json
{
  "date": "2026-11-04",
  "generatedAt": "2026-11-04T02:00:00.123Z",
  "activeCount": 7,
  "view": "PRESS",
  "me": {
    "publicId": "0f4c7a52-8f0e-4a8c-9a37-6d2f3b1d2e11",
    "nickname": "스타크",
    "score": 42,
    "rank": 2,
    "participating": true
  },
  "nearby": [
    {"publicId": "1b0e2f0a-3c4d-4e5f-8a9b-0c1d2e3f4a5b", "nickname": "익명", "score": 57, "rank": 1, "participating": true},
    {"publicId": "0f4c7a52-8f0e-4a8c-9a37-6d2f3b1d2e11", "nickname": "스타크", "score": 42, "rank": 2, "participating": true},
    {"publicId": "9a8b7c6d-5e4f-4a3b-8c2d-1e0f9a8b7c6d", "nickname": "별", "score": 42, "rank": 2, "participating": true}
  ],
  "top100": []
}
```

| 필드 | 의미 |
| --- | --- |
| `date` | KST 기준 경쟁 날짜. 기본 폴링은 DB 시각, 캐시 적용 폴링은 서버 애플리케이션 시각으로 판정 |
| `generatedAt` | 서버가 DB를 관찰한 시각(UTC ISO-8601). 캐시 적용 폴링은 공통 순위를 만든 시각 |
| `activeCount` | `generatedAt` 기준 최근 5초 안에 프레스가 반영된 서로 다른 기기 수 |
| `view` | 요청한 화면 |
| `me` | 내 참여 상태, 실제 점수와 순위. 상위 100명 밖이어도 실제 순위를 담음 |
| `nearby` | 나를 포함한 주변 최대 3명. 미참여면 상위 최대 2명 |
| `top100` | `ALL`이면 표시 순서의 첫 100명. `PRESS`면 빈 목록 |

목록 원소와 `me`는 같은 필드를 사용합니다.

| 필드 | 의미 |
| --- | --- |
| `publicId` | 그날에만 쓰는 공개 ID. 인증 기기 ID와 다름. 날짜가 바뀌면 같은 기기도 다른 값 |
| `nickname` | 기기 닉네임. 없으면 `익명` |
| `score` | 오늘 반영된 감정 프레스 합계 |
| `rank` | 점수만으로 정한 공동 순위 |
| `participating` | 오늘 점수가 양수이면 `true` |

미참여한 `me`는 `publicId=null`, `nickname=null`, `score=0`, `rank=null`, `participating=false`입니다.
목록이 비어도 200이며 `nearby=[]`, `top100=[]`입니다.

### 순위

- 오늘(KST) 점수가 양수인 기기만 참가자입니다.
- 표시 순서는 `score` 내림차순, 같은 점수는 `publicId` 오름차순입니다.
- `rank`는 점수만으로 정합니다. 같은 점수면 같은 순위이고 다음 순위는 건너뜁니다. 예: 1, 2, 2, 4.
- 먼저 도달한 기기를 앞에 보여 주지 않습니다. 공동 순위 안의 표시 순서는 `publicId`가 정합니다.
- `nearby`는 표시 순서에서 내 바로 앞부터 3명이며, 맨 앞과 맨 뒤에서는 3명이 되도록 범위를 보정합니다.
- `top100`은 표시 순서의 첫 100명으로 고정하고 공동 100위를 넘겨 늘리지 않습니다.
- 누른다고 순위가 반드시 오르지는 않습니다. 실제 계산된 순위를 표시합니다.

### 활동 인원

- 접속자 수가 아닙니다. 최근 5초 안에 프레스가 실제로 반영된 기기 수입니다.
- 기기 단위이므로 실제 사람 수와 다를 수 있습니다. 한 기기가 여러 감정을 눌러도 1로 셉니다.
- 새 프레스가 없으면 시간만 지나도 줄어듭니다. 빈 입력과 `0`만 담은 입력은 활동을 연장하지 않습니다.
- 앱이 클릭을 모아 보내는 간격이 길면, 계속 누르는 기기도 전송 사이에 숫자에서 빠질 수 있습니다.

## 입력과의 관계

1. 사용자가 누른 횟수를 모아 `POST /api/v2/emotions/presses`로 보냅니다.
2. 응답의 `counts`, `total`로 내 감정별 개수를 바로 표시합니다. 이 폴링 응답에는 감정별 개수가 없습니다.
3. 순위는 다음 폴링 응답으로 갱신합니다. 누른 직후 순위를 바로 보고 싶으면 폴링 한 번을 즉시 보내도 됩니다.

입력 상한, 제한(429), 서버가 입력을 저장할 수 없을 때의 503은 POST 문서의 계약을 따릅니다.
폴링 조회는 WebSocket 경쟁의 ON/OFF와 무관하게 항상 오늘 상태를 돌려줍니다.

## 폴링 연동 예시

조회 주기 1초는 실험용 초기 후보입니다. 서버가 정한 값이 아니며 검증된 최적값도 아닙니다.

```text
화면 진입 또는 포그라운드 복귀
  → 즉시 GET /api/v1/press-race/snapshot?view=<현재 화면>
  → 응답으로 화면 전체를 덮어쓴다
  → 응답(또는 실패)을 받은 뒤 1초 후 다음 요청을 예약한다

화면 전환(PRESS ↔ ALL)
  → 예약된 요청을 취소하고 새 view로 즉시 조회한다

감정 버튼 묶음 전송 성공
  → POST 응답의 counts로 내 개수를 표시한다
  → (선택) 예약을 앞당겨 즉시 조회한다

다른 탭, 백그라운드, 화면 이탈
  → 예약을 취소하고 조회를 멈춘다
```

- 이전 요청의 응답을 받은 뒤 다음 요청을 예약합니다. 요청이 겹치면 늦게 도착한 오래된 응답이 최신 화면을 덮을 수 있습니다.
  겹칠 수 있는 구현이라면 `generatedAt`이 마지막으로 표시한 값보다 이르면 버립니다.
- 응답은 매번 완전한 화면 상태입니다. 이전 응답과 합치지 않고 그대로 덮어씁니다.
- `date`가 바뀌면 새 날짜의 상태입니다. 전날 순위와 참여 상태를 이어 붙이지 않습니다.
- 응답 내용이 이전과 같아도 같은 형식으로 내려옵니다. 변화가 없다는 별도 신호는 없습니다.
- WebSocket의 `snapshotVersion`, `baseline`, `overtakes`는 없습니다. 추월 알림은 이 방식에서 제공하지 않습니다.

### 오류 처리

두 폴링이 같습니다.

| HTTP | 코드 | 처리 |
| --- | --- | --- |
| 400 | `COMMON-001` | 잘못된 `view`. 앱 구현 오류 |
| 401 | `AUTH-001` | 토큰 없음 또는 무효. 기존 HTTP 토큰 재발급을 한 번에 하나만 수행한 뒤 조회 재개 |
| 네트워크 오류, 5xx | - | 마지막 화면을 유지하고 다음 주기에 다시 조회 |

조회 실패 중에는 마지막으로 받은 순위를 유지합니다. 오래된 `activeCount`를 계속 표시할지, 알 수 없음으로 표시할지는 앱이 정합니다.

## 캐시 적용 폴링

`GET /api/v2/press-race/snapshot`은 기본 폴링과 같은 화면 상태를 돌려주되,
서버가 오늘의 공통 순위를 한 번 만들어 유효시간 동안 모든 요청에 재사용합니다.

| 항목 | 내용 |
| --- | --- |
| 유효시간 | 기본 1초. 실험용 초기 후보이며 검증된 최적값이 아님. 서버 설정으로 바꿀 수 있음 |
| `generatedAt` | 공통 순위를 만들 때 DB를 관찰한 시각. 요청 시각보다 최대 유효시간(과 공통 순위를 만드는 데 걸린 시간)만큼 이를 수 있음 |
| `activeCount` | `generatedAt` 기준. 새 프레스가 없을 때 줄어드는 시점이 최대 유효시간만큼 늦을 수 있음 |
| `me`, `nearby` | 요청한 기기 기준으로 요청마다 계산. 다른 기기의 화면이 섞이지 않음 |
| 날짜 전환 | KST 날짜가 바뀌면 유효시간이 남아 있어도 전날 순위를 쓰지 않고 새 날짜로 다시 만듦 |

- 다른 사람의 입력이 내 화면에 보이기까지 기본 폴링보다 최대 유효시간만큼 늦을 수 있습니다.
- 내가 누른 직후 바로 조회해도 유효시간 안이면 이전 순위가 올 수 있습니다. 내 감정별 개수는 POST 응답으로 표시합니다.
- 같은 유효시간 안의 응답은 `generatedAt`이 같습니다. 바뀌지 않았다고 오류로 보지 않습니다.

### 캐시 적용 폴링 연동 예시

기본 폴링 예시와 같은 흐름에서 경로만 바꿉니다. 조회 주기 1초도 실험용 초기 후보입니다.

```text
화면 진입 또는 포그라운드 복귀
  → 즉시 GET /api/v2/press-race/snapshot?view=<현재 화면>
  → 응답으로 화면 전체를 덮어쓴다
  → 응답(또는 실패)을 받은 뒤 1초 후 다음 요청을 예약한다

화면 전환, 묶음 전송 성공, 백그라운드 처리는 기본 폴링과 같다
```

- 앱에서 기본 폴링과 캐시 적용 폴링을 비교하려면 같은 화면, 같은 조회 주기에서 경로만 바꿔 연동합니다.
- 늦게 도착한 응답을 버리는 기준(`generatedAt`)과 오류 처리는 기본 폴링과 같습니다.

## BE 검증의 범위

실제 PostgreSQL에서 실제 POST 경로로 저장한 뒤 조회해 다음을 확인합니다.
- 여러 감정의 점수 합산과 한 기기를 활동 인원 1로 세는 것
- 동점의 공동 순위
- 쓰기 없이 시간이 지나면 활동 인원이 줄어드는 것
- 빈 입력이 활동을 연장하지 않는 것
- WebSocket 경쟁이 꺼져 있어도 조회되는 것

캐시 적용 폴링은 같은 방식으로 다음을 확인합니다.
- 같은 DB 상태에서 기본 폴링과 같은 화면(`generatedAt` 제외)
- 여러 기기가 같은 공통 순위를 써도 각자의 `me`, `nearby`
- 유효시간 안에는 DB를 다시 조회하지 않고, 지나면 새로 조회하는 것(저장소 호출 횟수로 확인)
- 유효시간이 지난 뒤 활동 인원 감소, KST 날짜 전환 시 다시 조회, 빈 날짜
- 비어 있을 때 동시에 들어온 요청이 DB를 한 번만 조회하는 것

정확히 5초 경계, 공개 ID 정렬, 주변과 100명 경계는 도메인 단위 테스트로 확인합니다.
실제 앱 표시, 화면 반영 지연, 부하는 이 검증에 포함되지 않습니다.
