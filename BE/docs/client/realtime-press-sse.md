# 실시간 프레스 SSE 구독 연동

관련 이슈: [#1102](https://github.com/woowacourse-teams/2026-pheeeew/issues/1102), 전송 분리 [#1105](https://github.com/woowacourse-teams/2026-pheeeew/issues/1105).
앱이 연결 하나를 열어 두면 서버가 실시간 프레스 화면의 최신 상태를 SSE(Server-Sent Events)로 보내는 방식입니다.
이 문서는 BE의 계약과 앱 연동 방법을 설명합니다. 실제 앱 연동 검증 기록은 아닙니다.
사용할 수 있는 실시간 프레스 연동 목록은 [폴링 연동](realtime-press-polling.md#사용할-수-있는-실시간-프레스-연동)에 있습니다.

## 구독 요청

```http
GET /api/v1/press-race/stream?view=PRESS
Authorization: Bearer <access token>
Accept: text/event-stream
```

| 항목 | 규칙 |
| --- | --- |
| 인증 | `Authorization` 헤더의 기존 기기 access token. 쿼리의 토큰은 인증에 쓰지 않음 |
| `view` | 선택. `PRESS` 또는 `ALL`. 생략하면 `PRESS`. 그 밖의 값은 `400 COMMON-001` |
| 응답 헤더 | `Content-Type: text/event-stream`, `Cache-Control: no-cache`, `X-Accel-Buffering: no` |

입력은 기존 `POST /api/v2/emotions/presses`를 그대로 씁니다. 내 감정별 개수는 POST 응답으로 표시합니다.

## 이벤트

### `snapshot`

```text
event:snapshot
data:{"date":"2026-11-04","generatedAt":"2026-11-04T02:00:00.123Z","activeCount":7,"view":"PRESS","me":{...},"nearby":[...],"top100":[]}

```

- 데이터는 폴링 응답과 같은 JSON입니다. 필드 의미, 순위, 동점, 목록 경계는 [폴링 응답](realtime-press-polling.md#응답)과 같습니다.
- 구독 직후 현재 상태를 한 번 보냅니다. 이후에는 내 화면 상태가 바뀔 때만 보냅니다.
- `generatedAt`만 바뀐 경우는 보내지 않습니다. 날짜가 바뀌거나 활동 인원이 줄어든 것은 화면 변경이라 보냅니다.
- 받은 `snapshot`으로 화면 전체를 덮어씁니다. 이전 이벤트와 합치지 않습니다.
- 중간 클릭, 추월, 중간 상태를 하나씩 보내지 않습니다. 최신 상태만 보냅니다.

### heartbeat

```text
:heartbeat

```

- 15초마다 보내는 SSE 주석 줄입니다. 연결 유지용이며 화면에 반영하지 않습니다.
- 서버가 끊긴 연결을 알아채는 시점은 그 연결에 다음으로 보낼 때입니다. heartbeat 간격 안에 반드시 정리된다고 보장하지 않습니다.

### 종료

종료 이유를 알리는 이벤트는 없습니다. 토큰 만료, 서버 배포, 네트워크 종료, 전송 시간 초과 모두 연결이 닫히는 것으로 나타납니다.
서버가 종료될 때(배포 포함)는 웹 서버의 graceful 종료보다 먼저 모든 구독을 닫습니다.

## 갱신 주기와 지연

- 서버는 구독자가 있는 동안 1초마다 DB에서 공통 순위를 한 번 만들고, 구독마다 화면을 계산합니다. 1초는 실험용 초기값입니다.
- 커밋된 저장만 반영됩니다. 1초 안의 여러 입력은 최신 상태 하나로 전달됩니다.
- 다른 사람의 입력이 내 화면에 보이기까지 앱의 묶음 전송 대기, 발행 주기(1초), 그 주기의 공통 순위 생성과 전송 시간이 더해집니다. 이 방식의 실제 반영 지연은 측정하지 않았습니다.
- 최초 `snapshot`은 최대 1초 전에 만든 공통 순위일 수 있습니다. `generatedAt`은 연결 시각이 아니라 그 순위를 관찰한 시각입니다.
- 서버가 공통 순위를 만들지 못한 주기에는 화면을 보내지 않습니다. 오래된 순위를 최신처럼 보내지 않습니다.

## 전송 방식

앱에 보이는 계약(이벤트, 필드, 오류, 동시 구독 상한)은 전송 방식과 관계없이 같습니다. 앱은 경로나 요청을 바꾸지 않습니다.

기본은 분리 전송입니다.
- 서버는 주기마다 공통 순위를 만들고 구독별 대기에 넘깁니다. 전송이 끝나기를 기다리지 않습니다. 수신이 늦은 연결이 공통 순위 생성과 다른 연결의 전송을 붙잡지 않게 하려는 방식입니다.
- 구독별 대기는 최신 `snapshot` 하나와 heartbeat 하나까지입니다. 이전 전송이 끝나지 않았는데 새 상태가 나오면 대기 중인 이전 상태를 버리고 최신 상태로 바꿉니다. 앱은 다음에 받는 `snapshot`으로 최신 상태를 맞춥니다.
- 한 구독에는 한 번에 하나만 보냅니다.
- 한 번의 전송이 5초 이상 걸리면 서버가 그 구독을 닫습니다. 검사는 발행 주기마다 하고, 주기는 1초 간격에 공통 순위를 만드는 시간이 더해지므로 5초보다 조금 늦게 닫힐 수 있습니다. 앱에는 연결이 닫힌 것으로 나타나며, 연결이 닫혔을 때와 같은 방법으로 다시 구독합니다.
- 전송이 막혀 있는 연결은 서버가 닫기로 한 뒤에도 실제 연결 종료가 늦어질 수 있습니다. 즉시 끝나거나 정해진 시간 안에 정리된다고 보장하지 않습니다. 동시 구독 수는 닫기로 한 시점에 반납합니다.
- 막힌 전송은 실제로 끝날 때까지 전송 스레드 하나를 차지합니다. 동시에 막힌 연결이 전송 스레드 수(기본 4) 이상이면 다른 구독의 전송도 그동안 밀립니다.
- 서버 전체의 전송 작업이 밀려 있으면 그 주기의 전송을 다음 주기로 미룹니다. 연결은 닫지 않습니다.

비교를 위해 기존 차례 전송도 서버 설정으로 고를 수 있습니다. 차례 전송에서는 서버가 구독마다 차례로 보내므로, 수신이 늦은 연결이 같은 주기의 다른 연결로의 전송과 다음 주기를 늦출 수 있습니다.

| 서버 설정 | 기본값 | 의미 |
| --- | --- | --- |
| `pheeeew.press-race.stream.send-mode` | `ISOLATED` | `ISOLATED`(분리 전송) 또는 `SEQUENTIAL`(차례 전송) |
| `pheeeew.press-race.stream.send-threads` | `4` | 분리 전송의 전송 스레드 수 |
| `pheeeew.press-race.stream.send-queue-capacity` | `300` | 분리 전송의 실행 대기열 크기. 한 구독은 대기열에 최대 한 건만 올라감 |
| `pheeeew.press-race.stream.send-timeout-millis` | `5000` | 분리 전송에서 한 번의 전송 제한 시간 |

값은 실험용 초기값입니다. 비교는 같은 조건에서 설정만 바꿔 각각 실행합니다.

## 연결 유지 시간과 토큰

- 서버는 구독에 쓴 access token의 남은 수명이 지나면 연결을 닫습니다. 새 연결이라고 30분을 다시 주지 않습니다.
- 앱은 토큰 만료 시각을 기준으로 기존 HTTP 토큰 재발급을 한 번에 하나만 수행한 뒤, 새 `Authorization` 헤더로 다시 구독합니다.
- 만료가 임박한 토큰으로 구독하면 연결이 곧 닫힙니다. 만료가 가까우면 먼저 갱신한 뒤 구독합니다.

## 앱 연동 예시

```text
화면 진입 또는 포그라운드 복귀
  → GET /api/v1/press-race/stream?view=<현재 화면> 구독
  → 첫 snapshot 으로 화면 전체를 그린다
  → 이후 snapshot 마다 화면 전체를 덮어쓴다

화면 전환(PRESS ↔ ALL)
  → 기존 구독을 닫는다
  → 새 view 로 다시 구독한다 (첫 snapshot 으로 새 화면을 그린다)

감정 버튼 묶음 전송 성공
  → POST 응답의 counts 로 내 개수를 표시한다
  → 순위는 다음 snapshot 을 기다린다

연결이 닫힘 (토큰 만료, 배포, 네트워크)
  → 마지막 화면을 유지한다
  → 토큰이 만료됐거나 곧 만료되면 갱신한다
  → 대기 후 다시 구독한다. 첫 snapshot 으로 최신 상태를 복구한다

다른 탭, 백그라운드, 화면 이탈
  → 구독을 닫고 다시 열지 않는다
```

- 재연결 대기는 0.5초부터 최대 5초까지 늘리고 무작위 지연을 섞습니다.
- 끊긴 동안의 중간 상태는 재생하지 않습니다. 다시 구독해 받은 첫 `snapshot`이 최신 상태입니다.
- 클라이언트 HTTP 읽기 제한 시간은 heartbeat 15초보다 길게 둡니다(예: 30초 이상). 읽기 제한 시간 안에 아무것도 오지 않으면 끊긴 것으로 보고 다시 구독합니다.

## 동시 구독과 오류

- 같은 기기는 서버 한 대에서 최대 2개까지 동시에 구독할 수 있습니다. 화면 전환과 재연결이 잠시 겹치는 경우를 위한 여유입니다.
- 앱은 기존 구독을 닫은 뒤 새로 엽니다. 서버가 닫힌 연결을 알아채기 전에는 이전 구독이 수에 남아 있을 수 있습니다.
- 상한은 서버 한 대 기준이며 여러 서버 전체의 상한을 보장하지 않습니다.

| HTTP | 코드 | 처리 |
| --- | --- | --- |
| 400 | `COMMON-001` | 잘못된 `view`. 앱 구현 오류 |
| 401 | `AUTH-001` | 토큰 없음 또는 무효. 토큰 갱신 후 다시 구독 |
| 429 | `PRESS_STREAM-001` | 같은 기기의 동시 구독 수 초과. 기존 연결은 유지됨. 즉시 반복하지 않고 0.5초부터 최대 5초까지 대기 시간을 늘리며 무작위 지연을 섞어 재시도 |
| 5xx, 네트워크 오류 | - | 마지막 화면을 유지하고 재연결 대기 후 다시 구독 |

오류 본문은 `Accept: text/event-stream`으로 요청해도 공통 `ErrorResponse` JSON입니다.

```json
{"code": "PRESS_STREAM-001", "message": "같은 기기의 실시간 프레스 구독 수를 넘었습니다."}
```

## 프록시와 환경

- 응답의 `X-Accel-Buffering: no`로 nginx 버퍼링을 이 응답에서만 끕니다. 현재 nginx 설정에는 이 헤더를 무시하는 `proxy_ignore_headers`가 없습니다.
- nginx `proxy_read_timeout`은 60초이고 heartbeat 15초가 더 짧습니다.
- 다음은 아직 확인하지 않았습니다.
  - 실제 nginx를 거쳐 이벤트가 지연 없이 전달되는지
  - 운영 ALB의 실제 유휴 시간

## BE 검증의 범위

실제 PostgreSQL에서 발행기를 수동 주기로 돌려 다음을 확인합니다. 아래 항목은 차례 전송으로 확인합니다.
- 구독 직후 각 기기가 자기 화면의 현재 상태를 받는 것
- 최초 구독의 1초 이내 공통 순위 재사용, 동시 최초 구독의 공통 순위 생성 1회
- 커밋된 여러 입력이 다음 주기에 최신 상태 하나로 전달되는 것, 화면이 같으면 다시 보내지 않는 것
- 쓰기 없이 활동 인원이 줄어드는 것, 구독자 수와 무관한 주기당 생성 1회, 구독자가 없을 때 DB를 읽지 않는 것
- heartbeat 간격, 토큰 만료, 전송 실패 시 정리와 구독 수 반납, 세 번째 구독 거절, 공통 순위 생성 실패 시 화면 미전송
- 앱 시계의 날짜가 다르면 공통 순위를 새로 만드는 것, 서버가 멈출 때 모든 구독을 닫고 반납하는 것

분리 전송은 전송에서 멈추는 테스트용 수신자로 막힌 연결을 대신해 다음을 확인합니다. 실제 소켓의 송신 버퍼가 차는 상황은 자동 테스트에 넣지 않았습니다.
- 막힌 구독이 있어도 다른 구독이 최신 `snapshot`과 heartbeat를 받고, 발행기가 주기마다 공통 순위를 만드는 것
- 막힌 전송이 풀리면 중간 상태 없이 최신 상태와 heartbeat 하나를 받는 것, 한 구독 안의 전송이 동시에 진행되지 않는 것
- 전송 시간 초과, 전송 오류, 연결 종료, 토큰 만료 뒤 구독 수 반납과 추가 전송 없음, 막힌 전송이 끝난 뒤 연결 종료
- 실행기가 가득 찬 주기의 구독을 유지하고 다음 주기에 최신 상태를 보내는 것
- 서버가 멈출 때 막힌 전송을 기다리지 않고 모든 구독 수를 반납하며 막힌 연결은 전송이 끝난 뒤 닫는 것, 다시 시작하면 보내는 것, 기기별 화면과 heartbeat 간격

실제 서버(기본값인 분리 전송)를 띄워 SSE 헤더와 첫 `snapshot`, 401, 400, 429, 쿼리 토큰 거절, 토큰 남은 수명 경과 후 종료와 구독 수 반납을 확인합니다.
발행 경로의 날짜 전환은 DB 시각을 옮길 수 없어 화면 상태 비교 단위 테스트와 최초 구독의 날짜 조건으로 확인합니다. 실제 앱 표시, 프록시 경유 전달, 반영 지연, 부하는 이 검증에 포함되지 않습니다.
