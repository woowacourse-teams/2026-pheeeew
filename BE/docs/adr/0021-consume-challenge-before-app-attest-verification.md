# ADR-0021: iOS 는 App Attest 검증을 시작하기 전에 challenge 를 소모한다

## Status

Accepted (2026-09-13)

## Context

- App Attest 는 **서버가 애플에 아무것도 묻지 않아요.** 앱이 보낸 attestation 객체 안의 인증서 체인을 우리가 직접 검증해요. Play Integrity 가 구글을 부르는 것과 근본이 달라요.
- 그래서 ADR-0018 의 challenge 당 시도 상한과 ADR-0020 의 하루 예산은 **묶을 외부 호출이 없어요.** 그대로 옮기면 근거 없는 제한이 생기고, 예산을 넘기면 우리가 만든 장애만 남아요.
- ADR-0018 이 "소모 시점을 앞당기기" 를 버린 이유는 **구글 장애로도 challenge 가 사라진다** 였어요. 그 사유가 이 경로에는 성립하지 않아요.
- 공개 키를 저장하지 않기로 했으므로(#260) challenge 1회용이 iOS 경로의 **유일한 재생 방어**예요.

## Decision

challenge 를 인증서 체인 검증 앞에서 소모해요. 조건부 UPDATE 로 1행을 얻은 요청만 암호 연산으로 넘어가요. iOS 경로에는 시도 상한과 하루 예산을 두지 않아요.

## Alternatives

- 안드로이드처럼 검증 뒤에 소모 — 같은 challenge 로 체인 검증을 무한히 반복할 수 있어요. 애플은 호출 예산이 없어 그것을 막는 다른 장치도 없어요.
- 시도 상한 5를 그대로 적용 — challenge 하나당 암호 연산을 5회까지 허용해요. 조기 소모가 1회로 더 조여요. DB 쓰기도 최대 6건에서 1건으로 줄어요.
- 하루 예산을 함께 적용 — 소진될 외부 할당량이 없어서 막는 것이 없고, 넘기면 정상 등록만 막혀요.

## Consequences

- (+) challenge 하나당 인증서 체인 검증이 한 번이에요. 상한 장치를 따로 두지 않고도 상한이 생겨요.
- (+) 외부 호출이 없으므로 예산 소진으로 정상 등록이 막히는 장애가 iOS 에는 없어요.
- (-) **암호 검증에 실패하면 challenge 가 사라져요.** 체인 검증부터 뒤가 그래요. 앱 버그나 일시적 오류로 실패한 정상 사용자도 challenge 를 새로 받아야 해요. 안드로이드와 동작이 달라요.
- (-) **ADR-0016 Compliance 의 "거절 경로에서 challenge 가 소모되지 않는지 확인해요" 가 이 경로에서 성립하지 않아요.** 그 문장은 안드로이드 경로에 한정돼요.
- (=) 이 차이를 클라이언트가 알아야 해요. 등록 API 와 challenge 발급 API 문서에 소모 시점이 플랫폼마다 다르다는 것을 적었어요.
- 재검토: 정상 사용자의 실패율이 관측되면 다시 봐요. 실패가 잦으면 소모를 뒤로 옮기고 다른 상한 장치를 만들어야 해요.

## Compliance

- 소모 지점 앞에서 떨어진 요청(형식 오류, `keyId` 누락)은 challenge 를 소모하지 않는지 확인해요.
- 소모 지점 뒤에서 떨어진 요청의 challenge 가 다시 쓰이지 않는지 확인해요.
- iOS 경로가 예산 행과 시도 수를 건드리지 않는지 확인해요. **등록이 성공하는 경로까지 돌려서 확인해요.**
