# ADR-0026: 기기 활동을 비동기로 기록하고 로컬 캐시로 중복 저장 시도를 줄인다

## Status

Accepted (2026-09-17)

## Context

- 익명 기기를 기준으로 DAU와 MAU를 집계하려면 글을 작성하지 않고 조회만 하는 기기의 활동도 기록해야 해요.
- 같은 기기가 하루에 여러 번 요청해도 집계에는 KST 기준 기기별 일별 기록 한 건이면 충분해요. 매 요청마다 DB 저장을 시도할 필요는 없어요.
- 활동 통계 저장 실패 때문에 사용자의 조회나 작성 요청이 실패하거나 DB 저장을 기다리게 하고 싶지 않아요. 대신 일부 기록이 누락될 수 있다는 한계를 받아들여요.
- 현재 운영 대상은 서버 한 대예요. 서버 사이의 중복 제출을 조율하기 위한 별도 저장소는 두지 않아요.

## Decision

기기 활동은 전용 실행기의 비동기 작업과 독립된 트랜잭션으로 저장해요.
Caffeine 로컬 캐시로 같은 기기와 활동 날짜의 중복 제출을 줄이고, 집계의 원본은 DB의 `DeviceDailyActivity`로 유지해요.
유실 없는 기록보다 서비스 응답과 운영 단순성을 우선하며, 재시작이나 캐시 퇴출로 발생하는 중복 저장 시도는 DB의 유일성 제약과 `ON CONFLICT DO NOTHING`으로 처리해요.

## Alternatives

- 매 요청에서 동기 저장: 저장 완료를 확인할 수 있지만 DB 대기와 저장 실패가 사용자 요청 처리에 직접 연결돼요.
- Redis로 중복 제출 제어: 서버 사이에서 표식을 공유할 수 있지만 별도 저장소 운영이 필요해요. 중복 제어만으로 비동기 대기 작업의 유실까지 해결되지는 않아요.
- 직접 만든 메모리 캐시: 동시 접근, 만료와 크기 제한을 직접 유지해야 해요. 이 관리는 Caffeine에 맡겨요.

## Consequences

- (+) 같은 기기와 날짜의 대기 중인 작업도 캐시로 합쳐요. 저장 성공 시 표식을 유지하고, 저장 실패나 제출 거절 시 해당 표식만 제거해 다음 활동에서 재시도할 수 있게 해요.
- (+) 재배포로 캐시가 비어도 이미 저장한 DB 기록은 남아요. 다음 요청에서 저장을 다시 시도할 수 있지만 같은 기기와 날짜의 행이 중복으로 생기지는 않아요.
- (-) 캐시와 작업 큐는 서버 메모리에만 있어요. 종료 시 아직 커밋되지 않은 활동은 유실될 수 있고, 해당 기기의 같은 날 후속 활동이 없으면 DAU와 MAU가 실제보다 작아질 수 있어요.
- (-) 정상 종료에서는 받은 작업의 완료를 최대 5초 기다려요. 이 시간이 모든 작업의 완료를 보장하지는 않으며, 강제 종료 때는 대기 작업을 복구하지 못해요.
- (=) 동시 실행 1개와 대기 256개로 부하를 제한해요. 제출이 거절되면 요청 스레드에서 대신 실행하지 않아요. DB 트랜잭션은 `REQUIRES_NEW`, 제한 시간은 3초이며 DB 연결 풀 등 자원은 서비스와 공유해요.
- (=) 캐시의 최대 크기 정책은 10,000개예요. 표식 생성 시 다음 KST 자정까지의 만료 시간을 정하고 중복 요청으로 연장하지 않아요. 만료나 크기 제한에 따른 퇴출도 추가 저장 시도를 만들 수 있어요.
- (=) 처리한 저장 실패와 제출 거절은 원인별 카운터에 모두 반영하고, 기기 식별자와 예외 원문을 제외한 한글 오류 로그는 인스턴스당 최대 분당 한 번 남겨요. 갑작스러운 프로세스 종료로 유실된 작업 수까지 파악할 수는 없어요.
- (=) 운영 프로필의 HTTP 필터에서 인증된 기기의 대상 서비스 요청이 2xx로 끝나면 기록해요. 빈 목록을 포함한 정상 조회도 활동이며, 인증 정보 전체 대신 기기 식별자와 요청 시각만 비동기 작업에 전달해요. 활동 날짜는 저장 완료 시각이 아니라 복사한 요청 시각의 KST 날짜예요.
- (=) DB의 일별 활동 원본은 자동 삭제하지 않아요. MAU의 최근 30일 조회 범위는 보관 기한이 아니에요. 실제 저장 용량과 집계 비용을 관찰한 뒤 보관 정책을 재검토해요.
- 재검토: 기록 누락이 제품 판단에 영향을 주거나 유실 없는 통계가 필요해지면, 실패율과 DB 부하를 확인하고 작업의 영속 보관과 재처리를 검토해요.

## Compliance

- PostgreSQL 17 / PostGIS 3.5 통합 테스트로 KST 날짜 경계, 중복 및 동시 저장, 요청 트랜잭션과의 분리를 검증했어요. 캐시 테스트로 동시 중복 제출, 만료, 크기 제한, 이전 작업의 실패가 새 표식을 지우지 않는지 검증했어요.
- HTTP 필터 테스트로 인증된 정상 조회·쓰기의 활동 인정과 비대상·실패 요청의 제외를 검증했어요. 실행기 포화와 저장 실패가 호출자에게 전파되지 않는지, 실패 후 재시도와 오류 로그의 식별자 제외가 유지되는지도 검증했어요.
- Alloy의 활동 지표 허용 목록과 실제 로그 필터를 로컬에서 검증했어요. [DB 비용 측정](../../docker/benchmarks/README.md)과 [지표·대시보드 안내](../../docker/grafana/README.md)에 측정 조건과 운영 확인 항목을 남겼어요.
- `Accepted`는 이 방식을 채택했다는 뜻이며 배포 완료를 뜻하지 않아요. 운영 배포 후 Grafana Cloud의 실제 지표·로그 수신, 대시보드 표시, 알림 적용과 사용량 확인은 남아 있어요.
