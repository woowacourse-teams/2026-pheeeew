# ADR-0024: 차단 필터를 `NOT EXISTS` 로 쓴다

## Status

Accepted (2026-09-14)

## Context

- `sighs.device_id` 가 `NULL` 을 허용해요(ADR-0023). 기존 한숨과 v1 로 들어온 한숨이 전부 `NULL` 이에요.
- SQL 에서 `device_id NOT IN (차단 목록)` 은 `device_id` 가 `NULL` 이면 `NULL` 로 평가돼요. 참이 아니므로 **그 행이 결과에서 빠져요.** 작성자를 모르는 한숨이 전부 지도에서 사라져요.
- `device_id IS NULL OR device_id NOT IN (...)` 은 동작이 맞아요. 다만 **그 `OR` 한 조각을 지우면 조용히 깨져요.** 프로덕션 코드에 주석을 쓰지 않기로 해서 "지우지 마세요" 를 코드에 남길 수도 없어요.
- 차단 목록이 비어 있으면 `NULL NOT IN (빈 집합)` 이 참이라 **회귀 테스트가 통과해버려요.** 실측으로 확인했어요.

## Decision

차단 필터를 `NOT EXISTS` 서브쿼리로 써요. 지도 조회와 목록 조회의 한숨 차단, 사용자 차단 네 술어 모두에 적용해요.

## Alternatives

- `NOT IN` — 위 이유로 쓰지 않아요. nullable 컬럼에서는 플래너가 안티조인으로 바꾸지도 못해요.
- `IS NULL OR NOT IN` — 동작은 맞지만 안전성이 사람의 주의력에 걸려 있어요. `NOT EXISTS` 는 같은 안전성이 구조에서 나와요.
- 애플리케이션에서 거르기 — 500건 상한 뒤에 거르면 결과 수가 들쭉날쭉해지고 커서 페이징이 깨져요.

## Consequences

- (+) `NULL` 안전성을 지울 수 없어요. 술어를 통째로 지우지 않는 한 깨지지 않아요.
- (+) 두 차단 테이블의 UNIQUE 제약이 그대로 접근 경로라 **새 인덱스가 필요 없어요.**
- (-) 술어가 넷으로 늘어 조회 SQL 이 길어져요.
- (=) **실행 계획을 자동 테스트로 고정하지 않아요.** 테스트 데이터 규모에서는 플래너가 정당하게 순차 탐색을 골라서, 강제로 끄고 단언하면 아무것도 검증하지 못해요. 20만 건을 넣고 사람이 `EXPLAIN (ANALYZE, BUFFERS)` 로 확인해요.
- (=) 실행 계획에 `Filter: (NOT (hashed SubPlan N))` 이 보이면 누군가 `NOT IN` 으로 되돌린 거예요.
- 재검토: 차단 목록이 한 기기당 수천 건으로 커지거나 지도 조회가 느려지면 실행 계획을 다시 봐요.

## Compliance

- 작성자를 모르는 한숨이 결과에 남는지 확인해요. **두 차단 테이블 양쪽에 행이 있는 상태에서, 두 술어를 각각 따로 켠 조합을 전부 만들어요.**
- 지도와 목록을 따로 확인해요. 목록은 필터가 CTE 안에 있어 지도 테스트가 대신하지 못해요.
- `NOT IN` 으로 바꾸면 그 테스트가 실제로 깨지는지 확인해요.
