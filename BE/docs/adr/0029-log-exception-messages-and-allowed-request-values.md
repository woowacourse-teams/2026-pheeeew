# ADR-0029: 서버 오류 로그에 예외 메시지와 허용한 요청 값을 남긴다

## Status

Proposed (2026-10-04)

[ADR-0012](0012-limit-exported-http-logs-and-use-aggregate-metrics.md)가 정한 로그 필드 범위를 바꾸는 제안이에요. 팀 검토를 위해 기록해요. 로컬 검증을 마쳤으며 배포 후 실제 로그는 아직 확인하지 않았어요.

## Context

- ADR-0012는 외부로 전송하는 오류 로그에서 요청 원문, 좌표, 인증 정보, 예외 메시지를 제외했어요. 로그에는 경로 템플릿, 상태 코드, 처리 시간, 추적 번호, 예외 종류와 위치가 남았어요.
- 2026-09-30 운영에서 `GET /api/v2/groups`가 500을 27건 반환했어요. 스택으로 `Enum.valueOf`와 `GroupService.findMine`까지는 알 수 있었지만 어떤 값이 원인인지는 로그에 없었어요.
- 경로 템플릿에는 리소스 식별자가 없어요. `/api/v2/groups/{groupId}`에서 실패해도 어느 그룹인지 로그로 알 수 없어요.
- 예외 메시지에는 값이 섞일 수 있어요. 로컬 PostgreSQL 17과 현재 드라이버(42.7.11)에서 NOT NULL 위반 메시지에는 실패한 행 전체가, UNIQUE 위반 메시지에는 키 값이 들어가는 것을 확인했어요. 이 서비스에는 메모와 위치를 담는 테이블이 있어요.
- 운영 콘솔 로그는 파일과 같은 JSON이에요. 배포가 실패하면 워크플로가 컨테이너 로그 마지막 100줄을 공개 저장소의 Actions 로그에 출력해요.

## Decision

서버 오류(5xx) 로그와 예약 작업 실패 로그에 예외 메시지를 남기고, 서버 오류 로그에는 허용 목록에 있는 이름과 형식의 경로 변수, 쿼리 값도 남겨요. 원인 사슬에 DB 예외가 있으면 메시지를 모두 버리고 SQL 상태 코드만 남겨요. 어떤 값 때문에 실패했는지 로그 한 줄로 알 수 있어야 원인을 찾고 재현할 수 있어서, 값이 섞이는 것을 확인한 DB 메시지만 막고 나머지 메시지의 위험은 받아들였어요.

## Alternatives

- 예외 메시지 제외 유지: 값이 원인인 오류마다 운영 데이터를 직접 확인해야 해서 선택하지 않았어요.
- 서버에만 남는 상세 로그를 따로 두고 예외 메시지와 요청자 해시를 거기에 기록: 요청 본문 값 추출과 함께 구현한 뒤 걷어냈어요. 로깅 코드가 163줄에서 599줄로 늘었고, 배포 실패 시 콘솔 출력이 Actions 로그로 나가는 것처럼 서버 밖으로 새는 경로를 하나씩 막아야 했어요. 요청자나 본문 값이 필요했던 사례도 아직 없었어요.
- 전부 기록한 뒤 민감한 값을 가리기: 새 필드에서 가리기를 빠뜨리면 그대로 전송돼서, 허용한 값만 남기는 방식을 유지했어요.

## Consequences

- (+) 로그 한 줄에서 예외 종류, 우리 코드의 발생 위치, 메시지, 대상 리소스를 함께 확인해요. 오류 로그를 조회하는 곳은 지금처럼 Cloud 한 곳이에요.
- (-) 예외 메시지는 형식이 정해져 있지 않아요. 라이브러리나 새 코드가 메시지에 요청 값을 넣으면 그 값이 Cloud로 전송돼요. 지금 우리 코드가 메시지에 변수를 넣는 곳은 6곳이고 값은 설정 이름, 상수, 외부 응답 상태 코드예요.
- (-) DB가 원인이면 메시지 없이 SQL 상태 코드, 예외 종류, 발생 위치만 남아요. 어느 제약의 어떤 값인지는 여전히 로그로 알 수 없어요.
- (-) 요청 본문과 요청자는 남기지 않아요. 요청자에 따라 결과가 달라지는 조회는 메시지에 단서가 없으면 로그만으로 재현할 수 없어요.
- (=) 예외 메시지에 사용자 입력, 위치, 식별자를 넣지 않는지, 허용 목록에 추가하는 값이 그것만으로 사람이나 위치를 드러내지 않는지 리뷰에서 확인해야 해요.
- (=) 잘못된 요청에 스프링과 톰캣이 던지는 예외 중에는 메시지에 요청 값을 담는 것이 있어요. 지원하지 않는 Content-Type, 해석할 수 없는 Accept 헤더와 쿼리 문자열에서 확인했어요. 확인한 경우는 4xx로 응답해 오류 로그를 남기지 않고, 쓰지 않는 multipart 해석과 폼 본문 필터는 껐어요. 같은 종류의 예외가 500으로 응답되는 것이 새로 보이면 4xx로 옮겨야 해요.
- (=) 배포 실패 시 워크플로가 출력하는 컨테이너 로그에서 두 오류 이벤트의 줄을 제외해요. 로그를 만들다 실패하면 응답과 예약 작업은 그대로 두고 건너뛰었다는 경고만 남겨요.
- 재검토: 예외 메시지로 민감한 값이 전송된 사례가 생기거나, 요청자나 본문 값이 없어 재현하지 못한 사례가 생기면 필드 범위를 다시 판단해요.

## Compliance

- 요청 로깅, 예외 형식, 예약 작업 오류 처리 테스트로 허용한 이름과 형식의 값만 남는지, 요청 본문으로 온 값은 남지 않는지, DB가 원인이면 감싼 예외의 메시지까지 버리고 SQL 상태만 남는지, 로그 생성이 실패해도 응답과 다음 예약 실행이 이어지는지 확인해요.
- 공통 웹 계약 테스트로 지원하지 않는 Content-Type과 메서드, 필수 쿼리 값 누락, 해석할 수 없는 Accept 헤더, 톰캣이 쿼리 문자열을 해석하지 못해 던지는 예외가 4xx로 응답하는지 확인하고, 요청 로깅 테스트로 지원하지 않는 Content-Type 요청이 오류 로그를 남기지 않는지 확인해요. multipart와 폼 본문 설정은 자동 테스트 없이 실제 톰캣에 요청을 보내 확인했어요.
- Alloy 로컬 검증으로 허용한 로거와 이벤트만 전송되는지 확인해요. 허용 규칙은 [Alloy 연결 안내](../../docker/alloy/README.md)에 있어요.
