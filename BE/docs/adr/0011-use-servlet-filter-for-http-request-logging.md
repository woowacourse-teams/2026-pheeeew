# ADR-0011: HTTP 요청 로그와 추적 문맥을 Servlet Filter에서 처리한다

## Status

Proposed (2026-09-11)

현재 모니터링 브랜치에 구현한 방식을 팀 검토를 위해 기록해요.

## Context

- 운영에서 실패하거나 느린 HTTP 요청을 찾고, 같은 요청에서 발생한 로그를 추적할 번호가 필요해요.
- 현재 애플리케이션은 동기 Spring MVC를 사용하고, 공통 예외 처리기가 예외를 HTTP 오류 응답으로 변환해요.
- 관찰하려는 범위에는 Controller 메서드뿐 아니라 요청 변환·검증과 응답 직렬화도 포함돼요.
- MDC는 현재 스레드에 연결되므로 요청 처리가 끝나면 추적 번호를 정리해야 다음 요청에 섞이지 않아요.

## Decision

Servlet Filter 기반의 요청 로깅 필터에서 후속 필터와 동기 MVC 처리를 감싸요. 처리 전에 `correlationId`를 MDC와 응답 헤더에 설정하고, 처리가 끝나면 상태 코드와 경과 시간을 바탕으로 로그를 남긴 뒤 이전 MDC 값을 복원하거나 제거해요. 예외 처리기가 이미 처리한 서버 오류는 요청 속성으로 전달받아 같은 위치에서 기록해요.

이 결정은 HTTP 요청 처리 범위의 로깅에 적용해요. 특정 메서드의 실행 시간과 결과를 계측하는 AOP는 별도로 사용할 수 있으며, 현재 지도 조회 지표는 이 방식으로 기록해요.

## Alternatives

- Controller AOP — 메서드 실행 전후 로깅에는 적합하지만, 요청 변환·검증은 메서드 호출 전에, 응답 직렬화는 반환 후에 일어나므로 원하는 HTTP 처리 범위와 달라요. 예외가 메서드 밖의 예외 처리기에서 어떤 응답으로 바뀌었는지도 해당 메서드의 advice만으로 확인하기 어려워 선택하지 않았어요.

## Consequences

- (+) Controller마다 로깅 코드를 넣지 않고 요청 추적 번호의 설정·정리와 HTTP 결과 기록을 한 흐름에서 관리해요.
- (+) 예외 처리기가 응답으로 변환한 서버 오류와 필터까지 전파된 예외를 같은 HTTP 로그 경로에서 다뤄요.
- (-) 예외 처리기와 로그 기록 코드가 오류 정보를 주고받는 요청 속성 계약을 유지해야 해요.
- (-) 측정 범위는 이 필터 이후의 처리예요. 앞선 필터, 프록시·네트워크 시간과 클라이언트가 응답을 모두 받은 시점은 포함하지 않아요.
- (=) 필터 밖으로 전파된 예외는 로그에서 500으로 분류하지만, 컨테이너가 나중에 확정하는 실제 응답 상태까지 관찰하는 것은 아니에요.
- (=) 이 결정은 앱이 직접 남기는 HTTP 로그에 적용해요. 컨테이너·라이브러리의 별도 오류 로그까지 중복이나 개인정보 제외를 보장하지 않아요.
- 재검토: 비동기 MVC, 스트리밍, 별도 스레드·큐를 도입하거나 tracing 계측이 같은 추적·로깅 책임을 맡게 되면 완료 시점과 문맥 전달 방식을 다시 판단해요.

## Compliance

- 요청 로깅 테스트에서 추적 번호 생성·MDC 복원, 처리된 오류와 전파된 예외, 느린 요청의 경계와 중복 기록 방지, HTTP 로그의 개인정보 제외를 확인해요.
- 공통 오류 응답 계약 테스트에서 기존 오류 응답의 상태 코드와 본문 계약을 유지하는지 확인해요.
