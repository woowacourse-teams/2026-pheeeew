# ADR-0016: challenge 소모를 조건부 UPDATE 의 영향 행 수로 판정한다

## Status

Accepted (2026-09-13)

## Context

- 무결성 증명의 재생 공격을 막으려면 서버가 발급한 값이 증명 안에 박혀 있어야 하고, 그 값이 1회용이어야 해요. 정상 기기에서 받은 증명을 저장해두고 계속 재사용할 수 있기 때문이에요.
- 상태 비저장 방식으로는 1회용을 보장할 수 없어요. HMAC 으로 서명한 값은 만료까지 몇 번이든 다시 쓸 수 있어요.
- 조회한 뒤 변경하는 방식은 조회와 변경 사이에 틈이 생겨 동시 요청에서 같은 값이 두 번 소모돼요.
- 인접한 기기 등록 경로가 ADR-0004 의 무트랜잭션 예외를 적용받고 있어요. 그 예외가 이 경로에도 번지는지 판단이 필요했어요.

## Decision

challenge 를 테이블에 저장하고, 소모 조건 세 개를 한 UPDATE 문에 담아 영향 행 수로 판정해요. 1행이면 내가 소모한 것이고 0행이면 거절해요.

```sql
UPDATE device_challenges SET consumed_at = ?
WHERE challenge = ? AND consumed_at IS NULL AND expires_at > ?
```

## Alternatives

- HMAC 으로 서명한 상태 비저장 challenge — 저장소가 필요 없지만 재사용을 막지 못해 선택하지 않았어요.
- 조회한 뒤 변경 — 동시 요청에서 같은 값이 두 번 소모돼요.
- 도메인에 `isConsumable()` 판정 메서드를 두기 — 막으려던 조회 후 변경을 그 메서드가 유도해서 두지 않았어요.

## Consequences

- (+) 동시 N건에서 정확히 1건만 성공해요. 실측으로 확인했어요.
- (+) 판정자가 하나뿐이라 조회와 변경이 갈라질 자리가 없어요.
- (-) 저장소가 필요해요. 테이블이 하나 늘고 정리 스케줄러도 필요해요.
- (=) **이 경로는 컨벤션 3장대로 트랜잭션을 둬요.** ADR-0004 가 무트랜잭션 예외를 멱등 저장 경로에만 적용한다고 이미 범위를 잘라 두었고, challenge 소모는 그 경로가 아니에요. 두 장치의 성질도 반대예요 — 멱등 저장은 같은 키가 수렴하게 만들고(삽입 실패 후 재조회로 같은 결과에 도달, 오염된 영속성 컨텍스트 때문에 트랜잭션 불가), challenge 소모는 갈라지게 만들어요(한 건만 통과, 예외 없음).
- (=) 정리 스케줄러는 청소가 아니라 용량 상한 장치예요. TTL 5분에 주기 5분이면 테이블이 누적 트래픽이 아니라 발급률 기준으로 수렴해요.
- (=) 사전 조회는 읽기 전용이라 아무것도 소모하지 않아요. 그래서 복호화가 실패하면 challenge 가 남고, 같은 challenge 로 구글 호출을 반복할 수 있어요. 등록 엔드포인트의 요청 수 제한이 별도로 필요해요.
- 재검토: 발급률이 테이블 부담이 될 만큼 오르면 저장소를 다시 보거나 발급 자체에 제한을 둬요.

## Compliance

- 동시 요청에서 정확히 한 건만 소모되는지 통합 테스트로 확인해요.
- 만료 경계 앞뒤에서 결과가 갈리는지 확인해요.
- 없음, 만료, 이미 소모를 같은 오류 코드로 응답하는지 확인해요. 구분하면 존재 여부 오라클이 돼요.
- 거절 경로에서 challenge 가 소모되지 않는지 확인해요.
