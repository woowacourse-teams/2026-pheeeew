# ADR-0010: 운영 모니터링에 Alloy와 Grafana Cloud를 사용한다

## Status

Proposed (2026-09-11)

현재 모니터링 브랜치에 구현한 구성을 팀 검토를 위해 기록해요. 로컬 검증을 마쳤으며 운영 배포와 실제 Cloud 수신은 아직 확인하지 않았어요.

## Context

- 운영 앱은 EC2 한 대에서 실행하며, 운영 DB는 RDS를 사용해요. 초기 모니터링 대상은 운영 앱의 지표와 로그예요.
- 운영 EC2의 자원이 제한적이고, 모니터링 전용 EC2를 추가하는 비용과 관리 부담도 줄이려 해요.
- HTTP 요청과 지도 조회의 요청량·지연·오류를 관찰하고, 문제가 생긴 요청의 로그를 조회할 필요가 있어요.
- 지표·로그 저장소를 직접 운영하면 수집 외에도 저장 용량, 보관 정책, 업그레이드와 장애 복구를 관리해야 해요.

## Decision

운영 EC2에서 앱과 별도 Alloy 컨테이너를 실행하고, 지표·로그 저장과 조회는 Grafana Cloud를 사용해요. Alloy는 Docker 내부에서 앱 지표와 공유 볼륨의 로그를 읽고 외부 HTTPS로 전송하며, 모니터링 전용 EC2나 자체 Prometheus·Loki 저장소는 추가하지 않아요.

## Alternatives

- 운영 EC2에 Prometheus·Loki를 함께 운영 — 저장소까지 직접 통제할 수 있지만 앱과 CPU·메모리·디스크를 경쟁하고 저장소 운영 책임이 늘어 선택하지 않았어요.
- 별도 모니터링 EC2에서 저장소 운영 — 앱 자원과 분리할 수 있지만 인스턴스 비용과 관리 대상이 늘어 초기 구성에서는 선택하지 않았어요.
- CloudWatch 추가 연동 — EC2·RDS 내부 지표를 보완할 수 있지만 초기 설정과 비용 관리 범위가 넓어져 보류했어요. 현재 앱 지표가 그 관측 범위를 대신한다는 뜻은 아니에요.

## Consequences

- (+) 지표·로그 저장소를 직접 운영하는 부담을 줄이고, 앱이 제공하는 데이터를 한 화면에서 조회할 수 있어요.
- (+) 수집은 Docker 내부에서, 전송은 외부 HTTPS로 처리하므로 공개 관리 포트나 기존 Cloudflare SSH 터널의 변경이 필요하지 않아요.
- (-) Grafana Cloud와 외부 네트워크에 의존하며, 사용량·요금제 한도에 맞춰 전송량을 관리해야 해요.
- (-) Alloy도 운영 EC2 자원을 사용해요. EC2가 멈추면 수집기도 함께 멈추고, 장시간 전송 장애나 강제 종료 시 일부 데이터가 유실될 수 있어요.
- (=) 초기 범위에는 EC2 전체 자원·CPU 크레딧, RDS 내부 상태, 외부 URL 가용성, traces·profiles가 포함되지 않아요. 운영 자원 여유는 배포 전후에, 실제 수신과 사용량은 배포 후에 별도로 확인해야 해요.
- 재검토: 수집기가 앱에 부담을 주거나, 비용·보관·데이터 위치 요구가 달라지거나, 앱 지표만으로 장애를 설명하기 어려워지면 수집 범위와 저장소 운영 방식을 다시 판단해요.

## Compliance

- 로컬에서 Alloy의 지표·로그 전송, 자원 제한 아래 기동, 정상 재시작과 로그 회전 처리를 확인했어요. 실제 운영 인증·수신과 장애 복구 범위 전체를 검증한 것은 아니에요.
- 구체적인 수집 설정과 운영 연결·보관 한계는 [Alloy 연결 안내](../../docker/alloy/README.md)에서 관리해요.
