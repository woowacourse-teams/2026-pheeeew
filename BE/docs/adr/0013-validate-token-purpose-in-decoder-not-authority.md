# ADR-0013: 토큰 용도를 권한이 아니라 디코딩 단계에서 검증한다

## Status

Accepted (2026-09-11)

## Context

- access token에 용도를 나타내는 `use` 클레임을 넣었어요(ADR-0007). 다른 용도로 발급한 토큰이 리소스 서버 경로를 통과하면 안 돼요.
- 이전 프로젝트는 용도를 Spring Security 권한으로 바꾸고 경로마다 `hasAuthority`로 검사했어요. 거기는 회원가입용과 접근용 두 가지가 있어서 용도에 따라 열리는 경로가 달랐어요.
- 피유는 용도가 하나뿐이에요. 모든 인증 경로가 같은 용도를 요구해요.
- 이슈 #258이 정한 오류 규칙은 토큰이 유효하지 않으면 `401`이에요.

## Decision

`OAuth2TokenValidator`를 `JwtDecoder`에 붙여 디코딩 단계에서 `use`와 `sub`를 검사해요. 용도를 권한으로 변환하지 않고, `JwtAuthenticationConverter`도 만들지 않아요.

## Alternatives

- 용도를 권한으로 변환하고 경로마다 `hasAuthority`로 검사 — 용도가 하나뿐이라 모든 규칙에 같은 문자열이 붙어 잡음만 늘어요. 결정적으로 **용도가 다른 토큰이 `401`이 아니라 `403`으로 나가요.** 토큰 자체가 이 서버에서 쓸 수 없는 것인데 권한 부족으로 보고하는 셈이라 이슈가 정한 오류 규칙과 어긋나서 선택하지 않았어요.
- 컨트롤러나 서비스에서 용도를 확인 — 확인을 빠뜨린 경로가 그대로 열려요. 인증 경계 밖으로 검사를 내보내지 않으려고 선택하지 않았어요.

## Consequences

- (+) 용도가 다른 토큰이 `401`로 나가요. 인가 규칙은 경로와 메서드만 다뤄요.
- (+) 검사를 빠뜨릴 수 있는 자리가 없어요. 디코딩을 거치지 않고 통과하는 경로가 없기 때문이에요.
- (-) **두 번째 용도가 생기면 이 결정을 다시 봐야 해요.** 같은 키로 발급한 다른 용도의 토큰은 리소스 서버 경로에서 디코딩 자체가 막혀요. 용도별로 열리는 경로를 다르게 하려면 권한 방식으로 바꾸거나 디코더를 나눠야 해요.
- (=) `sub`가 UUID 형식인지도 같은 자리에서 검사해요. 형식이 깨진 토큰이 `ArgumentResolver`까지 가지 않아요.
- 재검토: 용도가 둘 이상 필요해질 때 다시 판단해요. 무결성 증명(#259, #260)이나 차단(#262)이 별도 용도의 토큰을 요구하면 그 시점이에요.

## Compliance

- 용도가 다른 토큰이 `403`이 아니라 `401`로 나가는지 통합 테스트로 확인해요.
- `sub`가 UUID가 아닌 토큰이 거부되는지 확인해요.
