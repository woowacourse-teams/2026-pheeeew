# ADR-0019: 서비스 계정 `token_uri` 를 HTTPS 와 루프백 리터럴로만 허용한다

## Status

Accepted (2026-09-13)

## Context

- 구글 access token 을 받으려면 서비스 계정 개인키로 서명한 assertion 을 토큰 엔드포인트로 보내요. 그 주소는 서비스 계정 JSON 의 `token_uri` 에서 읽어요(ADR-0014).
- 그 값을 그대로 쓰면 JSON 이 바뀌었을 때 **우리가 서명한 assertion 이 임의의 주소로 나가요.** assertion 의 `aud` 가 `token_uri` 자신이라 받은 쪽이 그것을 구글에 다시 낼 수는 없지만, 서명된 값이 우리가 의도하지 않은 곳으로 흘러가는 것 자체가 막을 이유예요.
- 테스트는 구글을 부를 수 없어서 `127.0.0.1` 에 가짜 토큰 엔드포인트를 띄우고 `http` 로 붙어요.
- 프로파일로 검증을 끄는 방식은 쓰지 않기로 했어요. 우회 스위치 자체가 또 하나의 구멍이 돼요.

## Decision

계층적 절대 URI 이고 스킴과 호스트가 있으며 userinfo 가 없는 값만 받아요. `https` 는 그대로 허용하고, `http` 는 **루프백 리터럴**(`127.0.0.0/8`, `[::1]`)일 때만 허용해요. `localhost` 같은 이름은 허용하지 않아요.

## Alternatives

- 호스트를 구글 도메인으로 고정 — 가장 좁지만 테스트가 가짜 엔드포인트를 쓸 수 없어요. 검증을 끄는 스위치를 만들면 그것이 구멍이 돼요.
- `localhost` 도 허용 — 이름 해석이 판정에 끼면 **검사 시점과 접속 시점 사이에 해석 결과가 달라질 수 있어요.** 검사에서는 루프백으로 보이고 접속에서는 외부로 나가는 재바인딩이 성립해서 선택하지 않았어요.
- 검증하지 않기 — 현행이었고, 위 유출 경로가 열려 있어요.

## Consequences

- (+) 평문 `http` 목적지로는 assertion 이 나가지 못해요. 중간에서 읽히는 경로가 막혀요.
- (+) 테스트가 프로파일 우회 없이 그대로 동작해요. 루프백 목적지는 호스트 밖으로 나가지 않으므로, assertion 을 받을 수 있는 주체는 이미 서비스 계정 파일을 읽을 수 있는 쪽이에요.
- (-) **`https` 목적지의 호스트는 검사하지 않아요.** 변조된 JSON 이 `https://evil.example.com` 을 넣으면 assertion 이 그리로 갑니다. 이 결정은 그것을 막지 못해요.
- (-) 같은 호스트 안에서 듣는 프로세스가 있으면 루프백 목적지의 assertion 을 받을 수 있어요.
- (=) `localhost` 를 쓰는 설정은 거부돼요. 루프백을 쓰려면 리터럴로 적어야 해요. 이름을 막은 이유가 코드 모양만으로는 드러나지 않아요.
- 재검토: 테스트가 구글 도메인을 그대로 쓸 수 있게 되면 호스트 고정으로 좁혀요.

## Compliance

- `https` 통과, 외부 `http` 거절, `localhost` 거절, userinfo 포함 거절, 상대 URI 거절을 테스트로 고정해요.
- 가짜 토큰 엔드포인트가 `127.0.0.1` 로 통과하는지 확인해요.
