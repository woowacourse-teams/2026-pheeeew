# ADR-0007: 기기 인증에 서명한 access token과 저장한 refresh token을 나눠 쓴다

## Status

Accepted (2026-09-10)

## Context

- 신고 API가 요청 본문으로 받은 `deviceId`를 그대로 믿어요. 값을 바꿔 보내면 다른 기기를 사칭할 수 있고 중복 신고 방지도 뚫려요.
- 한숨 차단 기능은 차단 목록이 기기마다 다르므로, 요청을 보낸 쪽이 진짜 그 기기인지 서버가 확신할 수 있어야 해요.
- 익명 앱이라 계정이 없어요. 앱이 자격증명을 잃으면 되찾을 수단이 하나도 없어요. 이전 프로젝트에는 소셜 로그인이 있어 다시 로그인하면 복구됐지만 여기는 그 경로가 없어요.
- 자격증명은 나가는 빈도가 다르면 위험도 달라요. 매 요청에 실리는 값과 재발급 때만 나오는 값을 같은 수명으로 둘 이유가 없어요.

## Decision

access token은 RS256으로 서명한 JWT로 발급하고 서버에 저장하지 않아요. 수명은 30분이고 `sub`에는 순번 기본 키가 아니라 `devices.public_id`를 넣어요.

refresh token은 무작위 값으로 발급해 SHA-256 해시만 저장해요. 만료를 두지 않고 회전하지도 않으며, 폐기로만 통제해요.

## Alternatives

- access token을 opaque 값으로 두고 매 요청 조회 — 즉시 폐기가 가능하지만 인증마다 DB를 봐야 해요. 30분이면 폐기가 늦는 문제가 대부분 사라져서 선택하지 않았어요.
- refresh token을 Redis에 저장 — 이전 프로젝트가 쓰던 방식이에요. 피유에 Redis가 없고, 휘발되면 전원이 재등록해야 하는데 복구할 로그인이 없어서 선택하지 않았어요.
- refresh token 회전 — 재사용을 탐지할 수 있지만, 재발급 응답을 놓친 앱이 영구 로그아웃돼요. 복구 수단이 없어서 선택하지 않았어요.
- refresh token에 만료 두기 — 쓸 때마다 연장하면 도난 토큰의 수명을 줄이지 못하고, 연장하지 않으면 오래 앱을 열지 않은 사용자를 잘라요. 실질 효과가 휴면 정리뿐이라 선택하지 않았어요.
- `sub`에 순번 기본 키 넣기 — 토큰만 디코딩해도 전체 기기 수와 등록 순서가 드러나서 선택하지 않았어요.

## Consequences

- (+) 인증 단계에서 DB를 보지 않아요. 서명과 만료만 확인해요.
- (+) 서버에 재사용할 수 있는 자격증명 원본이 남지 않아요. DB가 유출돼도 토큰을 쓸 수 없어요.
- (-) 도난을 알아챌 수단이 없어요. 회전을 하지 않아 재사용 탐지가 없고, 로그인이 없어 접속 알림도 만들 수 없어요.
- (-) 만료가 없으므로 훔친 refresh token은 폐기하기 전까지 유효해요.
- (=) RSA 개인 키가 단일 실패 지점이 돼요. 키가 새면 누구나 토큰을 위조할 수 있어요. 다만 키를 바꾸면 access token만 무효가 되고 앱은 30분 안에 알아서 재발급받으므로 교체가 사용자에게 보이지 않아요.
- (=) 개발과 운영에 서로 다른 키 쌍을 만들어 배포 시크릿으로 관리해야 해요. 키가 없으면 애플리케이션이 부팅하지 못해요.
- 재검토: "내 한숨 삭제"처럼 토큰 하나가 되돌릴 수 없는 작업의 권한이 되면, 하드웨어 키(Android Keystore, iOS Secure Enclave)로 올려서 값 복사로는 훔칠 수 없게 만들어야 해요.

## Compliance

- JWT `sub`에 `public_id`가 들어가고 순번 기본 키가 노출되지 않는지 테스트로 확인해요.
- refresh token 원본이 DB에 저장되지 않고 해시만 남는지 확인해요.
- 위조되거나 형식이 잘못된 토큰에 `500`이 아니라 `401`이 나가는지 확인해요.
- 키 설정 객체의 `toString()`이 값을 가리는지, 파싱 실패 메시지에 값이 섞이지 않는지 확인해요.
