# ADR-0042: 배포 입력 차단과 경쟁 공개를 분리한다

## Status

Accepted (2026-10-27, #924의 사용자 승인 운영 설계). 구현·검증 결과와 실제 실행 승인은 별도다.

## Context

- 활성 서버 세대는 HTTP·WS 저장 자격이고 `enabled`·`activation_date`는 WS 경쟁 공개 조건이다. 경쟁 OFF에서도 호환 HTTP 저장을 유지한다.
- 현재 OFF 전용 전환은 DB 소유권과 nginx를 검증하지만, ON 전환의 신규 입력 차단·기존 WS 정리는 구현하지 않았다.
- 같은 컨테이너는 재시작 후에도 UUID를 유지한다. 메모리 차단만 사용하면 재시작 때 입력이 재개될 수 있다.
- 명령 응답 유실은 작업 미실행의 증거가 아니다. 지연된 개방 명령과 비상 차단도 경합할 수 있다.
- OFF에서는 새 WS 연결과 초기화가 거절되어, 소켓을 모두 닫으면 미확인 입력을 즉시 정산할 수 없었다.

## Decision

경쟁 공개 설정을 유지한 채 컨테이너에 지속되는 입력 차단 파일과 기존 DB 저장 울타리로 전환한다. 신규 접수는 잠금 전·후에 같은 개방 revision을 확인하고, 소유권 교체·복귀 트랜잭션에서 기존 기기 연결 자격도 무효화한다. 점수와 입력별 최종 결과는 보존한다.

차단 변경은 컨테이너 내부 배타 잠금, 예상 파일 내용 비교, 새로운 revision, 파일·디렉터리 동기화로 수행한다. 후보 입력의 개방 **시도 전** 단계를 영속 기록한다. 그 이전에 실행 신원·차단·DB·실제 프록시를 모두 확인한 실패만 ON 유지 자동 복귀를 허용한다. 개방 시도 이후 장애와 불확실성은 별도 중단·복구 경로로 처리하고 자동 재활성화하지 않는다.

경쟁 OFF에서도 인증된 본인의 기존 입력 결과와 확정 횟수를 정산하는 복구 전용 WS를 허용한다. `session.recovered`와 `inputEnabled=false`를 반환하고 신규 가산·순위 송신은 허용하지 않는다. 일반 경쟁 연결의 `session.ready` 의미는 유지한다.

## Alternatives

- 배포마다 경쟁 OFF→ON: 공개 정책과 일시 입력 차단이 섞이고, 중단 후 안전한 자정 재활성화 계약과 충돌하므로 선택하지 않았다.
- 프로세스 메모리 차단·단순 파일 rename: 재시작 또는 지연된 개방 명령으로 차단이 해제될 수 있어 선택하지 않았다.
- 공통 제어 행에 별도 차단 상태·연결 epoch 추가: 가능하지만 새 스키마와 구버전 이행 책임을 추가한다. 현재 단일 활성 서버·컨테이너 단위 운영에서는 기존 DB 울타리와 연결 무효화를 사용한다.

## Consequences

- (+) 정상 ON 배포는 공개 설정과 날짜를 바꾸지 않으며 사용자에게 배포마다 ON 조작을 요구하지 않는다.
- (+) OFF에서도 최종 결과를 보존해 정산하며, 미확인 입력을 새 ID 또는 HTTP fallback으로 재가산하지 않는다.
- (-) 전환 중 HTTP·WS 프레스가 일시 거절된다. 요청 ID 없는 HTTP 입력은 자동 재전송하지 않는다. 앱의 20초 복구 상한은 배포 시간 보장이 아니다.
- (-) 파일 상태·프로세스 신원·전환 기록·DB·프록시를 함께 검증해야 한다. 확인하지 못하면 두 서버와 기록을 보존한다.
- (=) 이미지 계약 `2`는 입력 차단·복구 경로를 포함한다. 구형 OFF 도구는 이를 안전하게 거절하고, 최초 도입은 OFF 상태에서 진행한다.
- 재검토: 다중 활성 서버, 컨테이너 파일 수명 변경, 대규모 연결 무효화 비용 또는 실제 전환 시간의 병목이 확인될 때.

## Compliance

실제 Spring HTTP·WS, nginx·Docker와 PostgreSQL 17/PostGIS 3.5에서 차단·재시작·응답 유실·복귀·미확인 정산을 검증한다. 로컬 증거를 실제 ON 배포·운영·실기기·부하 검증으로 확대하지 않는다.
