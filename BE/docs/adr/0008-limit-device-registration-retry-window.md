# ADR-0008: 기기 등록 재시도를 5분 안으로 제한한다

## Status

Accepted (2026-09-10)

## Context

- 기기 등록 응답이 유실되면 앱은 등록이 됐는지 몰라요. 그래서 같은 `requestId`로 재시도해요.
- 재시도가 성립하려면 서버가 토큰을 다시 내줘야 해요. 안 그러면 앱이 영영 토큰을 받지 못해요.
- 그런데 토큰을 다시 내준다는 것은, 그동안 `requestId`만 있으면 그 기기의 토큰을 받아낼 수 있다는 뜻이에요. 멱등 키로 만든 값이 잠시 자격증명처럼 동작해요.
- `requestId`는 요청 본문에 실려요. 신고 기능을 만들 때 Hibernate가 제약 위반 로그에 기기 식별자를 평문으로 출력하던 문제가 실제로 있었고, 개발 프로필의 바인딩 로그는 모든 INSERT 값을 그대로 찍었어요.

## Decision

기기가 만들어진 뒤 5분 이내의 재요청에만 토큰을 다시 발급하고, 그 뒤에는 `409`를 반환해요. `devices.created_at`으로 판단하므로 컬럼을 새로 두지 않아요.

## Alternatives

- 제한 없이 허용 — `requestId`가 사실상 영구 자격증명이 돼요. 한 번 로그로 새면 언제까지고 토큰을 받아낼 수 있어서 선택하지 않았어요.
- 재시도에 토큰을 주지 않고 오류만 반환 — 응답을 놓친 앱이 복구할 수 없어요. 익명 앱에는 다시 등록하는 것 말고 방법이 없는데, 그러면 이전 기기를 잃어요.
- 창을 길게 잡기 — 사용할 수 없는 기기 행이 덜 생기지만 `requestId`가 열쇠로 동작하는 시간이 그만큼 길어져요. 정상 재시도는 응답 유실 직후에 일어나므로 길게 잡아서 얻는 것이 적어요.

## Consequences

- (+) 로그나 오류 수집기로 샌 `requestId`의 유효 기간이 5분으로 잘려요.
- (-) 앱이 등록 직후 종료돼 한참 뒤에 재시도하면 `409`를 받고 새 `requestId`로 다시 등록해요. 아무도 사용할 수 없는 기기 행이 하나 남아요.
- (=) 이 제한은 2차 방어예요. 1차는 요청 본문과 기기 식별자를 로그에 남기지 않는 것이고, 이 결정은 그 방어가 뚫렸을 때 피해를 자르는 수단이에요.
- 재검토: 앱에서 창 밖 재시도가 실제로 자주 관찰되거나, 사용할 수 없는 기기 행이 지표를 어지럽힐 만큼 쌓이면 길이를 다시 정해요.

## Compliance

- 창 안의 재시도가 `200`과 함께 토큰을 받는지, 창 밖의 재시도가 `409`를 받고 토큰을 받지 못하는지 통합 테스트로 확인해요.
- 개발 프로필에서 요청 본문 값을 출력하는 로그 설정이 되살아나지 않았는지 확인해요.
