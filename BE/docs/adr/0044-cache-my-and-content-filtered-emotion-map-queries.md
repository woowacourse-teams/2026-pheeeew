# ADR-0044: 내 감정·내용 필터 지도 조회도 캐시를 사용한다

## Status

Accepted (2026-11-09, [#1143](https://github.com/woowacourse-teams/2026-pheeeew/issues/1143)). ADR-0043의 캐시 적용 범위를 `MY`·`MEMO`·`AUDIO` 필터까지 넓혀요.
ADR-0040의 쓰기·재집계 직렬화, 등록 3초 지연, 수정·삭제 즉시 반영, SQL 대체 계약은 그대로 유지해요.
구현·테스트 검증은 완료했으며 배포·운영 지표 확인은 아직 하지 않았어요.

## Context

- ADR-0043은 `ALL/ALL` 조회만 캐시하고, 그 외 필터는 요청 비중을 측정한 뒤 판단하기로 미뤘어요.
- 그룹 필터와 EMD 계층은 앱에서 쓰지 않아요. 실제로 캐시를 우회하던 조회는 `MY`·`MEMO`·`AUDIO`와 그 조합이에요.
- `emotions`에는 `device_id` 인덱스가 없어서, `MY` 핀 SQL은 최신순 인덱스를 훑으며 작성자와 공간 조건을 행마다 확인했어요.
  `MY` 지역 요약 SQL은 테이블 전체를 순차 스캔했어요.
- 메모와 녹음은 함께 있을 수 없어요(DB CHECK 제약, 도메인 생성자). 내용 종류는 녹음 여부 하나로 정해져요.
- 2026-11-09 로컬 합성 데이터 측정(핀 10만 건, PostGIS 17):

| 항목 | 이전 | 이번 결정 |
| --- | --- | --- |
| 핀 캐시 힙 | 8.11 MB | 9.88 MB (내용 종류·지역 코드 + 기기별 색인) |
| `MEMO`·`AUDIO` 캐시 핀 조회 | SQL | p50 17–201 µs |
| `MY` 캐시 핀 조회 | SQL | p50 1 µs 미만 (색인 없이 전체 탐색 시 최대 1.1 ms) |
| `MY` SQL 핀 조회 (100만 건) | p50 약 0.9 s | 인덱스 추가 후 p50 0.05–1.6 ms |
| `MY` SQL 지역 요약 (100만 건) | p50 약 150 ms | 인덱스 추가 후 p50 1 ms 미만 |

## Decision

`GROUP` 필터·EMD 계층·외부 트랜잭션을 제외한 지도 조회는 내용 필터와 `MY` 범위에도 캐시를 사용해요.

- **핀**: 경량 후보에 녹음 여부와 지역 코드를 보관하고, 탐색 때 내용 조건을 함께 확인해요.
  게시하는 스냅샷마다 작성 기기별 최신순 색인을 만들고, `MY`는 전체 후보 대신 이 색인을 탐색해요.
- **지역 요약 (`ALL` 범위)**: 지역 집계를 메모·녹음별로 나눠 보관하고, `ALL`은 두 종류를 합해요.
  기간 결과 캐시의 키는 `(스냅샷 버전, 내용 종류, 시작일, 종료일)`이고, 상한은 내용 종류마다 64개씩 192개예요.
- **지역 요약 (`MY` 범위)**: 기기별 집계는 만들지 않아요. 핀 캐시의 기기별 색인에서 요청마다 계산해요.
  요청 지표는 지역 캐시(`cache="regions"`)로 기록해요. 핀 캐시를 쓸 수 없으면 SQL로 응답해요.
- **SQL 대체 경로**: `emotions (device_id, created_at DESC, id DESC)` 부분 인덱스를 추가해요. 조건은 기존 핀 인덱스와 같아요.
  기존 인덱스 migration과 같이 `lock_timeout` 5초로 일반 `CREATE INDEX`를 실행해요.

## Alternatives

- 인덱스만 추가: `MY` SQL은 1.6 ms 이하로 충분히 빨라지지만, `MEMO`·`AUDIO`는 계속 매 요청 SQL이에요.
  기기별 색인은 남은 SQL과 DB 연결 사용을 없애고, 힙은 약 1 MB만 늘어요.
- 기기별 지역 집계 보관: 사용자 수만큼 메모리가 늘고 쓰기마다 복사할 맵이 늘어요. 한 기기의 핀 수는 적어서 즉석 계산으로 충분해요.
- 기기별 캐시를 따로 두기(`deviceId → 내 핀`): 첫 조회는 결국 SQL이고, 기존 스냅샷의 세대·완전 시점 규칙과 별도로 무효화를 관리해야 해요.
- `CREATE INDEX CONCURRENTLY`: 쓰기를 막지 않지만 트랜잭션 밖 migration이라는 새 패턴이 필요하고, 실패하면 INVALID 인덱스가 남아요.
  현재 테이블 크기에서는 일반 생성의 잠금 시간이 짧아서 기존 방식을 따라요.

## Consequences

- (+) 앱의 필터 조회가 기본 조회와 같은 캐시 경로를 사용해요. 캐시를 쓸 수 없어도 `MY` SQL이 인덱스를 써요.
- (-) 스냅샷을 게시할 때마다 기기별 색인을 다시 만들어요(정렬과 같은 주기의 O(n) 그룹화).
- (-) 지역 집계 재생성 SQL의 결과 행이 내용 종류만큼 늘고, 쓰기마다 해당 종류의 집계만 복사해요.
- (-) `MY` 지역 요약은 핀 캐시의 완전 시점을 따라요. 같은 화면의 `ALL` 지역 요약과 잠깐 다른 시점일 수 있어요.
- (=) 지역 요약은 지금 SQL과 같이 차단을 반영하지 않아요. 핀은 매 요청 차단을 제외해요.
- (=) 지도 조회 결정 기록과 캐시 요청 지표의 이름·태그는 그대로예요. `bypass_filter`는 이제 `GROUP`만 기록해요.
- 재검토: 핀 탐색 수(`pheeeew.map.cache.pin.scanned`)가 내용 필터에서 크게 늘거나, 힙·재생성 시간이 늘거나, `GROUP`·EMD를 다시 쓰게 될 때.

## Compliance

PostgreSQL 17/PostGIS 3.5 서비스 통합 테스트에서 `MY`·`MEMO`·`AUDIO`와 조합, 기간 유무별로
시도·시군구 요약과 모든 핀 페이지가 SQL 결과와 같고 캐시에서 응답하는지 검증해요. 차단·기간 밖 감정, 삭제 즉시 반영, 등록 배치 반영도 확인해요.
내용 종류별 집계와 종류 변경 반영, 기기별 색인 선택과 지역 요약 계산은 단위 테스트로 확인해요.
