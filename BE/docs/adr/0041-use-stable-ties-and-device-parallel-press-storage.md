# ADR-0041: 실시간 프레스는 안정적인 동점 표시와 기기별 병렬 저장을 사용한다

## Status

Accepted (2026-10-26). 사용자 승인 계약 v2로 #919 v1의 도달 우선 표시·전역 번호·전체 쓰기 직렬화를 대체해요.
구현·동시성·성능 검증 완료를 뜻하지 않으며 실제 순위판은 #921 범위예요.

## Context

- 최초 설계는 전역 제어 행을 배타 잠금하고 변경·도달 번호를 발급해 전체 쓰기를 직렬화했어요.
- 사용자는 엄격한 도달·커밋 선착순보다 동점 표시의 안정성과 최소 저장 구조를 선택했어요.
- 같은 기기의 중복 방지·연결 교체·HTTP/WS 합산 제한과 활성 서버 전환의 쓰기 차단은 유지해야 해요.

## Decision

실시간 목록은 `total DESC, public_id ASC`로 표시하고 공동 순위는 점수만으로 계산해요.
UUID는 PostgreSQL과 같은 표준 16바이트 unsigned 사전순(소문자 표준 문자열 오름차순)으로 비교하며 Java `UUID.compareTo`의 signed 비교를 사용하지 않아요.
일일 불투명 공개 ID는 해당 날짜 안에서 유지하며 먼저 접수·커밋한 기기의 우선 표시를 보장하지 않아요.
기존 HTTP 순위 API의 계약은 변경하지 않아요.

일반 저장은 공통 제어 행 `FOR SHARE` → 기기 제어 행 `FOR UPDATE` → 입력 행 `FOR UPDATE` → 감정명 순으로 잠그고 트랜잭션 종료까지 유지해요.
전역 `change_no`·`reach_order`와 대체 기기별 카운터를 두지 않으며 일반 프레스·닉네임 변경에서 공유 잠금을 배타 잠금으로 승격하지 않아요.
`PENDING`의 독립 접수 커밋과 후속 점수·투영·제한 소비·`APPLIED`의 원자 확정은 유지해요.
서버 전환은 신규 입력 중단 후 공통 행의 배타적 `UPDATE`로 모든 공유 트랜잭션의 종료를 기다리고 활성 세대를 교체해요.
부팅으로 활성 서버를 선점하지 않으며 초기 WS 비활성 기본값을 유지해요.

#921은 250ms마다 짧은 `REPEATABLE READ`로 전체 점수·닉네임을 재조회하고 조회부터 게시까지 한 흐름만 실행해요.
`afterCommit` dirty 신호는 조회를 앞당기는 힌트로만 사용하고 유실 복구는 전체 조회가 담당해요.
`snapshotVersion`은 서버 세대 안의 로컬 단조 증가 번호이며 영속 변경 번호나 커밋 watermark가 아니에요.
상세 입력·복구·응답 계약은 [실시간 프레스 계약](../decisions/realtime-press-contract.md)을 따라요.

## Alternatives

- 전역 배타 잠금·도달 번호: 선착순 의미를 유지하지만 모든 기기의 쓰기를 한 지점에서 직렬화하므로 선택하지 않았어요.
- 기기별 카운터·최대 시퀀스/시각 커서: 전역 커밋 포함 범위를 나타내지 못하며 이번 최소 구조에 추가하지 않아요.
- Redis·큐: 현재 필요한 저장 정합성은 PostgreSQL로 지키며 실제 필요가 측정되면 검토해요.

## Consequences

- (+) 서로 다른 기기의 저장은 호환되는 공유 잠금으로 진행하며 전역 번호 발급을 기다리지 않아요.
- (-) 도달 선착순 표시를 제공하지 않고 같은 기기의 경합과 전체 재조회·정렬 비용이 남아요.
- (=) 공유 잠금은 공정성·대기 시간 상한을 보장하지 않으며 서버 전환 대기·경합을 검증해야 해요.
- (=) 느린 과거 조회가 더 큰 버전으로 게시되지 않도록 단일 조회·게시 흐름을 지켜야 해요.
- 재검토: 저장 잠금 대기·조회 비용·실제 화면 반영 지연을 측정해요. 95% 1초는 아직 검증하지 않은 목표예요.

## Compliance

PostgreSQL 17/PostGIS 3.5에서 같은 기기의 중복·복구, 다른 기기의 병렬 저장, 서버 전환의 공유 잠금 대기를 검증해요.
#921에서 콜백 유실 후 전체 재조회와 과거 조회의 재게시 방지를 확인하고, 지연 시험은 버전 비교 대신 기대 적용 요청의 포함 여부를 별도로 관측해요.
