# ADR-0004: 멱등 저장 경로에는 트랜잭션을 두지 않는다

## Status

Accepted (2026-09-01)

## Context

- 코드 컨벤션 3장은 Service 클래스에 `@Transactional(readOnly = true)`를 두고 변경이 일어나는 메서드에만 `@Transactional`을 얹도록 정해요.
- 한숨 등록과 한숨 신고는 둘 다 멱등 저장이에요. 선조회로 대부분을 거르고, 그 사이를 파고든 동시 요청은 유니크 제약 위반을 잡아 기존 행을 재조회해서 돌려줘요.
- 선조회만으로는 막지 못해요. 같은 키로 6개를 동시에 요청하는 통합 테스트에서 5건이 실제로 유니크 제약 위반을 거쳐 재조회로 복구했어요.
- 두 Service에 컨벤션대로 애노테이션을 붙이고 전체 테스트를 실행하니 4건이 실패했어요. 신고 2건뿐 아니라 이미 배포된 한숨 등록 2건도 함께 깨졌어요.
- 실패 원문은 `org.hibernate.AssertionFailure: Entry for instance of ... has a null identifier`였어요. PostgreSQL이 트랜잭션을 중단시키는 `25P02`는 관측되지 않았고, 그 앞 단계인 JPA에서 먼저 막혔어요.
- JPA 명세는 flush가 실패하면 그 영속성 컨텍스트를 다시 쓰지 않도록 정해요. 실패한 뒤 같은 컨텍스트로 재조회할 수 없어요.

## Decision

멱등 저장 경로를 가진 Service에는 클래스와 메서드 어디에도 트랜잭션 애노테이션을 두지 않아요. 선조회, 삽입, 재조회가 각각 독립된 트랜잭션으로 실행되어야 삽입이 실패해도 재조회가 깨끗한 상태에서 시작해요. 이 예외의 근거를 각 Service 클래스 Javadoc에 남기고 이 ADR을 가리켜요.

## Alternatives

- `INSERT ... ON CONFLICT DO NOTHING`으로 예외를 아예 만들지 않기 — 트랜잭션 문제가 사라지고 코드도 짧아지지만, 네이티브 INSERT라 `BaseEntity`의 감사 필드가 채워지지 않고 시각을 SQL에 직접 넣어야 해서 선택하지 않았어요.
- 삽입만 별도 빈으로 빼고 `REQUIRES_NEW`로 감싸기 — JPA와 감사를 그대로 유지하지만 도메인마다 협력 클래스가 하나씩 늘고, 자기 호출로는 동작하지 않는 프록시 구조를 함께 알아야 해서 선택하지 않았어요.
- 재신고를 409로 바꾸고 예외를 그대로 던지기 — 예외를 잡지 않으니 트랜잭션을 컨벤션대로 붙일 수 있고 코드가 가장 단순해지지만, 재신고에 최초 결과를 돌려주는 계약을 포기해야 해서 선택하지 않았어요.

## Consequences

- (+) 동시 요청에서도 한 건만 저장하고, 경합에서 진 요청도 최초 결과를 200으로 받아요.
- (+) 협력 클래스나 네이티브 SQL을 추가하지 않고 현재 구조를 그대로 유지해요.
- (-) 코드 컨벤션 3장을 어기는 예외가 생겨요. 컨벤션만 보고 애노테이션을 붙이면 동시성 테스트가 깨져요.
- (-) 선조회와 삽입이 서로 다른 트랜잭션이라 두 문장 사이에서 장애가 나면 되돌릴 수 없어요. 지금은 한 번에 한 건만 저장해서 문제가 되지 않아요.
- (=) 이 예외는 멱등 저장 경로에만 적용해요. 다른 Service는 컨벤션 3장을 그대로 따라요.
- (=) 무결성 증명을 실은 등록 경로에서는 아래 `(+)` 의 동시 등록 보장이 성립하지 않아요. 근거와 실측은 ADR-0015 에 있어요.
- 재검토: 한 번의 저장이 여러 엔티티나 여러 테이블을 함께 바꾸게 되거나, 멱등 계약을 409로 바꾸기로 하면 다시 판단해요.

## Compliance

- 멱등 저장 경로를 가진 Service에 트랜잭션 애노테이션이 없는지, 근거 주석이 이 ADR을 가리키는지 리뷰에서 확인해요.
- 같은 키로 동시에 요청해도 한 건만 저장되고 나머지가 최초 결과를 받는지 통합 테스트로 검증해요.
