# ADR-0009: 등록 재시도에서 이전 refresh token을 폐기하지 않는다

## Status

Accepted (2026-09-10)

## Context

- 등록 재시도는 매번 새 refresh token을 발급해요(ADR-0008). 그래서 한 기기에 유효한 토큰이 여러 개 남아요.
- 회전, 만료, 폐기 API, 정리 스케줄러가 모두 없어서(ADR-0007) 한 번 발급한 토큰을 회수할 수단이 없어요.
- 그래서 재시도 시점에 그 기기의 기존 토큰을 폐기하도록 구현해 보고 측정했어요.

## Decision

폐기하지 않아요. 재시도는 이전 토큰을 그대로 두고 새 토큰만 발급해요.

## Alternatives

- 재시도 시 기존 토큰 폐기 — 구현해서 측정한 뒤 되돌렸어요. 등록 1건과 같은 `requestId` 동시 재시도 6건을 두 번 실행했더니 7행 중 유효한 행이 각각 6행과 4행으로 실행마다 달랐어요. 조회와 발급이 서로 다른 트랜잭션이라 경합에서 폐기가 성립하지 않았어요.

  더 나쁜 것은 그 뒤집힌 면이에요. 일부 요청은 `200`과 함께 받은 토큰이 응답을 받는 순간 이미 폐기된 상태였어요. 그 앱은 30분 뒤 `401`을 받고, 그때는 5분 창이 지나 `409`라 복구할 수단이 없어요. ADR-0007이 회전을 거부한 이유로 든 실패 모드와 같아서 선택하지 않았어요.

- 조회와 폐기와 발급을 한 트랜잭션으로 묶기 — ADR-0004가 등록 경로에 트랜잭션을 두지 못하게 해요. 재시도 경로만 떼어내면 가능하지만 동시 요청이 행 잠금에서 직렬화되거나 교착해요.

## Consequences

- (+) ADR-0004가 약속한 "경합에서 진 요청도 사용할 수 있는 결과를 받는다"가 지켜져요.
- (+) 정상 사용자가 아무 잘못 없이 잠기는 경로가 없어요.
- (-) 한 기기에 유효한 refresh token이 여러 개 쌓일 수 있고 회수할 수단이 없어요.
- (-) `DeviceRefreshToken.revoke()`와 `expires_at`에 프로덕션 호출자가 없어요. 도메인에만 있고 아무도 부르지 않는 코드로 남아요.
- (=) 5분 재시도 창(ADR-0008)이 이 증식을 막는 유일한 방어선이에요. 창을 늘리면 증식할 수 있는 시간도 함께 늘어나요.
- 재검토: 폐기 API나 정리 스케줄러를 만들 때 다시 판단해요. 그때는 `revoke()`를 부를 자리가 생기고, 트랜잭션 경계를 다시 볼 이유도 생겨요.

## Compliance

- 동시 등록에서 경합에 진 요청이 받은 토큰도 재발급에 사용할 수 있는지 통합 테스트로 확인해요.
