# 컬렉션 카드 이력 조회 실행계획 검증

- 검증일: 2026-10-23
- 대상: #843, `CollectionProgressRepository.findHistory`의 실제 SQL
- 결론: 이번 데이터에서는 추가 카드 인덱스가 필요한 병목 근거가 없어 기존 인덱스를 유지한다.

## 환경과 데이터

격리된 `postgis/postgis:17-3.5` 컨테이너(PostgreSQL 17.5, PostGIS 3.5.2)를 사용했다.
arm64 Mac에서 amd64 이미지를 에뮬레이션했다. 개발·운영 DB와 S3는 접근하지 않았다.

실제 `V20261008_1`, `V20261022_1`, `V20261022_2`, `V20261023_1` 마이그레이션을 그대로 실행해
카드·자산·집계의 컬럼, 제약, 최종 인덱스를 적용했다. 조회와 무관한 `devices`는 `id` PK만 둔 최소 테이블로 대체했다.

- 일반 기기 100개 × 365일 × 매일 5감정 = 카드 182,500개.
- 희소 감정 기기 1개: ANGRY 365개 + EXHAUSTED 1개.
- 카드 총 182,866개. 스탬프·프레스 집계도 각각 182,866행이며 횟수는 1·100이다.
- 날짜는 2025-10-23~2026-10-22. 감정별 256개 조합 이후 회차를 증가시켰다.
- 자산은 실제 v1 시드의 캐릭터 80행·도장 쌍 80행을 사용했다.

## 방법과 결과

`ANALYZE` 후 Java의 `CARD_DETAILS_SQL`을 추출하고 실제 `findHistory`와 같은 WHERE·ORDER BY·LIMIT를 붙였다.
첫 페이지는 `beforeDate=2026-10-23`, 마지막 위치도 같은 날짜와 `Long.MAX_VALUE`다.
깊은 페이지는 `lastDate=2026-04-26`, `lastId=Long.MAX_VALUE`이며 기기 42를 조회했다.
희소 감정은 기기 101의 EXHAUSTED다. 페이지 크기 20·50에 각각 21·51행을 요청했다.

`EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)`을 경우별 13회 실행하고 처음 3회는 워밍업으로 제외했다.
아래 중앙값과 범위는 나머지 10회의 DB **Execution Time**이다.
계획 시간과 버퍼는 저장한 마지막 실행계획의 단일 관측값이며 중앙값이 아니다.

모든 마지막 계획에서 shared read blocks는 0이었다. 캐시가 데워진 조회이며 콜드 캐시 측정이 아니다.
계획 시간은 실행 시간에 포함되지 않는다. 따라서 실행 중앙값만을 전체 쿼리 시간이나 HTTP 응답시간으로 해석하지 않는다.
네트워크·애플리케이션 매핑·직렬화·RDS 환경·동시 쓰기 부하를 포함한 성능 보장도 아니다.

## 실행계획 해석

- 카드: 기존 `uk_collection_cards_device_date_state(device_id, card_date, state)`를 역방향 Index Scan하고
  날짜별 `Incremental Sort`로 내부 ID 내림차순을 맞췄다. 하루 최대 5개 카드라는 제약과 맞는다.
- 페이지 크기 20에서는 전체 조회 26행·감정 조회 22행, 크기 50에서는 각각 56행·52행을 읽었다.
  `hasNext` 확인용 한 건과 정렬 그룹 경계 때문에 응답 개수보다 조금 더 읽는다. 전체 카드 스캔은 없었다.
- 180일 이전의 깊은 페이지도 날짜·ID 커서 조건으로 탐색 범위를 제한했다. OFFSET만큼 앞선 행을 읽고 버리는 방식이 아니다.
- 스탬프·프레스는 기존 유니크 인덱스로 조인했다. 자산은 각 80행뿐이며 감정 필터에서 Seq Scan·Materialize도 선택됐다.
  작은 자산 테이블의 Seq Scan은 카드 전체 스캔을 의미하지 않는다.
- 희소 감정 조회도 카드 인덱스로 EXHAUSTED 한 행을 읽었다.

현재는 인덱스·제품 SQL을 변경하지 않는다. 기기당 이력량·감정 분포·자산 버전 수가 달라지거나 실제 지연이 관측되면
대표 파라미터의 계획 시간·실행 시간·버퍼를 함께 재확인한다. 이 측정은 최적 계획을 모든 데이터 분포에 보장하지 않는다.

## 정리

측정용 코드와 전용 Docker 컨테이너·DB 데이터는 제거했다. 테스트용 자료를 제품 마이그레이션이나 앱에 추가하지 않았다.
