# 컬렉션 카드 이력 조회 실행계획 검증

- 검증일: 2026-10-23
- 대상: #843, `CollectionProgressRepository.findHistory`의 실제 SQL
- 최신 결론: 개수 조회는 기기별 날짜 범위의 카드 전체를 읽는 비용을 추가한다. 아래 후속 비교에서 기존 인덱스를 사용했으며, 이번 범위에서는 추가 인덱스를 도입할 근거가 없었다.

## 최초 목록 조회 검증 — 개수 추가 전

아래 최초 측정은 #910의 목록 전용 쿼리 결과다. 개수 추가 후 결과는 후속 비교 절을 참고한다.

### 환경과 데이터

격리된 `postgis/postgis:17-3.5` 컨테이너(PostgreSQL 17.5, PostGIS 3.5.2)를 사용했다.
arm64 Mac에서 amd64 이미지를 에뮬레이션했다. 개발·운영 DB와 S3는 접근하지 않았다.

실제 `V20261008_1`, `V20261022_1`, `V20261022_2`, `V20261023_1` 마이그레이션을 그대로 실행해
카드·자산·집계의 컬럼, 제약, 최종 인덱스를 적용했다. 조회와 무관한 `devices`는 `id` PK만 둔 최소 테이블로 대체했다.

- 일반 기기 100개 × 365일 × 매일 5감정 = 카드 182,500개.
- 희소 감정 기기 1개: ANGRY 365개 + EXHAUSTED 1개.
- 카드 총 182,866개. 스탬프·프레스 집계도 각각 182,866행이며 횟수는 1·100이다.
- 날짜는 2025-10-23~2026-10-22. 감정별 256개 조합 이후 회차를 증가시켰다.
- 자산은 실제 v1 시드의 캐릭터 80행·도장 쌍 80행을 사용했다.

### 방법과 결과

`ANALYZE` 후 Java의 `CARD_DETAILS_SQL`을 추출하고 실제 `findHistory`와 같은 WHERE·ORDER BY·LIMIT를 붙였다.
첫 페이지는 `beforeDate=2026-10-23`, 마지막 위치도 같은 날짜와 `Long.MAX_VALUE`다.
깊은 페이지는 `lastDate=2026-04-26`, `lastId=Long.MAX_VALUE`이며 기기 42를 조회했다.
희소 감정은 기기 101의 EXHAUSTED다. 페이지 크기 20·50에 각각 21·51행을 요청했다.

`EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)`을 경우별 13회 실행하고 처음 3회는 워밍업으로 제외했다.
아래 중앙값과 범위는 나머지 10회의 DB **Execution Time**이다.
계획 시간과 버퍼는 저장한 마지막 실행계획의 단일 관측값이며 중앙값이 아니다.

계획 시간은 실행 시간에 포함되지 않는다. 따라서 실행 중앙값만을 전체 쿼리 시간이나 HTTP 응답시간으로 해석하지 않는다.
네트워크·애플리케이션 매핑·직렬화·RDS 환경·동시 쓰기 부하를 포함한 성능 보장도 아니다.

### 실행계획 해석

- 카드: 기존 `uk_collection_cards_device_date_state(device_id, card_date, state)`를 역방향 Index Scan하고
  날짜별 `Incremental Sort`로 내부 ID 내림차순을 맞췄다. 하루 최대 5개 카드라는 제약과 맞는다.
- 페이지 크기 20에서는 전체 조회 26행·감정 조회 22행, 크기 50에서는 각각 56행·52행을 읽었다.
  `hasNext` 확인용 한 건과 정렬 그룹 경계 때문에 응답 개수보다 조금 더 읽는다. 전체 카드 스캔은 없었다.
- 180일 이전의 깊은 페이지도 날짜·ID 커서 조건으로 탐색 범위를 제한했다. OFFSET만큼 앞선 행을 읽고 버리는 방식이 아니다.
- 스탬프·프레스는 기존 유니크 인덱스로 조인했다. 자산은 각 80행뿐이며 감정 필터에서 Seq Scan·Materialize도 선택됐다.
  작은 자산 테이블의 Seq Scan은 카드 전체 스캔을 의미하지 않는다.
- 희소 감정 조회도 카드 인덱스로 EXHAUSTED 한 행을 읽었다.

현재는 인덱스·제품 SQL을 변경하지 않는다. 기기당 이력량·감정 분포·자산 버전 수가 달라지거나 실제 지연이 관측되면
대표 파라미터의 계획 시간·실행 시간·버퍼를 함께 재확인한다. 이 측정은 최적 계획을 모든 데이터 분포에 보장하지 않는다.

### 정리

측정용 코드와 전용 Docker 컨테이너·DB 데이터는 제거했다. 테스트용 자료를 제품 마이그레이션이나 앱에 추가하지 않았다.

## 후속 비교 — 오늘 포함·전체/감정별 개수 추가

검증일은 2026-10-23이다. 기준은 `f3fd8b442`의 목록 전용 SQL이고 비교 대상은
`32298392a`의 목록·개수 결합 SQL이다. 각 Java 소스의 문자열을 추출해 실행했으며 제품 코드는 변경하지 않았다.
첫 요청 날짜 범위는 두 쿼리 모두 `beforeDate=2026-10-24`로 맞췄다. 즉 기존 SQL에도 같은 날짜 범위를 주어
오늘 포함에 따른 데이터 차이와 개수 집계 비용을 섞지 않았다. 기존 API가 당일을 제외했던 계약 변경은 기능 테스트로 검증했다.
닉네임은 기존 기기 조회 결과를 사용하므로 이 SQL 비교 대상에 추가 쿼리가 없다.

### 데이터와 측정 방법

- 새 격리 `postgis/postgis:17-3.5` 컨테이너에 위와 같은 실제 마이그레이션을 적용했다.
  일반 기기 100개 × 365일 × 5감정, 희소 감정 기기 366장에 추가로 빈 기기·10년치 기기 18,250장·미래 날짜만 가진 기기 1장을 구성했다.
  총 카드 및 각 활동 집계는 **201,117행**, 자산은 실제 v1 시드 캐릭터 80행·도장 쌍 80행이다.
- 1년치 날짜는 2025-10-24~2026-10-23이다. 10년치는 3,650일이며 미래 카드는 2026-10-24다.
  깊은 페이지는 `lastDate=2026-04-26`, `lastId=Long.MAX_VALUE`다. 일반 기기는 42, 희소 101, 빈 기기 102, 10년치 103, 미래만 104다.
- `VACUUM ANALYZE` 후 경우별 두 쿼리를 교대로 각 13회 실행하고 앞의 3회를 버렸다.
  `EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)`의 10회 실행·계획 시간 중앙값과 실행 범위를 기록했다.
  버퍼는 마지막 실행의 관측값이다. 전체/ANGRY 첫·깊은 페이지 크기 20/50과 희소·빈 결과·미래 제외·장기 이력 총 14조건이다.
- 각 조건에서 기존/신규의 카드 행과 순서가 정확히 일치함을 검사했다. 새 쿼리의 5감정 개수도 별도 GROUP BY 결과와 대조했다.
  감정 필터가 비어도 본인 전체 개수가 남고, 빈 기기·미래 카드만 있는 기기의 개수는 0이다.

### 계획 해석과 판단

- 페이지 조회는 기존 `(device_id, card_date, state)` 인덱스의 역방향 스캔과 Incremental Sort를 유지한다.
  일반 전체 페이지는 20장일 때 카드 26행, 50장일 때 56행을 읽으며 깊은 페이지도 커서로 범위를 좁힌다.
- 추가 개수 집계는 같은 유니크 인덱스로 **Index Only Scan**한다. 일반 기기의 1,825행, 희소 기기의 366행,
  10년치 기기의 18,250행을 읽는다. 전체 테이블을 읽는 것은 아니지만 페이지 크기나 감정 필터에 비례해 비용이 작아지지도 않는다.
  다음 페이지에서도 날짜 범위 전체 개수를 다시 센다. 정확한 전체·감정별 개수를 제공하기 위한 추가 비용이다.
- 집계 CTE와 페이지 LEFT JOIN은 카드가 없어도 개수를 반환하게 한다. 최종 정렬은 최대 21/51행에 적용된다.
  활동 집계 조인은 기존 인덱스를 사용한다. 작은 자산 테이블은 조건에 따라 인덱스 또는 순차 스캔을 선택하며 제품 인덱스 변경은 없었다.
- 이번 결과만으로 추가 인덱스·캐시·별도 장수 저장 테이블을 도입하지 않는다. 현재 인덱스가 집계에 필요한 세 컬럼을 이미 담고 있다.
  장기 이용자의 카드 수가 늘면 집계량도 증가하므로 실제 이력량과 조회 빈도를 기준으로 다시 측정해야 한다.

### 측정 한계와 재현 조건

arm64 Mac에서 amd64 이미지 에뮬레이션이며 PostgreSQL 17.5/PostGIS 3.5.2다.
`shared_buffers=128MB`, `work_mem=4MB`이고 별도 서버 설정 튜닝은 하지 않았다.
모든 마지막 계획의 shared read blocks는 0이었다. `VACUUM ANALYZE` 직후라 집계 Index Only Scan의 Heap Fetches도 0인 유리한 조건이다.
최근 INSERT/UPDATE와 동시 쓰기, vacuum 지연에서는 heap 접근과 지연이 더 발생할 수 있다.
매 실행 새 psql 연결을 사용하고 계획 시간과 실행 시간을 따로 기록했으며 애플리케이션 JDBC prepared statement의 재사용 조건은 재현하지 않았다.
계획 시간을 제외한 실행 중앙값만으로 전체 쿼리·HTTP·운영 RDS 응답시간이나 처리량을 보장하지 않는다.
이 검증은 읽기 실행계획 비교이며 쓰기 비용·동시성 부하·이미지 로딩은 측정하지 않았다. SLO 합격 판정도 하지 않았다.

### 검증 및 정리

14조건 모두 카드 행/순서 일치와 개수 대조를 통과했다. 제품 코드의 검증 완료 상태는
`./gradlew test` 2,819개 통과·2개 건너뜀·실패 0이며, 이번에는 SQL 측정과 문서만 추가하여 전체 테스트를 반복하지 않았다.
측정용 스크립트·SQL·원시 결과와 전용 Docker 컨테이너·DB는 제거했다. 보고서만 저장소에 남겼다.
개발·운영 DB 및 S3는 접근하지 않았으며 커밋·푸시·배포하지 않았다(1·2번 구현 커밋과 별개인 이 보고서 갱신 기준).
