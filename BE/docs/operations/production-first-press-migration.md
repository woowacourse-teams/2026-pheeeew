# 운영 단일 서버 프레스 최초 이행 초안

이 문서는 설계 초안이며 실행 도구나 완료된 실행 절차가 아니다. 운영 전용 이행 도구, 프록시 경로 확인 및 복구 검증을 완료하기 전에는 실행하지 않는다. 기존 운영 CD의 계약 2 거절 조건을 제거하지 않는다.

## 대상과 전제

- 현재 확인한 운영 앱은 `pheeeew-prod-app`, 이미지 `prod-d928e1716a4f1b9d668ef0c47a1c15a35e813364`이다. 실제 실행 직전에 이미지 ID, 컨테이너 ID, DB 및 Flyway 이력을 다시 확인한다.
- 후보 소스는 최종 `develop` 커밋으로 정한다. 실행 직전에 해당 커밋의 빌드 결과와 이미지 ID를 확인한다. 아래 격리 DB 확인은 이전 `5961baec` 기준이며 최종 후보 전체 검증을 뜻하지 않는다.
- 운영 DB에 `press_race_control`이 없는 최초 이행만 다룬다. 경쟁은 OFF로 시작하며, 경쟁 공개는 별도 작업이다. 기존 점수 원본을 삭제하거나 DB를 과거 스냅샷으로 덮어쓰지 않는다.
- 이전 앱은 세대 울타리를 확인하지 않는다. 기존 앱의 종료와 자동 재시작 및 기존 CD의 재실행 방지가 확인되지 않으면 후보에 저장 자격을 주지 않는다.
- 적용 시점, 중단 공지, 신규 입력 차단 방법, 테스트 기기, 중단 기준, 담당자 및 복구 담당자는 실행 전에 확정한다.
- 2026-10-29: 운영 nginx 설정 `fb7a560c`을 반영하고 이전 설정을 `/opt/pheeeew/nginx/api.conf.before-fb7a560c-20261029`에 보관했다. 개발 `api-dev` DNS는 서버 고정 IP `43.202.199.127`로 변경했고 직접 HTTPS와 인증 WS를 확인했다. ALB 기본 규칙은 404이며 개발 도메인의 직접 API 200과 ALB 경유 404를 확인했다.
- 운영 `api.pheeeew.com`은 DNS-only CNAME으로 `pheeeew-alb-1544975328.ap-northeast-2.elb.amazonaws.com`을 가리키고, 운영 EC2에는 공유 `project-app`만 연결했다. 공개 도메인 및 ALB HTTPS 200, 기존 서버 IP 직접 연결 차단, Cloudflare SSH, 새 PostgreSQL 연결과 앱 health 상태를 확인했다. 기존 DNS는 A `3.39.142.124`, 기존 EC2 그룹은 `project-public`이다. 사용자가 기존 개발과 같은 방식에 동의해 nginx에 ALB 서브넷 real-IP 설정을 적용했다. 실제 ALB를 통한 조회에서 사용자가 앞에 추가한 임의 XFF는 로그의 요청자 IP에 반영되지 않았고, 공개 API는 200이었다. 적용 전 설정은 `/opt/pheeeew/nginx/api.conf.before-realip-20261028214732`다. `project-app`은 같은 그룹 내 다른 서버의 모든 포트를 허용하므로 전용 그룹과 같은 격리로 간주하지 않는다.
- 운영 ALB 통합 화면에서 WAF 연결 상태를 조회했으나 `wafv2:GetWebACLForResource` 권한 거부로 상태를 확인할 수 없었다. WAF가 연결됐거나 연결되지 않았다고 단정하지 않는다. 인프라 안내에 명시된 WAF 연결 여부는 권한이 있는 관리자가 확인해야 한다.
- 독립 검토에서 현재 공유 `project-app`의 자기 참조 전체 허용과 공유 `project-lb`를 사용하는 구성은 ALB 전용 접근을 증명하지 못했다. ALB 서브넷 내 비ALB 자원이 운영 nginx에 직접 연결할 수 있다면 X-Forwarded-For 마지막 값을 위조할 수 있다. 이는 인터넷의 임의 사용자가 곧바로 위조할 수 있다는 뜻이 아니며, 해당 서브넷에서 허용된 비ALB 자원의 존재 여부는 확인하지 않았다.
- 운영 RDS 콘솔의 2026-10-29 조회에서 자동 백업이 비활성화돼 있고 해당 DB 스냅샷이 0개로 표시됐다. 사용자는 이번 migration이 기존 프레스 데이터를 의도적으로 삭제하지 않는다는 확인 후 스냅샷을 만들지 않기로 결정했다. 백업이 없으면 예기치 않은 손상이나 조작 오류로 데이터가 삭제된 경우 해당 시점으로 DB를 복원할 수 없다. 구형 앱 재기동 시험은 데이터 백업을 대체하지 않는다.

## 운영 ALB의 사용자 주소 경계 검토

- 2026-10-29: 처음에는 DNS 전환 준비 전에 `project-app`을 적용해 공개 요청이 시간 초과됐다. `project-public`으로 복구한 뒤 DNS를 ALB로 바꾸고 다시 `project-app`을 적용했다. 이후 공개 HTTPS 200과 새 DB 연결을 확인했다.
- 전용 보안 그룹은 AWS 계정 정책의 명시적 거부로 생성하지 못했다. 사용자는 인프라 안내의 공유 `project-lb`, `project-app`, `project-db`를 사용하는 것을 선택했다. 공유 그룹 자체의 규칙은 변경하지 않았다.
- 운영 서버에서 `cloudflared`가 실행 중이고 `certbot.timer`가 활성화돼 있다. 인증서 갱신 설정은 `dns-cloudflare`이므로 HTTP 80 챌린지에 의존하지 않는다. 그룹 전환 후 Cloudflare SSH와 신규 DB 연결을 확인했다.
- ALB는 `X-Forwarded-For`를 첨부하며 클라이언트 포트 보존은 꺼져 있다. 운영 nginx는 사용자의 결정에 따라 개발에서 사용하던 서브넷 신뢰 방식을 적용했다. 위에 기록한 공유 서브넷의 위조 가능성은 해소된 것으로 취급하지 않는다.
- 대상은 `pheeeew-alb`, `pheeeew-prod` (`i-0f8f0d39a4ad66339`), `pheeeew-db`다. 적용한 nginx 파일의 SHA-256은 `1c0ac47cb83cce2c9157a7368af1a94a1cef6eaa90f8ecba735220e8f037fc0d`다. 운영 DB는 기존 `project-db`의 `project-app` 5432 허용 규칙을 사용한다.
- 운영 사용자 주소 처리 코드는 `be/dev` PR #1024와 `develop` 승격 PR #1025로 머지했다. 개발 CD는 `a680aba12d8e03d313d4690e3e01594775a3ec5a`로 성공했고 새 blue 컨테이너의 Nginx 경유 인증 WS 세대를 확인했다.
- RDS 연결 설정 화면에 KMS 별칭 조회 권한 오류가 있고 백업 관련 표시가 현재 상태 화면과 다르게 나타난다. 보안 그룹 변경 확인 화면에 요청하지 않은 수정이 나타나거나 확정 내용을 판별하지 못하면 적용하지 않는다. 문제가 생기면 nginx real-IP 설정을 먼저 이전 버전으로 복구하고 기존 연결을 정리한 뒤 EC2·ALB의 기존 보안 그룹과 기존 DNS를 되돌린다. 새로운 DB 연결, 직접 HTTPS, Cloudflare SSH 및 ALB 경로를 재확인한다.
- RDS 그룹 변경 시 기존 `project-db` 그룹을 보존하고 새 그룹을 추가한다. 기존 그룹을 유지하므로 DB 전체의 기존 접근 범위는 그대로다. 실제 변경 요약이 보안 그룹 추가만 포함하는지와 대기 변경을 확인한다. RDS 보안 그룹 변경에 불필요한 즉시 적용을 선택해 다른 보류 수정을 함께 적용하지 않는다. 새 RDS 그룹의 active 상태를 확인한 후 EC2 그룹을 교체하고 기존 pool이 아닌 새 DB 연결을 시험한다. 복구 시 기존 EC2 그룹과 새 DB 연결이 정상인 것을 확인하기 전에는 새 RDS 그룹을 제거하지 않는다.

## 전환 순서

1. 운영 앱·프록시 설정 및 이미지 digest, DB 대상과 Flyway 이력, 복구에 필요한 설정을 안전한 위치에 기록한다. 스냅샷은 생성하지 않기로 한 사용자 결정을 기록하고, 구형 이미지 복귀의 범위와 한계를 확인한다. 후보 이미지와 운영 프록시 변경을 검토하고, 구형 이미지가 변경된 DB에서 작동하는지 격리 환경에서 확인한다.
2. 외부 입력을 차단하고 구형 앱의 진행 중 요청과 DB 트랜잭션이 종료된 것을 확인한다. 구형 앱을 정지하고 재시작 정책과 CD가 다시 시작하지 못하는지 확인한다. 불확실하면 중단한다.
3. 후보의 고정 세대 UUID를 새로 생성해 후보 컨테이너 설정에 넣는다. 기존 UUID를 임의로 지정하지 않는다. 후보를 입력 CLOSED로 시작하고 Flyway 이력과 앱 기동, 컨테이너 실행 신원, DB 대상 및 CLOSED 상태를 확인한다. 일부 migration 실패는 전체 원복이 아니므로 이력과 실제 스키마를 보존해 조사한다.
4. 운영 전용 이행 도구가 control 행이 정확히 `generation=NULL`, `enabled=false`, `activation_date=NULL`일 때만 후보 UUID로 소유권을 조건부 변경한다. 변경 응답이 유실되면 DB 상태를 재조회한다. 예상과 다르거나 결과가 불확실하면 차단을 유지한다.
5. 후보 런타임 UUID, DB 소유권, OFF 상태, CLOSED revision, 검토된 nginx 설정과 컨테이너 신원을 확인한다. 원래 nginx가 멈춘 동안 개방 의도와 revision을 기록하고 후보를 연다. 그 후 원래 nginx를 이름 변경해 보존하고 신규 nginx를 켜 ALB를 통한 인증 WS UUID를 확인한다. 응답 유실 시 재조회하며 불명확한 요청은 재실행하지 않는다.
6. 공개 경로에서 본인 시험 기기의 HTTP 입력 하나를 도구로 보낸다. 원본의 정확한 증가, 해당 기기·날짜의 투영과 원본 합계 일치, 경쟁 OFF 유지를 확인한다. 요청에 ID가 없으므로 응답이 사라져도 재전송하지 않는다. WebSocket 사용자 기능 전체 검증과 경쟁 활성화는 별도 단계다.

## 중단과 복구

- 새 앱의 개방 **시도 전**: 후보 입력을 닫고 컨테이너를 정지하며 재기동을 방지해 구형 앱과의 동시 실행을 막는다. DB migration 적용 범위를 확인한 뒤 검증된 경우에만 구형 이미지·기존 프록시 설정으로 복귀한다.
- 새 앱의 개방 **시도 후**: 응답이 없더라도 저장이 발생했을 수 있다. 후보 입력을 차단하고 진행 중 저장과 트랜잭션의 종료를 확인한다. 후보를 정지하고 재기동을 막은 뒤 원본과 투영을 최종 재조회한다. 확인할 수 없다면 외부 입력 차단과 기록을 유지한다. 기존 CD의 자동 rollback, DB 소유권 강제 초기화, 구형 앱 자동 기동, 스냅샷 덮어쓰기는 하지 않는다. 저장 내역을 보존하고 원본·투영을 정산한 후 구형 복귀를 별도로 결정한다.
- 구형 앱이 다시 입력을 받으면 신규 점수 투영을 갱신하지 않는다. 다시 새 앱으로 전환하거나 경쟁을 공개하기 전에는 대상 날짜의 원본과 점수 투영을 대조·보정해야 한다. 기존 공개 ID와 입력 이력은 보존한다.

## 실행 전 미완료 항목

- 운영 단일 앱 도구의 조건부 DB 소유권 지정과 응답 유실 후 확인은 초안이다. 구형 앱과 nginx의 정지·재시작 금지를 검사하고, CD와 다른 writer가 중단됐다는 운영자 확인을 요구한다. 이 확인은 실제 CD 중단을 자동으로 증명하지 않는다. **전체 절차와 후속 배포 검증을 끝내기 전에는 운영에서 실행하지 않는다.**
- 후보 OPEN 의도 기록·결과 확인과 불확실한 OPEN을 새 CLOSED revision으로 무효화하는 초안을 추가했다. mock Docker 시험에서 OPEN 응답 유실과 OPEN이 취소보다 먼저 처리되는 경합 뒤 재차 닫는 경로를 확인했다. `ABORT_CLOSED`는 입력 차단과 WS 종료 ACK만 의미하며 진행 중 DB 저장 종료나 구형 이미지 복귀를 뜻하지 않는다. 실제 Spring·Docker 경합과 다른 writer의 통제는 아직 확인하지 않았다.
- 후보를 닫은 상태의 직접 조회는 `SERVER_DRAINING`과 후보 UUID를 요구한다. 공개한 뒤에는 ALB를 통한 인증 WS에서 `DEVICE_NOT_FOUND`와 동일 UUID를 확인한다. 일반 개발 배포의 UUID 조회 조건은 유지한다.
- 최초 이행은 사용자가 허용한 일시 중단을 이용해 기존 nginx를 정지한다. 따라서 maintenance 응답 관측 대신 nginx와 구형 앱의 정지, CD·기타 writer 중단을 확인해야 한다. 운영자 확인은 이 외부 전제를 대신 증명하지 않는다.
- 구형 앱과 동일 DB 계정의 다른 세션과 해당 DB의 준비된 트랜잭션이 없다는 검사는 다른 계정 writer나 새 CD 실행을 차단하지 않는다. CD 경합 차단을 별도로 확인하고 매 단계마다 구형 앱 신원을 다시 검증해야 한다.
- 운영 DB 읽기 전용 조회에서 구형 프레스 원본 `device_daily_presses`에 쓸 수 있는 로그인 역할로 앱 계정과 DB 관리자 역할들이 확인됐다. 준비된 트랜잭션은 조회 시점에 0건이다. 사용자는 운영 앱 외에 프레스를 수정하는 별도 서버·배치·수동 작업이 없다고 확인했다. 이행 시점에는 해당 전제와 앱·CD 중단, 실제 남은 DB 연결을 다시 확인해야 한다.
- 일반 CD와 최초 이행이 영속 잠금을 공유하는 코드를 추가했다. 현재 구현은 대상 서버에 반영되지 않았으며, 운영 변경·수동 SSH 작업에는 자체 잠금을 준수하도록 별도 통제가 필요하다. 읽기 전용 검사에서 미완료 journal 또는 지원하지 않는 이미지 계약을 확인해 변경 전에 거절하면 배포가 획득한 잠금을 해제한다. 그 외 실패나 응답 유실 시에는 자동 해제하지 않으며, 실제 원격 작업 종료 여부를 확인한 뒤 운영자가 복구해야 한다.
- 현재 `main`의 기존 운영 CD는 이 초안의 공유 잠금을 사용하지 않는다. 새 워크플로가 실제 실행 경로에 반영되기 전에 최초 이행 도구의 잠금만 획득해도 기존 CD 실행을 막을 수 없다. 이행 전 실제 실행 중인 워크플로와 진행 중인 작업을 확인하고, 기존 CD의 재실행을 별도로 차단·확인해야 한다. PR 생성이나 CI 성공만으로 이 조건을 충족했다고 간주하지 않는다.
- 최초 기동 전에 검토한 Git 커밋을 `attest-image-release`에 전달해 후보 이미지의 `APP_RELEASE`와 일치하는지 확인한다. 이후 `APP_IMAGE=<확인한 이미지> APP_RESTART_POLICY=no`로 `check-blue-configuration`을 실행하고, 같은 환경변수로 blue를 기동한다. 이 명령은 기존 앱·nginx 정지, blue 컨테이너 부재, 렌더링된 이미지·세대·DB URL·계정 일치를 확인한다. 검증 이후 다른 사용자가 설정이나 컨테이너를 변경하지 않아야 한다.
- 최초 저장 시험은 사용자 본인 시험 기기의 UUID로 `begin-press-probe`를 호출하고, `send-press-probe`로 HTTP 요청 하나를 전송한다. 응답 유실 때 `send`를 다시 실행하지 않고 `confirm-press-probe`만 사용한다. 기기의 기존 입력을 변경하거나 시험 입력을 빼지 않는다. 요청 전 해당 기기에 다른 입력이 없는 조건이 필요하다.
- 최초 완료 시 `press-prod-manifest.py`로 **검토한 Git 커밋에서** 만든 manifest의 SHA-256을 `attest-release-files`에 전달한다. 설치 파일, 이미지의 `APP_RELEASE`, nginx 고정 SHA와 대조한다. `finalize-bootstrap`은 DB 원본·투영, 앱과 nginx 신원, 공개 인증 WS를 다시 확인한 후 완료 기록을 남긴다. 이후 영속 잠금을 해제한다.
- 완료 전에 blue·green 로그 볼륨을 준비하고 새 Alloy 설정을 검증·기동한다. `finalize-bootstrap`은 Alloy의 health, 두 읽기 전용 로그 볼륨과 활성 blue의 메트릭 접근을 확인한다. 이는 Grafana Cloud에 실제 지표가 수신됐다는 증거가 아니므로 Cloud 규칙과 수신도 따로 확인한다.
- 일반 운영 CD는 완료 기록이 없거나 미완료인 경우 거절한다. 기존 main의 CD를 중단한 상태에서 최초 이행을 완료하고 main을 머지한 다음, CD를 다시 켜고 main 워크플로를 수동 실행한다. 중단 중 이전 실행 재시도나 수동 Docker 변경을 하지 않는다. 각 배포마다 현재 활성 앱과 DB를 확인하며, 후보 DB URL·계정은 후보 시작 전에 기존 앱과 두 번 비교한다.
- 완료 journal을 남기고 잠금을 해제하는 후속 배포 경로는 로컬 초안이다. journal을 임의 삭제하거나 잠금을 강제 해제하지 않는다. 실제 운영 전환과 후속 CD 실행은 아직 검증하지 않았다.
- 현재 원격 `develop`의 운영 CD는 계약 2 이미지를 거절한다. 변경된 blue/green 경로는 아직 원격에 반영되지 않았으며, 기존 단일 서버 CD의 거절 조건만 제거해서는 안 된다.
- 후속 배포 초안은 운영 blue/green compose와 nginx 포인터를 사용하며 일반 배포에서 계약 2만 받는다. 최초 후보는 `APP_RESTART_POLICY=no`로 생성한 `pheeeew-prod-app-blue`여야 한다. `press-generations.env`와 nginx 설정 SHA-256은 이행 전에 기록한다. OPEN 확인 후에는 기존 nginx를 ID로 이름 변경해 보존하고 새 nginx를 만든다. `PUBLIC_CONFIRMED`는 공개 인증 WS 경로의 UUID 확인까지만 뜻하며 최초 저장 시험이나 일반 CD 재개를 의미하지 않는다.
- nginx SHA-256은 전송하기 전 검토한 릴리스 파일에서 계산해 `attest-proxy-config`에 전달한다. 서버에 이미 복사된 파일만 해시해 전달하면 검토본과 일치하는지는 확인되지 않는다.
- 원본 프레스는 중단 후 행 수·전체 합계와 `id` 순서의 전체 행 fingerprint를 기록하고 migration 후 비교한다. 이는 원본 테이블 비교이며 운영 데이터베이스 전체 백업을 뜻하지 않는다.
- 2026-10-29 운영 인스턴스 읽기 전용 조회 당시 메모리 `available`은 약 852 MiB, 구형 앱 사용량은 약 427 MiB였다. 추후 배포 초안은 후보의 640 MiB 제한과 128 MiB 여유를 확인한 뒤 후보를 띄운다. 순간 조회는 이후 메모리 증가나 실부하에서의 충분한 여유를 보장하지 않는다.
- migration 중 실패와 각 개방 경계에서의 복구 검토.
- 운영 nginx의 WebSocket 전달과 ALB 경로, 인증서·보안 그룹, 개발 ALB 분리 계획의 별도 확인.
- 전체 migration이 적용된 운영 DB에서 구형 이미지의 업무 호환성 및 재도입 시 점수 투영 보정 검증.

## 격리 환경 복구 확인 (2026-10-29)

운영 컨테이너가 사용 중인 구형 이미지를 읽기 전용으로 가져와 빈 PostgreSQL 17/PostGIS 3.5와 시험 기기를 사용했다. 구형 앱이 기동하고 HTTP 프레스를 한 번 저장한 뒤, `5961baec` 소스에서 빌드한 후보 이미지로 migration 8건을 적용했다. 같은 구형 이미지가 변경된 DB에서 다시 기동해 HTTP 프레스를 한 번 더 저장했고, 원본 합계가 2인 것을 확인했다.

이는 시험 데이터와 성공 경로에 대한 확인이다. 실제 운영 데이터의 제약 충돌, migration 중 부분 실패, 운영 프로필의 외부 연동, 구형 앱 복귀 후 신규 앱 재도입 및 점수 투영 보정은 확인하지 않았다. 운영 DB는 조회만 했다.

별도 PostgreSQL 17/PostGIS 3.5 이미지의 격리된 테스트 테이블에서 소유권 UPDATE를 커밋한 직후 응답 실패를 모의했다. 재조회로 커밋 결과를 확인했고, 이미 변경된 행에 대해 이전 NULL 소유자를 조건으로 다시 변경하려는 시도는 거절됐다. 같은 격리 DB에서 실제 prepared transaction과 유휴 연결을 만들고 제거하며 이행 도구의 대기 조회가 이를 감지하는 것도 확인했다. 이는 DB 조건과 응답 유실 처리의 일부만 확인한 것이며 운영 이행 전체 검증은 아니다.
