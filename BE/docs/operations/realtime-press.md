# 실시간 프레스 배포·활성화·중단·복구

기준: [입력·복구 계약](../decisions/realtime-press-contract.md), [ADR-0042](../adr/0042-fence-press-admission-during-deployment.md).
이 문서는 절차와 실행 조건이다. 실제 개발·운영 ON 리허설, 운영 이행, 실기기·부하·화면 1초 목표를 통과한 기록이 아니다.

## 서로 다른 네 작업

| 작업 | 공개 설정 | 저장 자격과 입력 |
| --- | --- | --- |
| 정상 ON 배포 | `enabled`·`activation_date` 유지 | 잠시 입력을 차단하고 새 컨테이너 세대로 교체한 뒤 재연결 정산 |
| 최초 활성화 | 개발은 최초 계약 1→2 이행 성공 뒤 자동 활성화 | HTTP를 유지하면서 경쟁을 즉시 사용 가능하게 함 |
| 긴급 중단 | `enabled=false`, 기존 날짜 보존 | 진행 저장 종료·기존 연결 무효화 후 HTTP와 복구 전용 연결만 재개 |
| 중단 후 재활성화 | 자동 수행하지 않음 | 원인·정합성·앱 준비를 확인한 뒤 별도 승인 후 즉시 활성화 |

서버 세대는 저장 자격이다. 공개 스위치를 켜는 것과 다르며 클라이언트가 blue/green 또는 목적지 서버를 선택하지 않는다.
일반 배포마다 사람이 경쟁 ON을 다시 켜지 않는다. 새 앱은 WS 입력을 HTTP로 fallback하지 않는다.

## 실행 전 고정할 내용

실제 실행 요청마다 아래를 확정한다. 과거 인수인계의 UUID·컨테이너 ID를 현재 값으로 대입하지 않는다.

- 대상 환경·SSH 호스트·API 주소, 소스 SHA와 실제 이미지 ID·계약 라벨.
- 현재 컨테이너 ID·시작 시각·재시작 횟수, 설정 UUID·실행 UUID·DB 소유권, `enabled`·`activation_date`, DB 목적지.
- 전환·백업 기록 유무, 실제 HTTPS 라우팅, 실행 시각·담당자·관측 항목.
- 전용 시험 기기와 데이터 범위, 중단 기준·복구할 이미지 및 허용할 명령. HTTP POST 응답이 유실되면 자동 재전송하지 않는다.
- 최초 공개에는 모든 HTTP 쓰기 경로·투영·일일 공개 ID·실제 클라이언트 지원과 전환 증거가 필요하다. 이 문서만으로 준비 완료를 판정하지 않는다.

컨테이너·이미지·DB·날짜·공개 상태가 예상과 다르거나 기록이 남아 있으면 다음 변경을 중단하고 읽기 전용으로 정산한다.
토큰·JWT 키·DB 비밀번호를 출력하거나 기록에 넣지 않는다.

## 이미지 계약과 최초 이행

| 이미지 계약 | 허용 범위 |
| --- | --- |
| `press-generation-contract=1` | 기존 공통 저장·세대 울타리. ON 입력 차단·복구 전용 WS까지 지원한다고 판단하지 않음 |
| `press-generation-contract=2` | 공통 저장에 더해 지속 입력 차단·복구 전용 WS 지원. ON 배포는 양쪽 이미지 모두 이 계약 필요 |

새 이미지는 `/app/press-admission`과 필수 설정을 사용한다. 최초 파일이 없으면 CLOSED로 시작하고 부팅만으로 DB 소유권을 얻거나 입력을 열지 않는다.
파일은 컨테이너의 쓰기 계층에 두며 tmpfs·공유 볼륨으로 옮기지 않는다. 같은 컨테이너 재시작은 파일과 UUID를 보존하고, 새 컨테이너는 새 UUID·CLOSED로 시작한다.
구형 OFF 도구는 계약 2를 거절한다. 새 도구·이미지를 함께 도입하고 최초 계약 2 이행은 OFF에서 수행한다.

개발 서버에서 계약 1의 경쟁 OFF·날짜 미설정 상태를 계약 2로 처음 이행하는 경우, 전환과 이전 서버 정리가 검증된 뒤 DB 시각의 당일 KST 날짜로 경쟁을 활성화한다. 기존 점수와 날짜별 공개 ID는 보존한다. 이미 ON인 정상 배포는 ON과 기존 활성화 날짜를 그대로 유지한다. 개발 최초 활성화는 개발 서버 전체에 적용되며 실제 배포와 활성화는 별도 승인 후 실행한다.

`migrate_legacy_generation`은 임의 세대 프로세스의 승인된 최초 OFF 이행에만 사용하는 실행별 입력이다.
개발의 기존 이행은 완료됐으므로 다음 일반 배포는 기본 `false`를 사용한다. ON 또는 실패 우회를 위한 옵션이 아니다.

운영은 현재 단일 앱 Compose·기존 배포 경로다. 계약 2 이미지는 기존 운영 워크플로에서 설정 전송·앱 교체 전에 거절한다.
운영의 이미지·스키마·세대·저장 경로를 따로 확인하고 승인된 전환 경로를 준비해야 한다. 개발 blue/green 성공으로 운영 준비 완료를 선언하지 않는다.

## 정상 전환

1. 기존 실제 라우팅·DB 소유권·실행 인스턴스를 확인하고 전환 기록을 만든다. 후보는 새로운 UUID로 예열하며 입력은 CLOSED다.
2. 원본 입력을 PAUSED로 바꾼다. 공통 DB 행의 조건부 UPDATE가 진행 공유 잠금 트랜잭션의 커밋·롤백을 기다린 뒤 소유권을 교체한다. 같은 트랜잭션에서 기기 연결 자격을 무효화한다.
3. 원본을 CLOSED로 바꾸고 모든 연결 참조 해제를 확인한다. nginx 설정 검사·reload 후 실제 HTTPS의 `X-Upstream`·응답 본문·실행 UUID·DB를 다시 대조한다.
4. 후보 개방 **시도**를 영속 기록한 다음 후보를 OPEN으로 바꾼다. 앱은 새 연결에서 `session.ready`와 미확인 정산을 완료한 뒤 신규 입력을 재개한다.
5. 검증된 원본의 이전 nginx 워커·요청 종료를 확인하고 고정 컨테이너 ID로 정리한다. 완료 기록은 소유권·프로세스·개방 상태를 최종 확인한 뒤 정리한다.

차단 파일은 `MODE revisionUUID serverGenerationUUID` 한 줄이다. 각 변경은 컨테이너 내부 배타 잠금에서 예상 내용과 비교하고 새 revision으로 원자 교체·동기화한다.
앱은 DB 공유 잠금 전·후에 같은 OPEN revision인지 검사한다. PAUSED→OPEN을 가로질러 늦게 잠금을 얻은 요청도 예전 개방 자격을 재사용하지 못한다.
지연된 개방 명령이 후속 CLOSED를 덮어쓰지 못하며 명령 응답 유실은 정확한 revision 재조회로 판정한다.
`.closed` 확인 파일은 해당 revision의 **논리적 연결 해제** 확인이다. 실제 TCP 종료·nginx 이전 워커 종료와 구분한다.

전환 중 프레스 요청은 일시 거절될 수 있다. 기존 저장 잠금은 공정성이나 최대 대기 시간을 보장하지 않는다.
DB 잠금·문장·연결과 각 검증 단계는 유한한 제한 시간을 사용하고, 초과하면 성공을 추정하지 않는다. 앱의 20초 자동 복구 상한을 배포 시간 보장으로 사용하지 않는다.

## 실패와 복귀

| 실패 경계 | 처리 |
| --- | --- |
| 원본 입력 차단 전 예열·검사 실패 | 기존 원본의 소유권·라우팅·ON 상태 보존 |
| 후보 개방 시도 전, 실행 신원·차단·DB·프록시 모두 확인 가능 | 후보 차단 유지, DB 소유권·연결 자격 정리, 원본 라우팅·구 연결 종료 확인 후 ON 유지 자동 복귀 |
| 후보 개방 시도 이후 | ON 자동 복귀 금지. 안전하게 확인 가능한 범위에서 경쟁 OFF·양쪽 입력 차단. 호환 이미지·현재 소유권을 확인한 별도 복구 |
| DB·게이트·라우팅·실행 결과 불확실 | 두 서버·전환 기록 보존, 입력 개방 금지. OFF·복구가 확인됐다고 보고하지 않음 |

개방 명령의 응답이 유실되면 아직 개방 전이라고 판단하지 않는다. OPEN_ATTEMPTED 기록은 명령보다 먼저 영속화한다.
원본이 재시작·교체됐다면 같은 UUID라는 이유만으로 복귀하지 않는다. DB에 NULL 또는 과거 UUID를 강제로 쓰지 않는다.
이미 반영된 점수·입력 최종 결과를 지우거나 배포 이전 합계로 되돌리지 않는다.

계약 2 경로는 양쪽 프로세스의 실제 응답과 차단 상태를 확인해야 한다. 후보가 종료돼 런타임 검증을 할 수 없으면 개방 전이라도 ON 자동 복귀를 중단한다.
`restart=unless-stopped`인 컨테이너가 잠시 정지해 있다는 관측만으로 이후 저장이 불가능하다고 판단하지 않는다.
이 경우 원본 입력 차단·두 컨테이너·기록을 유지하고 실행 인스턴스·재시작 정책·현재 DB를 확인한 별도 복구를 준비한다. 비상 OFF도 확인하지 못했다면 OFF 완료로 보고하지 않는다.

배포 후 결함 때문에 이전 이미지로 돌아가는 작업은 위의 ‘개방 전 자동 복귀’가 아니다.
공개를 OFF로 중단하고 현재 공통 저장·복구 계약을 지원하는 이미지를 새 컨테이너·새 UUID로 배포한다.
공통 저장 계약을 모르는 옛 바이너리는 별도의 입력 중단·진행 작업 종료·원본/투영 재집계 검증 절차가 필요하며 이 도구의 정상 복귀 대상으로 사용하지 않는다.

## 활성화·중단 명령

다음 예시는 개발의 승인된 운영 디렉터리에서 현재 조회값을 대입하는 형식이다. 명령을 적었다는 사실은 실행 승인이 아니다.
`--probe-port`는 기본 443이며 로컬 격리 시험에만 다른 포트를 쓴다. 현재 도구의 라우팅 검증은 개발 API를 대상으로 한다.

```bash
cd /opt/pheeeew
python3 press-generation.py status CURRENT_CONTAINER

python3 press-generation.py activate CURRENT_CONTAINER \
  --expected-generation CURRENT_UUID \
  --expected-activation-date null

python3 press-generation.py stop CURRENT_CONTAINER \
  --expected-generation CURRENT_UUID \
  --expected-activation-date CURRENT_ACTIVATION_DATE
```

`null`은 실제 DB 날짜가 NULL일 때만 사용한다. 재활성화는 현재 보존된 날짜를 예상값으로 전달한다.
활성화 날짜는 DB의 현재 KST 날짜로 정해 즉시 경쟁을 켠다. 잠금 확보 전후에 날짜가 바뀌면 추측하지 않고 중단한다.
과거 점수·일일 공개 ID를 초기화하지 않는다.

정상 `stop`은 PAUSED → 진행 작업 종료·조건부 OFF·연결 자격 무효화 → CLOSED·연결 해제 확인 → 현재 소유권·실제 라우팅 확인 → HTTP/복구 전용 재개 순서다.
경쟁은 계속 OFF다. 재활성화는 원인을 해결하고 별도 승인을 받은 뒤 실행한다.
실패한 전환 기록이 남아 있는 상태에서 일반 `stop`·`activate`를 반복 실행해 우회하지 않는다. 우선 `status`로 실제 DB·양쪽 프로세스·입력 차단 상태를 확인한다.

### 활성화·중단 명령 자체가 끊긴 경우

`kind=activate/stop` 기록에는 변경 전·의도한 최종 제어값, DB에서 확인한 날짜, DB 목적지·프로세스 신원·게이트 명령을 보존한다.
이 기록은 배포 중 비상 OFF 기록과 다르므로 `resume-off`로 처리하지 않는다. 먼저 조회하고 별도로 승인한 정산 명령을 사용한다.

```bash
python3 press-generation.py status CURRENT_CONTAINER

# 중단 명령의 정산: ORIGINAL_DATE는 기록에 있는 변경 전 날짜다.
python3 press-generation.py reconcile-control CURRENT_CONTAINER \
  --expected-generation RECORDED_UUID \
  --expected-activation-date ORIGINAL_DATE_OR_null

# 활성화 명령의 정산은 기록된 활성화 날짜를 사용한다.
python3 press-generation.py reconcile-control CURRENT_CONTAINER \
  --expected-generation RECORDED_UUID \
  --expected-activation-date ORIGINAL_DATE_OR_null
```

활성화 정산은 **경쟁을 켜는 SQL을 실행하지 않는다.** 현재 DB가 기록된 최종 상태이면 반영을 확인하고 기록을 정리한다.
변경 전 상태만 조회된 경우에는 **미확정으로 기록을 보존한다.** 원래 도구가 종료돼도 자식 `psql`·DB 명령이 아직 실행 중이거나 늦게 커밋할 수 있으므로, 이를 취소·미실행 완료로 보고하지 않는다.
다른 상태도 추정하지 않고 기록을 유지한다. 원래 명령의 최종 종료와 실제 DB를 확인한 별도 정산 없이는 새 활성화·배포를 시작하지 않는다.
다시 활성화하려면 새 실행 시점과 별도 실행 승인을 판단한다.

중단 정산은 같은 실행 인스턴스·DB·실제 라우팅을 증명하고 단계별 기록에 따라 OFF·진행 작업 정리·CLOSED 확인·HTTP 재개를 마친다.
이전 개방 명령의 응답이 유실돼도 기록된 같은 CAS 의도만 정산한다. 같은 제어값이 조회된다는 이유만으로 진행 작업 종료까지 확인됐다고 판단하지 않는다.
현재 프로세스·날짜·게이트 revision이 예상과 다르면 새 입력을 열거나 기록을 지우지 않는다.

### 개방 시도 이후 비상 중단에서 HTTP만 복구

`EMERGENCY_OFF_CONFIRMED`는 DB OFF와 양쪽 CLOSED를 확인한 상태이며 서비스 재개 완료가 아니다.
실제 DB의 현재 소유자가 여전히 같은 실행 인스턴스이고 그 서버로 라우팅됨을 확인한 뒤, 별도 복구 승인으로 다음 명령을 사용한다.

```bash
python3 press-generation.py resume-off CURRENT_OWNER_CONTAINER \
  --expected-generation CURRENT_OWNER_UUID \
  --expected-activation-date CURRENT_ACTIVATION_DATE
```

이 명령은 계약 2 서버들의 CLOSED·연결 해제 확인과 지연 개방 명령의 revision 무효화를 확인한 뒤 **현재 소유자의 HTTP·복구 전용 연결만** 연다.
현재 소유자는 반드시 계약 2여야 한다. 최초 OFF 이행의 나머지 서버가 계약 1이면, 같은 DB에서 현재 소유자가 아니며 원래 프로세스 신원이 유지돼 저장 울타리로 차단됨을 검증한 경우만 허용한다. 계약 1을 새 소유자로 지정하거나 차단 기능이 있다고 판단하지 않는다.
DB 소유권·공개 날짜·`enabled=false`를 바꾸지 않는다. 응답이 유실되면 새 동작을 추측해서 보내지 않고 저장된 의도와 현재 상태를 다시 확인한다.
완료 상태 `HTTP_RECOVERED`에서도 두 컨테이너와 전환 기록을 보존한다. 다음 배포 전에 이전 nginx 워커·요청 종료, 현재 소유권·실제 라우팅, 보존할 컨테이너·이미지를 확인한 별도 정리가 필요하다.
전환 기록만 삭제해서 새 배포를 강행하거나 이전 UUID를 DB에 복원하는 절차가 아니다.

## 로컬 검증과 실제 리허설의 구분

- 실제 Spring HTTP·인증 WS와 PostgreSQL 17/PostGIS 3.5에서 저장·차단·정산·최종 결과 보존을 검증한다.
- Docker/nginx 전환 스크립트 회귀의 Python 앱 스텁과 실제 Spring 이미지 통합 검증을 구분한다.
- 작은 수신 버퍼의 느린 연결 종료는 기능 검증이며 운영 규모·전송 지연의 측정 결과가 아니다. 서버 송신 성공을 앱 표시 완료로 대신하지 않는다.
- 실제 리허설은 대상 SHA·이미지·환경·시점·시험 데이터·중단·복구 기준을 고정해 별도 승인받는다. 실제 실행 전까지 개발 ON·운영 이행·실기기·부하·#924 전체 완료를 표시하지 않는다.
